**Omega-serv** — это HTTP/1.1-сервер, написанный на чистом Python (только стандартная библиотека для ядра сервера), предназначенный для раздачи статического контента и, опционально, PHP-FPM, с неотключаемым усилением протокола и наслаиваемыми (а не обязательными) модулями безопасности (WAF, TLS, аутентификация). Седьмой инструмент в наборе `omega-`, но намеренно **вне будущей интеграции `omega-suite`** (работает на локальной машине, где размещён, а не с удалёнными целями — то же семейство, что и `omega-fire`); построен по принципам Clean Architecture, `bootstrap/` выполняет роль корня композиции.

## 1. Видение и рамки

Заявленный приоритет — **прочность/безопасность ядра HTTP прежде всего** — WAF и TLS являются опциональными модулями, накладываемыми поверх, но никогда не обязательными предпосылками. Сервер, который делает одну вещь (раздаёт файлы, опционально PHP), но делает это правильно, с реальным, неотключаемым усилением протокола, вместо сервера, который делает многое наполовину.

### Что делает Omega-serv

- Раздаёт статический контент (файлы, опциональный листинг каталогов, алиасы, редиректы, переписывание URL, кэш) с безопасным разрешением путей (traversal, двойное кодирование, символические ссылки).
- Усиливает протокол HTTP по умолчанию, без возможности отключения: явный список разрешённых методов, проверка заголовка `Host`, отклонение неоднозначности `Content-Length`/`Transfer-Encoding`, неотключаемые заголовки безопасности и базовая CSP.
- Опционально: фильтрация WAF (сигнатуры, ограничение частоты запросов, список блокировки), прямой TLS (самоподписанный сертификат, подписанный локальным CA, или публичный через Let's Encrypt/Certbot с автоматическим продлением — см. §9), HTTP Basic-аутентификация по зонам, PHP через FastCGI/PHP-FPM, изолированные зоны загрузки.
- Проверяет собственную конфигурацию (`audit security`) и устанавливается как системная служба (systemd/OpenRC/runit).
- Полностью скриптуемый неинтерактивный CLI **и интерактивный интерфейс (Textual)**, оборачивающий ровно те же сценарии использования — см. §3. Дорожная карта интерфейса (`OMEGA-SERV_PLAN-DETAILLE_INTERFACE.md`, §12) **полностью реализована**: реестр возможностей, профили/опции, детальная настройка (алиасы/редиректы/переписывание URL/FastCGI/листинг каталогов/аутентификация/кэш/WAF/доверенные прокси/исходящий reverse proxy/TLS), управление логами (Библиотека/Избранное, 3 просмотрщика — простой/классический/объединённый lnav —, Просмотр и обработка IP, удалённые источники SSH, ротация/резервное копирование/автоматизация/восстановление/очистка/экспорт), системная служба, мульти-инстанс (реестр, создание), проверка/симуляция/аудит, резервное копирование/восстановление конфигурации, мастер первого запуска, настройки приложения (тема, профиль рендеринга, пути экспорта/скриншотов), контекстный гид-справка (карточка для каждого экрана с конкретными примерами, FAQ, экспорт в HTML, исчерпывающее покрытие, проверенное тестами), систематическое указание необходимости перезагрузки/перезапуска после каждого сохранения, полная настройка Active Defense без ручного редактирования файла.

### Чего Omega-serv не делает

- Чистый CGI (исключён из рамок V1 — поддерживается только FastCGI/PHP-FPM).
- Взаимная аутентификация TLS (mTLS), OCSP stapling — вне рамок V1, см. §15. (ACME/Let's Encrypt через Certbot доступен, см. §9c/9d.)
- HTTP-кэш, разделяемый между процессами.
- Сканирование/аудит удалённой цели (для этого см. `omega-check`/`omega-scan`/`omega-deep` — Omega-serv проверяет только сам себя, никогда не третью сторону).

### Предупреждение об использовании

Omega-serv **отказывается запускаться от root**. Ни один модуль безопасности (WAF, TLS, аутентификация) не включён по умолчанию ни в одном из поставляемых профилей, включая `hardened` — их включение всегда явное действие (`config enable-tls`, `option enable waf`...). Сам профиль `hardened` рекомендует обратный прокси для реальной экспозиции в Интернет, а не заменяет его собой.

## 2. Установка

### Требования

- Python 3.10+
- `openssl` (бинарный файл, а не библиотека Python) для всего, что касается TLS-сертификатов — остальные функции работают без него.

### Установка

> ⚠️ **Обновляете существующую установку?** Команда ниже **молча пропускает распаковку**, если `omega-serv/` уже существует (она предполагает прерванную первую установку, а не обновление) — вы бы тогда переустановили зависимости поверх **старого, неизменённого кода**, без единого сообщения об ошибке. Используйте раздел [Обновление](#обновление) ниже вместо этого.

```bash
[ -d omega-serv ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-serv.tar.gz
cd omega-serv/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. Создаёт виртуальное окружение `.venv`, если оно ещё не существует.
2. Устанавливает пакет (`pip install -e .`) — **никаких внешних зависимостей** (см. §6).
3. Делает `omega-serv.sh` и `install.sh` исполняемыми.
4. Добавляет алиас `serv` в `~/.bashrc` и `~/.zshrc` (без дублирования, если уже присутствует).

### Обновление

Если `omega-serv/` уже существует (предыдущая установка), **никогда не запускайте `tar` из этой папки**: она попытается создать вложенную `omega-serv/omega-serv/` и завершится с ошибкой. В отличие от omega-fire, `install.sh` здесь никогда не изменяет права доступа к папке (ни один шаг не использует `sudo`) — поэтому риска папки, принадлежащей `root`, нет, и распаковка прямо поверх существующей установки безопасна.

```bash
# Из РОДИТЕЛЬСКОЙ папки omega-serv/ (никогда не изнутри неё)
tar -xzf omega-serv.tar.gz
cd omega-serv/
./install.sh
```

Архив намеренно исключает все живые данные (`var/db/`, `var/log/`, `var/backups/`, `secure/secrets/`, `secure/certificates/*.key`, `config/omega-serve.json`, **`webroot/` — реально обслуживаемый сайт**...) — распаковка поверх существующей установки никогда не затрагивает ваши данные, сертификаты, настройки или обслуживаемый контент, заменяется только код приложения. `install.sh` использует уже существующий `.venv` и просто переустанавливает в него зависимости.

> ⚠️ **Если сервис уже активен, одного шага выше недостаточно.** Он заменяет код на диске, но уже запущенный процесс продолжает работать со старым кодом, загруженным в память — после этого всегда требуется **полный перезапуск**:
> ```bash
> sudo systemctl restart <имя-сервиса>
> ```
> **Никогда не простая перезагрузка** (`systemctl reload`, или экран СЕРВИС → *Перезагрузить*): она перечитывает только некоторые параметры конфигурации (правила WAF, зоны аутентификации...), **но никогда сам код Python**. `systemctl status <имя-сервиса>` с датой запуска старше вашего обновления подтверждает, что сервис всё ещё работает на старом коде. Если вы всегда обновляетесь, перезаписывая ту же папку (стандартный случай выше), этот перезапуск — единственный недостающий шаг, переустановка сервиса не требуется.

> ⚠️ **Если после этого сервис уходит в цикл перезапуска** (`systemctl status` чередует active/inactive, `journalctl -u <имя-сервиса>` показывает `PermissionError` при записи файла в `var/`): `tar` восстанавливает права директорий такими, какими они были захвачены в архиве, что может стереть разделение прав, настроенное для выделенной системной учётной записи при первоначальной установке — даже если сам `install.sh` никогда их не трогает. Переустанавливать юнит не нужно: экран СЕРВИС → **Исправить права** (повторно применяет разделение прав на `var/` и `secure/auth/`, не трогая сам юнит systemd).

### Зависимости

Ядро сервера (парсер HTTP/1.1, клиент FastCGI, хеширование паролей через `hashlib.scrypt`) остаётся на чистом Python/stdlib, а всё, что касается TLS-сертификатов, проходит через бинарный файл `openssl` как подпроцесс, а не через криптографическую библиотеку Python — **никаких внешних зависимостей для этого**. Только интерактивный интерфейс (§3) вводит некоторые: `omega-lib` (темы, определение терминала — общая библиотека набора, не опубликована на PyPI, включена в распространяемый архив), `textual` и `pyte` (эмуляция терминала для объединённого рендеринга `lnav` внутри интерфейса), `jinja2` (тематизированный экспорт HTML) и `psutil` (экран "Состояние и Ресурсы" — CPU/RAM/диск/сеть). Опциональная зависимость для разработки/тестирования (`pip install -e ".[test]"`): `hypothesis` (property-based тесты для HTTP-парсера и резолвера путей, никогда в продакшене). Инструменты качества (`pip install -e ".[dev]"`): `pytest`, `ruff`, `mypy`, `import-linter`. Дополнительный опциональный экстра (`pip install -e ".[magnet]"`): `lupa` (встроенная привязка Lua, предкомпилированное колесо, системный интерпретатор `lua` не требуется), используется только дополнительным WAF-скриптом "magnet" (§7) — никогда не устанавливается по умолчанию; его отсутствие отображается (возможность `waf-magnet`, экран **Возможности**) с точной командой установки, без блокировки остальной части сервера.

### Рекомендуемые опциональные инструменты

Интерфейс работает в деградированном режиме, если эти инструменты отсутствуют:

- `openssl` — необходим для всего, что связано с TLS-сертификатами (самоподписанный, локальный CA, импорт); без него команды `certs *` не работают, но остальной сервер функционирует нормально (см. §9).
- `certbot` — необходим только для мастера **Let's Encrypt** и его автоматического продления (§9c/9d); самоподписанному TLS/локальному CA он никогда не требуется.
- `lnav` — расширенный анализ логов, встроенный в экран **Управление логами** (§3); при отсутствии исполняемого файла — чёткое явное сообщение об ошибке, никакого краха, остальная часть экрана (просмотр/слежение/ротация/статистика) работает нормально и без него.
- `scp` (пакет `openssh`/`openssh-clients`, почти всегда уже установлен) — нужен только для **Удалённых источников (SSH)** (§13a); без него получение завершается чётким сообщением об ошибке, остальная часть Библиотеки работает нормально.
- `python-psutil` (системный пакет, эквивалентный `psutil` из PyPI) — в любом случае устанавливается автоматически через `pip install -e .` (обязательная зависимость пакета, экрану **Состояние и Ресурсы** он всегда нужен), но предустановка через системный менеджер пакетов избавляет `pip` от необходимости локально компилировать его wheel.

```bash
# Arch Linux и производные (Manjaro...)
sudo pacman -S openssl certbot lnav python-psutil openssh

# Debian/Ubuntu и производные
sudo apt install openssl certbot lnav python3-psutil openssh-client

# Fedora
sudo dnf install openssl certbot lnav python3-psutil openssh-clients
```

## 3. Использование

Два функционально строго эквивалентных интерфейса, логика никогда не дублируется между ними: неинтерактивный CLI (скриптуемый, используется ниже) и интерактивный интерфейс Textual (меню, формы, таблицы) — каждое действие одного существует на стороне CLI, интерфейс лишь оборачивает те же сценарии использования.

### Интерактивный режим (TUI)

Рекомендуется для повседневного использования — запускается без аргументов:

```bash
./omega-serv.sh
```
если вы создали псевдоним, просто введите `serv` в терминале:
```bash
serv
```

### Общий путь пользователя

Экран заставки (splash, закрывается по клавише или клику) → главное меню (Мастер первого запуска / Реестр возможностей / Профили / Детальная настройка / Активная безопасность / Управление логами / Служба / Мульти-инстанс / Состояние и Ресурсы / Аудит / Резервное копирование) → выбор раздела, затем действия — каждая форма проверяет обязательные поля перед продолжением → явное подтверждение перед любой чувствительной или разрушительной операцией (перезапуск, удаление, восстановление...) → систематическое указание, что делать дальше (автоматическая горячая перезагрузка либо подтверждение полного перезапуска) после каждого сохранения, изменяющего уже обслуживаемую конфигурацию. Адаптация к терминалу (цвета, размер, структурная деградация профиля рендеринга) автоматическая, без ручных флагов — см. §4.

#### Клавиатурные сочетания (интерактивный интерфейс)

| `Ctrl+P` | Палитра команд (Тема, Скриншот, Настройки...) |

#### Гид-справка (клавиши `F1`/`a`)

Встроенная система справки, никогда не простой статический текст: каждый документированный экран (карточка: определение/поля для заполнения с конкретными примерами/выполняемое действие/реакция — перезагрузка, перезапуск или ничего) доступна прямо с него по клавише `F1`; клавиша `a` открывает полное меню (структура идентична реальной навигации приложения) с доступом к FAQ (реальные подводные камни, встреченные на практике, напр. классы атак Active Defense, права доступа общего файла лога службы) и автономным экспортом в HTML (с сохранением активной темы) всего гида целиком. Резервный переход на общий справочный экран, пока для конкретного экрана ещё нет карточки — на данный момент покрытие исчерпывающее, проверено тестом.

#### Главное меню (интерактивный интерфейс)

- **Мастер первого запуска** — управляемый путь из 8 шагов (приветствие → возможности только для чтения → выбор профиля → bind/порт → опциональный TLS → проверка → итог + запись → предложение установки службы); позволяет сгенерировать полную конфигурацию и запустить сервер, ни разу не обращаясь к CLI.
- **Реестр возможностей** — проверка системы только для чтения (система инициализации, занят ли уже настроенный порт, наличие `openssl`/`logrotate`/`tailscale`/`lnav`, дисковое пространство, лимит дескрипторов...), экспорт JSON/HTML.
- **Профили** — тот же сценарий использования, что и `profile` в CLI (§5), diff всегда показывается перед записью.
- **Детальная настройка сервера** — полный CRUD по алиасам/редиректам/переписыванию URL/листингу каталогов/доверенным прокси/исходящему reverse proxy/FastCGI/кэшу/аутентификации/контролю доступа/страницам ошибок, плюс подменю **TLS** (статус, генерация самоподписанного сертификата, мастер локального CA, мастер Let's Encrypt/Certbot, автоматическое продление, отзыв, включение/отключение — см. §9); второй блок, **ОПЦИИ И ПРОВЕРКА**, объединяет быстрые ссылки на **Опции** (`option` CLI, §7) и **Проверить конфигурацию** (`config check` CLI, §10) — тот же сценарий, что настроить опции и затем проверить, эти два экрана больше не доступны напрямую из главного меню. WAF здесь больше не живёт (см. "Активная безопасность" ниже): он в основном раскрывает непрерывно меняющееся операционное состояние, а не простую статическую форму настройки. Каждое сохранение систематически указывает, что делать дальше: автоматическую и бесшумную горячую перезагрузку, если служба активна (листинг каталогов, доступ, алиасы/редиректы/переписывание URL, кэш, страницы ошибок, доверенные прокси, зоны reverse proxy/FastCGI, пользователи/зоны аутентификации), либо явное подтверждение полного перезапуска, когда изменение затрагивает слушающий сокет, TLS или Active Defense — больше ни один экран не оставляет догадываться, нужно ли перезапускать сервер.
- **Активная безопасность** — единый экран, объединяющий два блока РЯДОМ ДРУГ С ДРУГОМ: **Active Defense** (Состояние, Отслеживаемые угрозы со score/уровнем, Инциденты с хронологией/экспортом IoC/отчётом, назначения Deception, Симуляция решения в режиме dry-run, **Настройки** — полная конфигурация без ручного редактирования `config/omega-serve.json`, см. §11) и **WAF** (Состояние, Модули — режим/наборы правил/список блокировки, Тестирование запроса, Custom — создание собственного правила, Magnet — импорт внешнего скрипта `mod_magnet` с проверкой совместимости перед активацией) — см. §11.
- **Управление логами** — меню из двух колонок. Колонка **Библиотека**: центральный узел, ссылающийся на все логи для обработки (ручное наполнение — один клик по умолчанию добавляет логи, собственные для этого экземпляра: access/error/нативный WAF, + скрипт magnet §7, если активен —, либо **удалённый источник**, полученный по SSH, см. ниже); **Избранное** (сохранённая под именем комбинация логов + просмотрщика, прямой запуск); **Просмотр логов** с выбором из 3 просмотрщиков в зависимости от числа выбранных логов — Простой (слежение в реальном времени + общая статистика: уникальные IP/доля ошибок/коды HTTP для любого формата), Классический (чтение + слежение), объединённый `lnav` (настоящий рендеринг терминала внутри интерфейса, логи magnet включены по умолчанию + ручные пути, **закреплённые** для сохранения между сессиями); **Просмотр и обработка IP** (топ IP по одному или нескольким выбранным логам, период 24ч/7д/30д/всё, удаление IP). Колонка **Обслуживание** (без изменений): ручная или автоматическая по порогу размера ротация/архивация, немедленное создание резервной копии, настройка/управление запланированными автоматизациями (декларативно — см. примечание ниже), восстановление/очистка архива, экспорт списка.
- **Служба** — те же действия, что и `service` в CLI (§12), разовое повышение привилегий `sudo` на каждое действие, всё приложение целиком никогда не запускается от root.
- **Мульти-инстанс** — глобальный реестр (`~/.config/omega-serv/instances.json`, вне любого каталога проекта) известных установок на этой машине с systemd-статусом каждой; создание новой инстанции (копирование дерева, собственное свежее виртуальное окружение и зависимости, свежая конфигурация с отдельным портом, проверки на вложенность и конфликт портов) прямо из интерфейса. Кнопка остаётся визуально незаметной при одной установке (метка "Мульти-инстанс" становится "Инстансы (N)" начиная с 2 известных); полное переключение на другую инстанцию тоже доступно (`os.execv`, явное подтверждение, отдельный экран-заставка, объявляющий переключение при перезапуске); полное удаление инстанции (юнит, выделенная системная учётная запись — если её больше не использует ни одна другая инстанция — и, по желанию, каталог, никогда по умолчанию).
- **Состояние и Ресурсы** — обзор на первый взгляд, обновляется каждые 2 секунды: состояние сервера (процесс/PID, статус системной службы, активный профиль/опции/TLS/порт), живой поток лога доступа (пропускная способность, разбивка по кодам статуса, уникальные IP, доля ошибок), системные ресурсы (CPU/RAM/диск/подкачка/нагрузка/сеть через `psutil`); также объединяет быстрый доступ **Симулировать запрос** (тот же сценарий использования, что и соответствующая команда CLI, §10).
- **Аудит безопасности** — тот же сценарий использования, что и соответствующая команда CLI (§10).
- **Резервное копирование конфигурации** — tar.gz-архив файла конфигурации и, по явному выбору, правил WAF/зон аутентификации/сертификатов (обязательное подтверждение при включении реальных секретов)/базы Active Defense, восстановление, список, удаление.

> Примечание о запланированных автоматизациях ротации: они регистрируются (частота + целевой лог), но **ничто не выполняет их автоматически** — ни в интерфейсе, ни в виде фоновой задачи. Это осознанный выбор в пользу паритета с эквивалентным экраном в `omega-fire`, который имеет ровно такое же исключительно декларативное поведение. Реальное периодическое выполнение (таймер systemd, фоновая задача) станет отдельной работой в будущем, только при подтверждённой необходимости.

#### Настройки приложения (клавиша `o` или палитра команд)

Только настройки интерфейса — никогда не путать с `config/omega-serve.json` (собственная конфигурация сервера): активная тема, профиль рендеринга (`complete`/`standard`/`reduced`/`mono`, требуется перезапуск), путь экспорта (`var/exports/` по умолчанию), путь скриншотов (`var/screenshots/` по умолчанию), очистка любой из двух папок (требуется подтверждение).

```bash
# Запустить сервер (на переднем плане, SIGTERM = аккуратная остановка с периодом ожидания, SIGHUP = горячая перезагрузка WAF/Auth)
./omega-serv.sh serve

# Конфигурация
./omega-serv.sh config init                # генерирует config/omega-serve.json (безопасные значения по умолчанию)
./omega-serv.sh config check                # проверяет без запуска (те же блокирующие условия, что и при запуске)
./omega-serv.sh config show
./omega-serv.sh config enable-tls --cert ... --key ... --mode direct
./omega-serv.sh config disable-tls

# Профили (minimal / standard / hardened / development)
./omega-serv.sh profile list
./omega-serv.sh profile show hardened
./omega-serv.sh profile apply hardened --dry-run   # diff перед применением, всегда

# Опции (aliases, redirects, rewrites, dirlisting, cache, waf, upload, fastcgi, reverse_proxy...)
./omega-serv.sh option list
./omega-serv.sh option enable waf
./omega-serv.sh option disable waf

# Симулировать запрос без запуска сервера (полезно для проверки правила перед включением)
./omega-serv.sh simulate-request GET /index.html

# WAF (работает даже при отключённой опции, через неявный --force)
./omega-serv.sh waf test --method GET --path /admin --remote-ip 203.0.113.1
./omega-serv.sh blocklist list
./omega-serv.sh blocklist add --network 203.0.113.0/24 --reason "обнаружено сканирование" --duration-seconds 3600
./omega-serv.sh blocklist remove --network 203.0.113.0/24

# Active Defense (deception + режим войны, опция "active_defense" - см. §11)
./omega-serv.sh active-defense status
./omega-serv.sh active-defense simulate --ip 203.0.113.42 --path /wp-login.php --attack-class scan --score 40
./omega-serv.sh active-defense purge
./omega-serv.sh threats list --level hostile
./omega-serv.sh threats show 203.0.113.42:ab12cd34
./omega-serv.sh incidents list --status open
./omega-serv.sh incidents show <incident-id>
./omega-serv.sh incidents close <incident-id>
./omega-serv.sh incidents export-ioc <incident-id> --format json,csv
./omega-serv.sh incidents generate-report <incident-id>
./omega-serv.sh deception list
./omega-serv.sh deception release --subject 203.0.113.42:ab12cd34

# TLS-сертификаты - самоподписанные (9a)
./omega-serv.sh certs generate-self-signed --cn localhost --san-dns localhost --san-ip 127.0.0.1
./omega-serv.sh certs show
./omega-serv.sh certs check-expiry --warn-days 30

# TLS-сертификаты - локальный CA (9b)
./omega-serv.sh certs generate-ca --cn "Мой локальный CA" --days 3650
./omega-serv.sh certs generate-csr --cn server.local --san-dns server.local --key-out server.key --csr-out server.csr
./omega-serv.sh certs sign-csr --csr server.csr --ca-key secure/certificates/ca/root-ca.key --ca-cert secure/certificates/ca/root-ca.pem --out server.pem --fullchain-out fullchain.pem
./omega-serv.sh certs revoke --cert server.pem --ca-key secure/certificates/ca/root-ca.key --ca-cert secure/certificates/ca/root-ca.pem

# TLS-сертификаты - импорт (9c, напр. из хука Certbot)
./omega-serv.sh certs import --key privkey.pem --cert fullchain.pem

# HTTP Basic-аутентификация
./omega-serv.sh auth add-user --username alice
./omega-serv.sh auth create-zone --url-prefix /admin/ --allowed-users alice
./omega-serv.sh auth list

# Аудит безопасности (никогда не блокирует, только информативный)
./omega-serv.sh audit security --format text --min-severity medium

# Резервное копирование конфигурации (конфигурация всегда включена;
# реальные секреты никогда не шифруются по умолчанию, --confirm-secrets обязателен для их включения)
./omega-serv.sh config backup --description "перед миграцией"
./omega-serv.sh config backup --include-auth --include-certificates --confirm-secrets
./omega-serv.sh config backup --include-active-defense --description "угрозы/инциденты"
./omega-serv.sh config list-backups
./omega-serv.sh config restore --snapshot-id snapshot_20260908_170003_762484

# Системная служба (systemd/OpenRC/runit, автоопределение)
./omega-serv.sh service install --user omega-serv --group omega-serv
./omega-serv.sh service start
./omega-serv.sh service status
```

### Примечательные коды завершения

| Команда | Код | Значение |
|---|---:|---|
| `audit security` | `0` | Ничего серьёзного (нет `CRITICAL`/`HIGH`) |
| `audit security` | `1` | Есть хотя бы одна находка `CRITICAL` |
| `audit security` | `2` | Есть хотя бы одна `HIGH` без `CRITICAL` |
| `audit security` | `3` | Ошибка выполнения (конфигурация не найдена...) |

| любая другая команда | `0`/`1` | Успех / неудача проверки |

## 4. Совместимость терминалов

Интерактивный интерфейс (Textual) автоматически определяет возможности терминала (эмулятор, размер) и соответственно адаптирует структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`), без ручных флагов. Режим CLI всегда остаётся простым текстом, независимо от терминала. Политика разделяется всем набором `omega-` (`omega-lib`, `terminal/policies.py`) — идентична политике `omega-check`/`omega-fire`.

### Профиль в зависимости от определённого эмулятора

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| Linux TTY, устаревший SSH | `mono` |
| Нераспознанный эмулятор | `reduced` (запасной вариант по умолчанию) |

### Профиль в зависимости от размера терминала

| Минимальный размер (колонки × строки) | Потолок профиля |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| ниже | `mono` |

Итоговый выбранный профиль — **наиболее ограничивающий из двух** (эмулятор и размер) — Ghostty на весь экран, уменьшенный до 70 колонок, опустится до `mono`, даже если его эмулятор допускал бы `complete`. Обновляется в реальном времени клавишей `r`, либо переопределяется вручную из настроек приложения (клавиша `o`, §3).

## 5. Профили

| Профиль | Назначение |
|---|---|
| `minimal` | Простая демонстрация/локальный запуск: только статика, ни одна опция не включена |
| `standard` | Статический сайт или небольшой продакшен: обычные заголовки, базовая CSP, dirlisting/CGI/FastCGI отключены |
| `hardened` | Экспозиция с минимальными привилегиями: локальный bind по умолчанию (для Интернета рекомендуется обратный прокси), только методы GET/HEAD, строгая CSP, anti-slowloris — WAF **никогда** не включается автоматически, даже здесь |
| `development` | Только для локальной разработки, никогда не представляется как пригодный для Интернета: обязательный bind на loopback, CSP в режиме report-only, подробные страницы ошибок |

Порядок слияния конфигурации: встроенные безопасные значения → выбранный профиль → сохранение текущих активных опций (переживают смену профиля) → явный пользовательский overlay. Перед записью всегда показывается полный diff (`profile apply`).

## 6. Архитектура

Clean Architecture (`core / domain / ports / application / infrastructure / interfaces / bootstrap`) — `bootstrap/` является корнем композиции (эквивалент `app/` у других инструментов набора). Осознанная особенность проекта, проверяемая `import-linter`, а не просто предполагаемая: `application/server/start_server.py` (а также `validate_config.py`, `run_audit.py`) выступают в роли **фабрик построения, зависящих от реальной конфигурации** (какой менеджер служб, включать ли WAF...) и напрямую создают экземпляры конкретных адаптеров `infrastructure/` — в отличие от более строгого паттерна CHECK/TRACK, где `application/` использует только `ports/`. Единственное действительно универсальное правило: `domain/`/`core/` никогда не зависят от внешних слоёв.

```text
src/omega_serv/
├── core/            Сквозной словарь (platform_info, константы)
├── domain/           Чистая бизнес-логика (HTTP, конфигурация, безопасность WAF/TLS/auth/audit, маршрутизация)
├── ports/            Контракты (Protocol), ожидаемые приложением
├── application/      Сценарии использования - некоторые функции (build_server...) также собирают конкретные адаптеры (см. выше)
├── infrastructure/    Реальные реализации (asyncio, openssl как подпроцесс, systemd/OpenRC/runit, файлы)
├── interfaces/cli/    Неинтерактивный CLI на argparse
├── interfaces/tui/    Интерактивный интерфейс Textual (те же сценарии использования, логика никогда не дублируется)
└── bootstrap/         DependencyContainer, определение корня проекта
```

Правила, проверяемые `import-linter` (8 контрактов): `domain`/`core` никогда не зависят от внешних слоёв; `interfaces.tui` никогда напрямую не зависит от `infrastructure`; `textual` ограничен `interfaces.tui`; `subprocess` ограничен `infrastructure/process/subprocess_runner.py` (и `infrastructure/lnav/`, интерактивный PTY-поток); `ssl` ограничен `infrastructure/tls/ssl_context_builder.py`; `jinja2` ограничен `infrastructure/exporters/html_exporter.py`; `sqlite3` ограничен `infrastructure/persistence/sqlite_active_defense_connection.py` (единственное реляционное хранилище проекта, зарезервированное для Active Defense — см. §11); `lupa` ограничен `infrastructure/waf/lua_waf_adapter.py` (дополнительный WAF-скрипт "magnet", §7).

## 7. Опциональные модули

Все отключены по умолчанию во всех поставляемых профилях — включение всегда явное (`option enable <имя>` или `config enable-tls`):

| Модуль | Роль |
|---|---|
| `waf` | Сигнатуры (чувствительные пути, сканер UA/Referer, SQLi/XSS/CMDi в теле запроса), пользовательские списки ключевых слов (текстовый файл, одно слово на строку — легко поддерживать без редактирования JSON), ограничение частоты (token bucket), список блокировки (CIDR + истечение срока), репутация/эскалация, импорт существующего WAF-скрипта Lighttpd `mod_magnet` как опциональное дополнение типа "magnet" (без переписывания, экстра `pip install -e ".[magnet]"` — аддитивно, никогда не может снять нативную блокировку; проверка совместимости при импорте, отдельный экран TUI) — режим `log-only` структурно не способен блокировать |
| TLS | Прямой (самоподписанный, локальный CA, или публичный через Let's Encrypt/Certbot с автоматическим продлением — см. §9), никогда mTLS/OCSP в V1 |
| Аутентификация | HTTP Basic по зонам (`url_prefix`), `hashlib.scrypt` с защитой от временных атак (постоянное время даже для неизвестного пользователя) |
| FastCGI/PHP-FPM | Единственная пара `(url_prefix, script_root)`, `script_root` изолирован вне `webroot/` конструктивно (статический обработчик никогда не может раскрыть исходный код PHP) |
| Исходящий reverse proxy | Omega-serv сам выступает в роли proxy к одному или нескольким backend (обратное направление `server.tls.mode = "behind_proxy"`) — балансировка нагрузки (round-robin, взвешенная, least-connections, ip-hash, least-response-time, реальная нагрузка), привязка сессий и правила маршрутизации по заголовкам, пассивная и активная проверка состояния, кэширование ответов (с учётом `Vary`, много-вариантное), backpressure, защита от зацикливания, API горячего администрирования — подробности см. §7a |
| Загрузка | Изолированные зоны, квоты по зонам, имена файлов генерируются сервером — без потоковой передачи в V1 (ограничено `server.max_request_size`) |
| `active_defense` | Deception + режим войны на основе уже вычисленных сигналов WAF (никогда отдельного score): статические ловушки, целевое замедление/расширенное журналирование/ограничение частоты, инциденты + экспорт IoC — см. §11 |

### 7a. Исходящий reverse proxy — подробности

Omega-serv может сам выступать в роли reverse proxy к одному или нескольким HTTP/HTTPS backend — не путать с `server.tls.mode = "behind_proxy"` (Omega-serv находится **за** proxy, обратный механизм). Зоны настраиваются через полный CRUD (TUI: *Детальная настройка → Reverse Proxy*), один или несколько upstream на зону.

- **Балансировка нагрузки** — `round_robin` (по умолчанию), `weighted_round_robin`/`weighted_least_connections`/`ip_hash` (взвешенные), `least_connections`, `least_response_time`, `real_load` (реальная нагрузка). У `real_load` есть нативный режим (опрос `/.omega-serv-load/`, использует ровно те же показания `psutil`, что и экран "Состояние и ресурсы", никогда не выполняется второй вызов) или декларативный режим (опрос стороннего HTTP-эндпоинта, минимальный формат `{"load_percent": ...}` или простое число) — гранулярность задаётся на уровне upstream, одна зона может сочетать оба режима.
- **Привязка сессий и условная маршрутизация** — непрозрачный sticky-cookie (реальный host:port никогда не раскрывается клиенту) и правила по заголовкам (точное совпадение или префикс), оба фильтруются по доступности целевого upstream (при недоступности целевого upstream корректно откатываются к активной стратегии).
- **Состояние (health)** — пассивное (счётчики последовательных отказов/успехов, разные пороги для перехода вниз/вверх, чтобы ограничить "флаппинг") **и** активное (периодический опрос, независимый от реального трафика, опционален для каждого upstream, использует тот же механизм фоновой задачи, что и опрос реальной нагрузки). Состояния `DOWN` (всегда автоматически), `DRAINING`/`MAINTENANCE` (всегда вручную, явно временные, никогда не сохраняются) — вручную переведённый upstream исключается из новых выборов, но никогда не прерывает уже установленное соединение. Автоматический повтор на другом upstream — только для идемпотентных методов (GET/HEAD/OPTIONS) и только при ошибке соединения.
- **Backpressure** — настраиваемый лимит активных соединений на upstream; перегруженный upstream корректно отвечает 503, в отличие от неработающего upstream (502, запрос всё равно повторяется).
- **Кэширование ответов** — только GET/HEAD, никогда ответ с ошибкой, никогда `Set-Cookie`, если зона явно это не разрешила; учитывает `Cache-Control`/`Vary` upstream (есть переключатель для игнорирования, но он опасен — та же философия, что и у проверки TLS). Несколько вариантов одного и того же ресурса (`Vary`) действительно сосуществуют на диске, а не "последний записанный побеждает". Блокировка от "stampede" (кэш реально перестраивает только один из параллельных запросов). Диагностический заголовок `X-Omega-Cache: HIT`/`MISS`/`BYPASS` в каждом ответе. Просмотр статистики/очистка — в отдельном экране TUI (*Кэш reverse proxy*).
- **Защита от зацикливания** — hop-by-hop заголовки удаляются, `X-Forwarded-*` всегда перезаписываются (никогда не объединяются со значениями клиента), счётчик `X-Omega-Proxy-Hops` увеличивается при каждой пересылке (корректный отказ после 5 "прыжков" — обнаруживает косвенную петлю между двумя экземплярами, которую локальная проверка конфигурации в принципе не может увидеть).
- **WebSocket** — upgrade можно разрешить на уровне зоны, один upstream фиксируется на весь срок жизни туннеля после установления, без тайм-аута приложения.
- **Горячее администрирование** — небольшой локальный HTTP API (`/.omega-serv-admin/`, защищён `trusted_proxy`, как и нативный опрос нагрузки) позволяет TUI читать/принудительно устанавливать состояние DRAINING/MAINTENANCE backend и читать актуальное соотношение hit/miss кэша **реально работающего сервера** (отдельный экран *Состояние backend в реальном времени*) — поскольку TUI и сервер остаются двумя разными процессами без общей памяти, этот локальный HTTP-канал — единственный мост между ними.

## 8. Усиление HTTP (неотключаемое)

- Строка запроса/заголовки ограничены **во время** чтения (никогда не постфактум), устаревшее сворачивание заголовков отклоняется, `Transfer-Encoding` всегда отклоняется (никогда не угадывается).
- Дублирующийся `Content-Length` отклоняется; `Expect: 100-continue` корректно отклоняется (417).
- Явный белый список методов (иначе 405 + `Allow`), заголовок `Host` проверяется (отсутствующий/пустой/дублирующийся-даже-идентичный/управляющий символ → 400).
- Заголовки безопасности и базовая CSP (`enforce`/`report-only`) применяются к **каждому** ответу, включая ошибки — не обходятся никакой опцией. `Cross-Origin-Opener-Policy`/`Cross-Origin-Resource-Policy` всегда `same-origin`, без реального риска поломать сайт. `Cross-Origin-Embedder-Policy` всегда явно отправляется (никогда не отсутствует — внешний сканер отличает "не рассмотрено" от "разрешено осознанно"), по умолчанию `unsafe-none` на **всех** профилях, включая `hardened`: в отличие от двух предыдущих заголовков, `require-corp`/`credentialless` могут блокировать кросс-доменные ресурсы (шрифты, изображения, сторонние iframe), специфичные для реально обслуживаемого сайта — настраивается (`security.coep_mode`). Зоны CSP (`security.csp_zones`): **явные** исключения по префиксу пути (напр. `unsafe-inline` только под `/какая-то-папка/`, которой это действительно нужно), каждая полностью заменяет политику по умолчанию для своего префикса — никогда слияние, никогда глобальное ослабление; любое исключение остаётся видимым в `audit security` (CSP-001/CSP-002 также проверяют зоны), даже если оно намеренное. Создание направляется мастером по директивам (экран **Общая безопасность**), каждое поле предзаполнено **текущим** значением глобальной политики — чтобы изменять только то, что нужно, а не начинать с пустого поля, которое непреднамеренно принесёт в жертву остальные директивы; при ослаблении `unsafe-inline`/`unsafe-eval`/обобщённого источника `*` в собранной зоне требуется дополнительное явное подтверждение.
- Адреса IPv4, отображённые в IPv6 (`::ffff:x.x.x.x`), нормализуются перед любым сравнением (список блокировки, доверенный прокси, ограничение частоты) — иначе известный обход.
- Проверено property-based тестами (`hypothesis`, тысячи сгенерированных примеров) против HTTP-парсера и резолвера путей, в дополнение к классическим юнит-/интеграционным тестам.

## 9. TLS

### 9a. Самоподписанный сертификат (минимальный)

Покрывает реалистичный сценарий локального/лабораторного/VPN использования (Tailscale...): единственный listener, прямой `ssl.SSLContext`, RSA 2048/4096 или ECDSA P-256/P-384.

### 9b. Локальный CA

Для нескольких клиентских устройств, которым нужно доверять серверу без индивидуального повторного импорта сертификата: локальный удостоверяющий центр подписывает столько серверных сертификатов, сколько нужно.

```text
secure/certificates/ca/
├── root-ca.key    # 0600 - самый чувствительный элемент проекта
├── root-ca.pem    # 0644 - для импорта в хранилище доверия клиентов
├── serial.txt     # 0600 - отслеживание следующего серийного номера
└── index.txt      # 0600 - отслеживание статуса V(алиден)/R(отозван) для каждого подписанного сертификата
```

Процесс: `certs generate-ca` (пароль ключа CA **обязателен**, интерактивный запрос с двойным подтверждением, если `--password` не указан) → `certs generate-csr` (ключ + CSR сервера) → `certs sign-csr` (подписывает CA, копирует SAN из CSR, при необходимости строит `fullchain.pem`) → указать `tls.certificate.certificate_path` на этот `fullchain.pem`. Скомпрометированный сертификат отзывается через `certs revoke` (отмечает в `index.txt`, сначала проверяет, что сертификат действительно от этого CA — иначе отказывает). Нет распространения CRL в V1, нет внешнего CA/CSR для стороннего удостоверяющего центра, нет mTLS (см. §15).

### 9c. Let's Encrypt / ACME (Certbot) — публичный, самостоятельный хостинг

Для действительно публичного сайта с сертификатом, которому доверяют браузеры, полная схема самостоятельного хостинга: DDNS (Dynu или аналог, полностью на ответственности оператора) → Certbot → Omega-serv. Только мастер в TUI (`Детальная настройка → TLS → Мастер Let's Encrypt`) — запускает `certbot certonly --webroot` как подпроцесс (**никогда** `--standalone`, порт 80 уже занят Omega-serv; **никогда** переизобретённый ACME-клиент) с `--config-dir`/`--work-dir`/`--logs-dir`, указывающими на `secure/certificates/letsencrypt/` внутри проекта — **никогда** `/etc/letsencrypt/` — это делает сам Certbot полностью непривилегированным. Полученный сертификат импортируется автоматически (тот же механизм, что и `certs import`, см. примеры CLI выше), и записывается скрипт хука продления. Тестовый режим (staging) включён по умолчанию — снимите галочку только после проверки, что домен/webroot действительно работают, чтобы избежать реальных лимитов частоты Let's Encrypt.

Требования, полностью вне рамок Omega-serv: домен, указывающий на публичный IP (DDNS), и порты 80/443, перенаправленные на эту машину.

### 9d. Автоматическое продление (Certbot)

`Детальная настройка → TLS → Автоматическое продление` подстраивается под реально обнаруженный менеджер служб **для этого экземпляра** (никогда не общий механизм между несколькими экземплярами multi-instance): systemd → генерирует и устанавливает таймер (`<service>-certbot-renew.timer`, дважды в день плюс случайная задержка, `certbot renew` ограничен `--config-dir` этого экземпляра); иначе → строка crontab (текущий пользователь, без привилегий), если `crontab` доступен; иначе → показываются инструкции для ручной настройки, без принудительной записи. В некоторых дистрибутивах (в том числе Arch/Manjaro) пакет Certbot не устанавливает **никакого** таймера по умолчанию, в отличие от Debian/Ubuntu — отсюда этот экран, а не простая проверка предположительно уже существующего механизма. После настройки продление автоматически переимпортирует каждый обновлённый сертификат и перезапускает службу без дальнейшего вмешательства.

## 10. Аудит безопасности

`audit security` **не блокирует**: он повторно выполняет уже блокирующие проверки `config check` как `CRITICAL`, затем применяет рекомендательные правила (TLS, CSP, опасные методы, таймауты, гигиена загрузок — в чистой логике; права доступа к файлам, срок действия сертификата, установленный systemd-юнит, размер логов — через реальный I/O). `WAF-001` (WAF остаётся в `log-only`) отслеживается во времени через небольшой файл состояния (`var/run/waf-mode-state.json`) — срабатывает только после ≥14 дней, наблюдаемых в `log-only` при повторных запусках, а не при первом `audit`.

## 11. Active Defense (deception + режим войны)

Опциональный модуль (`option enable active_defense`, по умолчанию отключён), который квалифицирует враждебное поведение на основе уже вычисленных сигналов WAF (`WafDecision`/репутация/список блокировки — никогда отдельного независимого расчёта score), и может перенаправить источник на ловушку, замедлить его ответы и вести более детальное журналирование, сформировать пригодный к использованию инцидент, а затем экспортировать индикаторы компрометации (IoC). Никогда не блокирует сам трафик — сетевая блокировка остаётся зоной ответственности `omega-fire`; Active Defense наблюдает, отклоняет, замедляет и фиксирует.

**Угрозы и score** : каждый источник (`IP + SHA-256-хеш User-Agent`) накапливает score (блокирующий `WAF-001` +10, эскалация репутации +25, известный бан +25, POST на уже назначенную ловушку +30 — снижение на -5 каждые 15 минут без новых событий), квалифицируемый как `normal`/`suspicious`/`hostile`/`contained` (`contained` требует дополнительно уже известного бана). `mode: monitor` наблюдает, не действуя; `mode: enforce` реально применяет действия ниже.

**Режим войны** (`options.active_defense.settings.war_mode`) : `DefensePlaybook` (`actions: ["redirect_to_decoy", "enrich_log", "delay", "rate_limit", "create_incident", "export_ioc"]`), запускаемый по настраиваемым порогам для любого источника не `normal`:
- `enrich_log` — отдельный JSONL-журнал (`var/log/active-defense-enriched.jsonl`, никогда не смешивается с логом WAF/продакшена), заголовки редактируются, тело HTTP хешируется (SHA-256) или усекается в зависимости от `logging.capture_request_body`.
- `delay` — ограниченное и джиттерное замедление (`war_mode.slowdown.minimum_ms`/`maximum_ms`/`jitter_ms`), никогда не блокирует цикл asyncio.
- `rate_limit` — выделенное ограничение частоты запросов по источнику (`war_mode.rate_limit.requests`/`window_seconds`), использует тот же механизм, что и WAF, но под отдельным ключом.
- `create_incident` — автоматическое открытие/объединение инцидента при превышении `thresholds.incident_score`.

**Deception (ложные цели)** : источник `hostile`/`contained` может быть направлен на статическую ловушку (`fake_admin`, `fake_cms`, `fake_api`, `fake_secrets` — правдоподобные, но всегда фиксированные ответы, никогда реального чтения файла или подпроцесса), выбираемую в зависимости от наблюдаемого класса атаки (`deception.profiles.<имя>.match_attack_classes`, один или несколько из `scan`/`credential_stuffing`/`sqli`/`xss`/`path_traversal`/`upload_probe`/`api_probe`/`unknown`). Два уровня изоляции, осознанно принятые и задокументированные как таковые:
- **Уровень 1** (fixture in-process, `isolation_level: "fixture"`, по умолчанию) — явно СЛАБАЯ изоляция: тот же процесс, тот же пользователь ОС, что и продакшен, приемлемо только потому, что fixture никогда не делает ничего, кроме возврата статического шаблона. ИМЯ профиля должно точно совпадать с одной из 4 fixtures выше — иначе оно отклоняется при валидации (`validate_active_defense_config`), чтобы избежать ловушки, когда неправильно названная ловушка никогда молча не срабатывает.
- **Уровень 2** (реально изолированный backend, `isolation_level: "proxy"`) — перенаправляется на отдельный процесс через `options.active_defense.settings.deception.decoy_zones.<имя>` (upstream `host`/`port` уже запущенного сервера, никогда не создаётся автоматически; никогда не читается из `options.reverse_proxy` — ловушка никогда не может случайно указать на продакшен-зону, проверяется при `config check`), повторно используя тот же механизм исходящего reverse proxy, что и продакшен (`serve_proxy()` — если upstream недоступен в момент реального запроса: атакующему возвращается 502, никогда не сбой).

**Экран Настройки** (TUI, Активная безопасность → Active Defense → Настройки) : полная настройка всего вышеперечисленного — режим, включение режима войны, область/действия/пороги/замедление/лимит запросов, deception (поведение по умолчанию, CRUD профилей ловушек и зон ловушек с примерами значений, отображаемыми в каждом поле), IoC, хранение и журналирование — проверяется теми же правилами, что и CLI, перед каждым сохранением, без необходимости ручного редактирования `config/omega-serve.json`. После любого изменения систематически требуется полный перезапуск (Active Defense никогда не перезагружается на лету).

**Инциденты и IoC** : полная хронология по каждому инциденту, извлечение индикаторов (IP, хешированный User-Agent), версионированный JSON-экспорт/CSV, ограниченный публикуемыми IoC/отчёт в Markdown — каждый экспорт сопровождается файлом `<export>.sha256` (стандартный формат `sha256sum`). Автоматический экспорт при закрытии инцидента, если включён `ioc.auto_export_on_close` (по умолчанию включён). `active-defense purge` закрывает вновь затихшие инциденты и удаляет истёкшие состояния угроз.

**Симуляция** : `active-defense simulate` (CLI) и кнопка «Симулировать» (TUI, экран Активная безопасность) прогнозируют score/уровень и объясняют каждое действие, которое было бы запущено — строгий dry-run, без реальной записи, без сетевого воздействия.

Резервное копирование/восстановление: `config backup --include-active-defense` включает базу sqlite (угрозы/инциденты/назначения) в архив — никогда не содержит секретов в открытом виде, поэтому `--confirm-secrets` не требуется, в отличие от `--include-auth`.

## 12. Службы и эксплуатация

Автоматическое определение systemd/OpenRC/runit (`service install/status/start/stop/restart/enable/disable/uninstall`). Сгенерированный systemd-юнит применяет неотъемлемое усиление по умолчанию: `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome`, `ReadWritePaths` ограничен `var/`, обязательные выделенные пользователь/группа, `UMask=0077`, `Restart=on-failure`. Аккуратная остановка по SIGTERM (дренаж активных соединений, настраиваемый период ожидания, затем принудительное закрытие); горячая перезагрузка по SIGHUP (только правила WAF и зоны Auth — bind/порт/TLS и Active Defense никогда не изменяются без полного перезапуска).

## 13. Логи

`var/log/access.log` (формат Apache combined + `request_id`, экранирование от инъекций в логи), `var/log/error.log`. Ротация по размеру/количеству хранимых файлов (`logs.rotation`). Нативный WAF: `var/log/waf-alerts.log` (`options.waf.logging.path`). Скрипт magnet (§7): `options.waf.magnet.paths.alerts_log`/`.blocklist_log`, по умолчанию `var/log/waf-magnet-alerts.log`/`var/log/waf-magnet-blocklist.log` — добавляются в Библиотеку по умолчанию (кнопка *Добавить известные логи Omega-Serv*) только если magnet активен; `lnav` всегда предлагает их независимо от этого (отсутствующий файл просто игнорируется при запуске).

### 13a. Удалённые источники (SSH)

Централизует, по явному запросу, лог backend-сервера, расположенного в той же локальной сети за обратным прокси (экран **Управление логами → Библиотека → Удалённые источники (SSH)**). «Получение» — это разовое ручное действие, никогда не живой поток и не автоматический опрос: **копия** получается через `scp` в момент нажатия *Получить сейчас*, записывается в `var/log/remote/`, затем добавляется в Библиотеку как обычный лог (колонка *Доступ* = `ssh`, колонка *Изменён* = дата **этого** получения — никогда не дата удалённого файла); новое получение просто заменяет предыдущую копию более свежей.

Намеренные ограничения (полное исследование см. в `OMEGA-SERV_ETUDE-FAISABILITE_LOGS_DISTANTS.md`): никакого автоматического сканирования сети, никакого подключения без явной настройки (метка/хост/удалённый путь, необязательные пользователь/порт/приватный ключ — если оставить пустыми, решение принимают `ssh`/`~/.ssh/config`, как если бы команда вводилась вручную), ни один пароль никогда не запрашивается и не сохраняется (приватный ключ упоминается только по пути к нему, никогда не читается и не хранится Omega-serv), никакой проверки размера перед передачей. Возможность `scp` определяется локально в **Реестре возможностей** (только наличие бинарника, никогда проверка доступности хоста); Samba намеренно оставлена в стороне (YAGNI, пока не подтверждена реальная потребность).

## 15. Вне рамок

- Чистый CGI (только FastCGI/PHP-FPM)
- mTLS (аутентификация клиента по сертификату), OCSP stapling
- Внешний CA / CSR для стороннего удостоверяющего центра, полное распространение CRL
- Пакетный режим/периодический мониторинг — каждая команда является явным действием
- Выделение модуля WAF в самостоятельный проект `omega-waf` (запланировано, никогда не начато — уже спроектировано с чистым разделением в расчёте на это выделение, без параллельной разработки)
- Интеграция в `omega-suite` (работает на локальной машине, а не с удалённой целью — то же исключение, что и у `omega-fire`)
- Active Defense: экспорт STIX 2.1/MISP, выделенные нагрузочные тесты, реальная интеграция с событиями бана `omega-fire` (заблокирована со стороны `omega-fire`, который сегодня не предоставляет никакой поверхности для чтения)
