**OMEGA-SERV** — сервер HTTP/1.1, написанный на чистом Python (ядро сервера использует только стандартную библиотеку), предназначенный для раздачи статического контента и, по желанию, PHP-FPM, с неотключаемым усилением протокола и модулями безопасности (WAF, TLS, аутентификация), которые подключаются по выбору, а не навязываются. Седьмой инструмент набора `omega-`, но намеренно **вне будущей интеграции `omega-suite`** (он действует на локальной машине, где размещён, а не на удалённых целях — то же семейство, что и `omega-fire`); построен по принципам Clean Architecture, где `bootstrap/` служит корнем композиции.

## 1. Видение и границы

Заявленный приоритет — **прежде всего надёжность и безопасность ядра HTTP**: WAF и TLS — необязательные модули поверх него, а не предварительные условия. Сервер, который делает только одно (раздаёт файлы, возможно PHP), но делает это правильно, с настоящим усилением протокола, которое невозможно обойти, — вместо сервера, который делает многое наполовину.

### Что делает OMEGA-SERV

- Раздаёт статический контент (файлы, необязательный список каталога, псевдонимы, перенаправления, перезаписи, кэш) с безопасным разрешением путей (traversal, двойное кодирование, символические ссылки). Большие файлы отправляются блоками прямо с диска и никогда не загружаются в память; у каждого файла есть `ETag` и `Last-Modified` (перезагрузка = пустой ответ 304), он принимает частичные запросы `Range` (продолжение загрузки, видео); изображения, медиа, шрифты, CSS и JS получают `Cache-Control` по умолчанию, который меняется на экране Кэш. Предварительно сжатые текстовые файлы: если рядом с `site.css` лежит `site.css.br` или `site.css.gz` (созданные командой `brotli -k site.css` или `gzip -k site.css`) и браузер их принимает, отправляются они — никогда не версия старше оригинала.
- По умолчанию усиливает протокол HTTP без возможности отключения: явно разрешённые методы, проверка заголовка `Host`, отклонение неоднозначности `Content-Length`/`Transfer-Encoding`, неотключаемые заголовки безопасности и базовая CSP.
- По желанию: фильтрация WAF (сигнатуры, ограничение частоты, список блокировки), прямой TLS (самоподписанный сертификат, подписанный локальным CA или публичный через Let's Encrypt/Certbot с автоматическим продлением — см. §9), аутентификация HTTP Basic по зонам, PHP через FastCGI/PHP-FPM, изолированные зоны загрузки.
- Режим « boost »: несколько серверных процессов, не больше одного на каждый доступный процессор машины (экран Устойчивость и лимиты); счётчики безопасности (лимит запросов, повторения) общие для всех процессов и остаются точными.
- Проверяет собственную конфигурацию (`audit security`) и устанавливается как системная служба (systemd/OpenRC/runit).
- Полностью скриптуемый неинтерактивный CLI **и интерактивный интерфейс (Textual)**, охватывающий ровно те же сценарии использования — см. §3. План развития интерфейса (`OMEGA-SERV_PLAN-DETAILLE_INTERFACE.md`, §12) **выполнен полностью**: реестр возможностей, профили/параметры, подробная настройка (псевдонимы/перенаправления/перезаписи/FastCGI/список каталога/аутентификация/кэш/WAF/доверенные прокси/исходящий обратный прокси/TLS), управление журналами (Библиотека/Избранное, 3 просмотрщика — простой/классический/объединённый lnav —, IP-адреса, удалённые источники SSH, ротация/резервное копирование/автоматизация/восстановление/очистка/экспорт), системная служба, несколько экземпляров (реестр, создание), проверка/имитация/аудит, резервное копирование/восстановление конфигурации, мастер первого запуска, настройки приложения (тема, режим отображения, пути экспорта/скриншотов), контекстное руководство (карточка на каждый экран с конкретными примерами, FAQ, экспорт в HTML, полное покрытие, проверенное тестом), систематическое указание перезагрузки/перезапуска после каждого сохранения, полная настройка Active Defense без ручного редактирования файлов.

### Чего OMEGA-SERV не делает

- Голый CGI (исключён из границ V1 — поддерживается только FastCGI/PHP-FPM).
- Взаимная аутентификация TLS (mTLS), OCSP stapling — вне границ V1, см. §15. (ACME/Let's Encrypt через Certbot доступен, см. §9c/9d.)
- HTTP-кэш, общий для нескольких процессов.
- Сканирование/аудит удалённой цели (для этого см. `omega-check`/`omega-scan`/`omega-deep` — Omega-serv проверяет только себя, никогда третьих лиц).

### Предупреждение об использовании

Omega-serv **отказывается запускаться от имени root**. Ни один модуль безопасности (WAF, TLS, аутентификация) не включён по умолчанию ни в одном поставляемом профиле, включая `hardened` — их включение всегда является явным действием (`config enable-tls`, `option enable waf`...). Сам профиль `hardened` рекомендует обратный прокси для реальной публикации в Интернете, а не заменяет его.

## 2. Установка

### Требования

- Python 3.10+
- `openssl` (программа, а не библиотека Python) для всего, что связано с сертификатами TLS — остальные функции работают и без него.

### Загрузка

Архив последней версии и контрольные суммы SHA-256 каждой версии: [omega-serv-2.0.1.tar.gz](https://kraynux.snake-mackarel.ts.net/omega-serv/download/omega-serv-2.0.1.tar.gz) · [sha.txt](https://kraynux.snake-mackarel.ts.net/omega-serv/download/sha.txt)

```bash
wget https://kraynux.snake-mackarel.ts.net/omega-serv/download/omega-serv-2.0.1.tar.gz
wget https://kraynux.snake-mackarel.ts.net/omega-serv/download/sha.txt
sha256sum -c --ignore-missing sha.txt
```

### Установка

> ⚠️ **Вы обновляете существующую установку?** Приведённая ниже команда **молча пропускает распаковку**, если `omega-serv/` уже существует (она считает, что это прерванная первая установка, а не обновление) — тогда вы переустановите зависимости поверх **старого, неизменённого кода**, без единого сообщения об ошибке. Вместо этого используйте раздел [Обновление](#обновление) ниже.

```bash
[ -d omega-serv ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-serv-2.0.1.tar.gz
cd omega-serv/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. Создаёт виртуальное окружение `.venv`, если оно ещё не существует.
2. Устанавливает пакет (`pip install -e .`) — **никаких внешних зависимостей** (см. §6).
3. Делает `omega-serv.sh` и `install.sh` исполняемыми.
4. Добавляет псевдоним `serv` в `~/.bashrc` и `~/.zshrc` (без дублирования, если он уже есть).

### Обновление

Если `omega-serv/` уже существует (предыдущая установка), **никогда не запускайте `tar` изнутри этого каталога**: он попытается создать вложенный `omega-serv/omega-serv/` и завершится ошибкой. В отличие от omega-fire, `install.sh` никогда не трогает права каталога (ни один шаг не требует там `sudo`) — поэтому здесь нет риска получить каталог, принадлежащий `root`; распаковка прямо поверх существующей установки безопасна.

```bash
# Из РОДИТЕЛЬСКОГО каталога omega-serv/ (никогда изнутри)
tar -xzf omega-serv-2.0.1.tar.gz
cd omega-serv/
./install.sh
```

Архив намеренно исключает всё рабочее состояние (`var/db/`, `var/log/`, `var/backups/`, `secure/secrets/`, `secure/certificates/*.key`, `config/omega-serve.json`, **`webroot/` — реально обслуживаемый сайт**...) — распаковка поверх никогда не затрагивает имеющиеся данные, сертификаты, настройки или обслуживаемый контент; заменяется только код приложения. `install.sh` повторно использует существующее `.venv` и просто переустанавливает поверх зависимости.

С 2026-10-18 `var/` и `secure/auth/` вообще больше не входят в архив, даже пустыми: распаковка поверх больше не сбрасывает их права (общие с учётной записью службы systemd) — после обновления больше не нужно « Служба → Повторно применить права ». `install.sh` создаёт эти каталоги, если их нет, никогда не трогая существующие.

> ⚠️ **Если служба уже работает, описанного выше шага недостаточно.** Он заменяет код на диске, но уже запущенный процесс продолжает работать со старым кодом, загруженным в память — после этого всегда нужен **полный перезапуск**:
> ```bash
> sudo systemctl restart <имя-службы>
> ```
> **Никогда не простая перезагрузка** (`systemctl reload` или экран СЛУЖБА → *Перезагрузить*): она перечитывает только некоторые параметры конфигурации (правила WAF, зоны аутентификации...), **но никогда сам код Python**. Если `systemctl status <имя-службы>` показывает дату запуска раньше вашего обновления, значит, служба всё ещё работает на старом коде. Если вы всегда обновляете, перезаписывая тот же каталог (стандартный случай выше), этот перезапуск — единственный недостающий шаг; переустанавливать службу не нужно.

> ⚠️ **Если после этого служба зацикливается на перезапуске** (`systemctl status` переключается между active/inactive, `journalctl -u <имя-службы>` показывает `PermissionError` при записи файла в `var/`): распаковка через `tar` восстанавливает права каталогов в том виде, в каком они сохранены в архиве, что может стереть общий доступ, настроенный для выделенной системной учётной записи при первой установке, — даже если сам `install.sh` его никогда не трогает. Переустанавливать unit не нужно: экран СЛУЖБА → **Восстановить права** (повторно применяет общий доступ к `var/` и `secure/auth/`, не трогая unit systemd).

### Зависимости

Ядро сервера (парсер HTTP/1.1, клиент FastCGI, хеширование паролей через `hashlib.scrypt`) остаётся чистым Python/stdlib, а всё, что связано с сертификатами TLS, проходит через программу `openssl` как подпроцесс, а не через криптографическую библиотеку Python — **для этого никаких внешних зависимостей**. Их добавляет только интерактивный интерфейс (§3): `omega-lib` (темы, определение терминала — общая библиотека набора, не опубликованная на PyPI, поставляется в дистрибутивном архиве), `textual` и `pyte` (эмуляция терминала для объединённого отображения `lnav` в интерфейсе), `jinja2` (HTML-экспорт с темой) и `psutil` (экран Состояние и ресурсы — ЦП/ОЗУ/диск/сеть). Необязательная зависимость для разработки/тестирования (`pip install -e ".[test]"`): `hypothesis` (тесты свойств парсера HTTP и разрешателя путей, никогда в продакшене). Инструменты качества (`pip install -e ".[dev]"`): `pytest`, `ruff`, `mypy`, `import-linter`. Дополнительный необязательный пакет (`pip install -e ".[magnet]"`): `lupa` (встроенная привязка Lua, предкомпилированный wheel, системный интерпретатор `lua` не нужен), только для дополнительного скрипта WAF « magnet » (§7) — никогда не устанавливается по умолчанию; его отсутствие сообщается (возможность `waf-magnet`, экран **Возможности**) с точной командой установки, не блокируя остальной сервер.

### Рекомендуемые необязательные инструменты

Интерфейс работает в ограниченном режиме, если этих инструментов нет:

- `openssl` — нужен для всего, что связано с сертификатами TLS (самоподписанный, локальный CA, импорт); без него команды `certs *` завершаются ошибкой, но остальной сервер работает нормально (см. §9).
- `certbot` — нужен только для мастера **Let's Encrypt** и его автоматического продления (§9c/9d); самоподписанному TLS/локальному CA он не нужен.
- `lnav` — расширенный объединённый анализ журналов на экране **Управление журналами** (§3); если программа не найдена, выводится понятное сообщение об ошибке, без сбоя; остальная часть экрана (просмотр/отслеживание/ротация/статистика) работает без него нормально.
- `scp` (пакет `openssh`/`openssh-clients`, почти всегда уже установлен) — нужен только для **Удалённых источников (SSH)** (§13a); без него получение завершается понятным сообщением, остальная Библиотека работает нормально.
- `python-psutil` (системный пакет, соответствующий `psutil` из PyPI) — в любом случае автоматически устанавливается через `pip install -e .` (обязательная зависимость пакета, экрану **Состояние и ресурсы** он нужен всегда), но предварительная установка через системный менеджер пакетов избавляет `pip` от локальной сборки wheel.

```bash
# Arch Linux и производные
sudo pacman -S openssl certbot lnav python-psutil openssh

# Debian/Ubuntu и производные
sudo apt install openssl certbot lnav python3-psutil openssh-client

# Fedora
sudo dnf install openssl certbot lnav python3-psutil openssh-clients
```

## 3. Использование

Два функционально строго эквивалентных интерфейса, никогда без дублирования логики между ними: неинтерактивный CLI (скриптуемый, используется ниже) и интерактивный интерфейс Textual (меню, формы, таблицы) — каждое действие одного существует на стороне CLI, интерфейс лишь оформляет те же сценарии использования.

### Интерактивный режим (TUI)

Рекомендуется для повседневной работы — запускается без аргументов:

```bash
./omega-serv.sh
```
если вы создали псевдоним, просто введите `serv` в терминале:
```bash
serv
```

### Языки интерфейса

17 языков: французский, английский, испанский, португальский (Бразилия), итальянский, немецкий, нидерландский, польский, русский, китайский, вьетнамский, тайский, индонезийский, японский, корейский, хинди, арабский. Выбор в Настройках (клавиша `o`, « Langue / Language », подпись никогда не переводится) или разово через `OMEGA_SERV_LANG=en serv`. В текстовой консоли Linux (TTY) языки, письменность которых отсутствует в консольных шрифтах (вьетнамский, китайский, тайский, японский, корейский, хинди, арабский), на время сеанса отображаются на английском. На хинди терминалы, которые сами составляют связанные буквы (Kitty, Ghostty, Konsole), сдвигают рамки и столбцы — по-разному в зависимости от шрифта: при запуске выводится предупреждение; Terminator, GNOME Terminal, Xfce Terminal и Alacritty показывают хинди выровненным. Две отдельные настройки: **язык страниц для посетителей** (страницы ошибок, список каталога — экран Страницы ошибок, по умолчанию французский) и **язык экспорта** (HTML и отчёт об инциденте — Настройки, по умолчанию « Как интерфейс »). Журналы сервера (`journalctl`) остаются на французском.

### Общий порядок работы

Заставка (splash, закрывается клавишей или щелчком) → главное меню (Мастер первого запуска / Реестр возможностей / Профили / Подробная настройка / Активная безопасность / Управление журналами / Служба / Несколько экземпляров / Состояние и ресурсы / Аудит / Резервное копирование) → выбор раздела, затем действия, причём каждая форма проверяет обязательные поля перед продолжением → явное подтверждение перед любой чувствительной или разрушительной операцией (перезапуск, удаление, восстановление...) → систематическое указание дальнейшего шага (автоматическая перезагрузка на лету или подтверждение полного перезапуска) после любого сохранения, изменяющего уже обслуживаемую конфигурацию. Подстройка под терминал (цвета, размер, структурное понижение режима отображения) выполняется автоматически, без ручного флага — см. §4.

#### Сочетания клавиш (интерактивный интерфейс)

| Клавиша | Действие |
|---|---|
| `↑` / `↓` | Перемещение между элементами экрана |
| `Tab` / `Shift+Tab` | Перемещение между полями формы |
| `Esc` | Возврат на предыдущий экран (подтверждение выхода на главном экране) |
| `t` | Следующая тема (применяется сразу, без подтверждения) |
| `r` | Обновить определение терминала |
| `F1` | Справка по активному экрану (контекстная карточка — см. "Руководство" ниже) |
| `a` | Полное руководство (навигируемое меню + FAQ) |
| `o` | Настройки приложения (тема, режим отображения, пути экспорта/скриншотов — см. ниже) |
| `q` | Выход (с подтверждением) |
| `Ctrl+P` | Палитра команд (Тема, Скриншот, Параметры...) |

> **Исключение — редактор списков (WAF → Custom)**: никаких сочетаний клавиш, всё делается мышью; клавиатура служит только для ввода (символы, Enter, стрелки, Home/End, Page Up/Down, Backspace, Delete). `Esc`, `F1` и `Ctrl+P` там неактивны (кнопка **Справка**); активным остаётся только `Ctrl+Q`, с подтверждением при несохранённых изменениях.

#### Руководство (клавиши `F1`/`a`)

Встроенная система справки, а не просто статический текст: каждый задокументированный экран (карточка с определением/полями для заполнения с конкретными примерами/вызываемым действием/реакцией — перезагрузка, перезапуск или ничего) доступен прямо из него через `F1`; клавиша `a` открывает полное меню (дерево, идентичное реальной навигации приложения) с доступом к FAQ (ловушки, встреченные при реальном использовании, например классы атак Active Defense, права при общей службе) и автономным HTML-экспортом (с сохранением активной темы) всего руководства. Пока для экрана нет отдельной карточки, используется общий справочный экран — сейчас покрытие полное и проверено тестом.

#### Главное меню (интерактивный интерфейс)

- **Мастер первого запуска** — пошаговый процесс из 8 шагов (приветствие → возможности только для чтения → выбор профиля → bind/порт → необязательный TLS → проверка → сводка + запись → предложение установить службу); позволяет создать полную конфигурацию и запустить сервер, не зная CLI.
- **Реестр возможностей** — системная проверка только для чтения (система инициализации, занят ли настроенный порт, наличие `openssl`/`logrotate`/`tailscale`/`lnav`, место на диске, лимит дескрипторов...), экспорт в JSON/HTML.
- **Профили** — тот же сценарий использования, что и `profile` в CLI (§5), diff всегда показывается перед записью.
- **Подробная настройка сервера** — полный CRUD для псевдонимов/перенаправлений/перезаписей/списка каталога/доверенных прокси/исходящего обратного прокси/FastCGI/кэша/аутентификации/контроля доступа/страниц ошибок, плюс подменю **TLS** (состояние, генерация самоподписанного, мастер локального CA, мастер Let's Encrypt/Certbot, автоматическое продление, отзыв, включение/отключение — см. §9); вторая рамка **ПАРАМЕТРЫ И ПРОВЕРКА** собирает там ярлыки к **Параметрам** (`option` CLI, §7) и **Проверить конфигурацию** (`config check` CLI, §10) — тот же порядок действий, что и настроить, а затем проверить; эти два экрана больше не открываются напрямую из главного меню. WAF здесь больше не живёт (см. "Активная безопасность" ниже): он показывает в основном постоянно меняющееся рабочее состояние, а не простую статическую форму настройки. Каждое сохранение систематически указывает дальнейший шаг: автоматическая и бесшумная перезагрузка на лету, если служба активна (список каталога, доступ, псевдонимы/перенаправления/перезаписи, кэш, страницы ошибок, доверенные прокси, зоны обратного прокси/FastCGI, пользователи/зоны аутентификации), или явное подтверждение полного перезапуска, когда изменение касается слушающего сокета, TLS или Active Defense — ни один экран больше не заставляет гадать, нужно ли перезапускать сервер.
- **Активная безопасность** — единый экран с двумя блоками рядом: **Active Defense** (Состояние, Отслеживаемые угрозы с оценкой/уровнем, Инциденты с хронологией/экспортом IoC/отчётом, назначения Deception, Имитация решения в режиме dry-run, **Настройки** — полная настройка без ручного редактирования `config/omega-serve.json`, см. §11) и **WAF** (Состояние, Модули — режим/пакеты правил/список блокировки, Проверка запроса, Custom — создание собственных правил и загрузка списков путей/ключевых слов, редактируемых мышью (см. §11b), Magnet — импорт внешнего скрипта `mod_magnet` с проверкой совместимости перед включением) — см. §11.
- **Управление журналами** — меню в две колонки. Колонка **Библиотека**: центральный узел, ссылающийся на любой обрабатываемый журнал (ручное наполнение, один щелчок автоматически добавляет журналы самого экземпляра — access/error/встроенный WAF, + скрипт magnet §7, если он активен —, или **удалённый источник**, полученный по SSH, см. ниже); **Избранное** (сохранённая под именем комбинация журналов + просмотрщика, прямой запуск); **Просмотр журналов** с 3 просмотрщиками на выбор в зависимости от числа выбранных журналов — Простой (tail в реальном времени + общая статистика IP/ошибок/кодов HTTP для любого формата), Классический (чтение + отслеживание), объединённый `lnav` (настоящее отображение терминала в интерфейсе, журналы magnet включены автоматически + ручные пути, **закреплённые** для сохранения между сеансами); **IP-адреса** (самые активные IP из одного или нескольких выбранных журналов, период 24ч/7д/30д/всё, удаление IP). Колонка **Обслуживание** (без изменений): ручная или автоматическая ротация/архивирование по порогу размера, немедленное создание резервной копии, настройка/управление запланированными автоматизациями (декларативно — см. примечание ниже), восстановление/очистка архива, экспорт списка.
- **Служба** — те же действия, что и `service` в CLI (§12), разовое повышение прав `sudo` для каждого действия, никогда всё приложение не запускается от root.
- **Несколько экземпляров** — глобальный реестр (`~/.config/omega-serv/instances.json`, вне любого каталога проекта) известных установок на машине, с состоянием systemd каждой из них; создание нового экземпляра (копия дерева каталогов, собственное виртуальное окружение и зависимости, свежая конфигурация с отдельным портом, проверка вложенности и конфликта портов) прямо из интерфейса. Кнопка практически незаметна при единственной установке (надпись "Несколько экземпляров" превращается в "Экземпляры (N)", как только их становится 2); полное переключение на другой экземпляр (`os.execv`, явное подтверждение, отдельная заставка, сообщающая о переключении при перезапуске); полное удаление экземпляра (удаление unit, выделенной системной учётной записи, если она больше не используется другими экземплярами, и необязательное удаление каталога, никогда по умолчанию).
- **Состояние и ресурсы** — обзор с первого взгляда, обновляемый каждые 2 секунды: состояние сервера (процесс/PID, состояние системной службы, профиль/активные параметры/TLS/порт), поток журнала доступа в реальном времени (пропускная способность, распределение по кодам состояния, уникальные IP, доля ошибок), системные ресурсы (ЦП/ОЗУ/диск/swap/нагрузка/сеть, через `psutil`); здесь же ярлык **Имитировать запрос** (тот же сценарий использования, что и соответствующая команда CLI, §10).
- **Аудит безопасности** — тот же сценарий использования, что и соответствующая команда CLI (§10).
- **Резервное копирование конфигурации** — архив tar.gz файла конфигурации и, по явному выбору, правил WAF/зон аутентификации/сертификатов (подтверждение обязательно, как только включаются настоящие секреты)/базы Active Defense, восстановление, список, удаление.

> Примечание о запланированных автоматизациях ротации: они сохраняются (частота + целевой журнал), но **ничто не выполняет их автоматически** — ни со стороны интерфейса, ни в фоне. Это осознанный выбор ради единообразия с аналогичным экраном `omega-fire`, который ведёт себя так же декларативно. Реальное периодическое выполнение (таймер systemd, фоновая задача) нужно строить отдельно, если потребность подтвердится.

#### Настройки приложения (клавиша `o` или палитра команд)

Только настройки интерфейса — никогда не путать с `config/omega-serve.json` (конфигурация сервера): активная тема, режим отображения (`complete`/`standard`/`reduced`/`mono`, требуется перезапуск), путь экспорта (по умолчанию `var/exports/`), путь скриншотов (по умолчанию `var/screenshots/`), очистка одного или другого каталога (подтверждение обязательно).

```bash
# Запуск сервера (передний план, SIGTERM = корректная остановка с периодом ожидания, SIGHUP = перезагрузка на лету WAF/Auth)
./omega-serv.sh serve

# Конфигурация
./omega-serv.sh config init                # создаёт config/omega-serve.json (безопасные значения по умолчанию)
./omega-serv.sh config check                # проверяет без запуска (те же блокирующие проверки, что и при запуске)
./omega-serv.sh config show
./omega-serv.sh config enable-tls --cert ... --key ... --mode direct
./omega-serv.sh config disable-tls

# Профили (minimal / standard / hardened / development)
./omega-serv.sh profile list
./omega-serv.sh profile show hardened
./omega-serv.sh profile apply hardened --dry-run   # diff перед применением, всегда

# Параметры (aliases, redirects, rewrites, dirlisting, cache, waf, upload, fastcgi, reverse_proxy...)
./omega-serv.sh option list
./omega-serv.sh option enable waf
./omega-serv.sh option disable waf

# Имитировать запрос без запуска сервера (полезно для проверки правила перед включением)
./omega-serv.sh simulate-request GET /index.html

# WAF (работает даже при отключённом параметре, через неявный --force)
./omega-serv.sh waf test --method GET --path /admin --remote-ip 203.0.113.1
./omega-serv.sh blocklist list
./omega-serv.sh blocklist add --network 203.0.113.0/24 --reason "обнаружено сканирование" --duration-seconds 3600
./omega-serv.sh blocklist remove --network 203.0.113.0/24

# Active Defense (deception + режим войны, параметр "active_defense" - см. §11)
./omega-serv.sh active-defense status
./omega-serv.sh active-defense simulate --ip 203.0.113.42 --path /wp-login.php --attack-class scan --score 40
./omega-serv.sh active-defense purge
./omega-serv.sh threats list --level hostile
./omega-serv.sh threats show 203.0.113.42:ab12cd34
./omega-serv.sh incidents list --status open
./omega-serv.sh incidents show <incident-id>
./omega-serv.sh incidents close <incident-id>
./omega-serv.sh incidents export-ioc <incident-id> --format json,csv
./omega-serv.sh incidents generate-report <incident-id>
./omega-serv.sh deception list
./omega-serv.sh deception release --subject 203.0.113.42:ab12cd34

# Сертификаты TLS - самоподписанный (9a)
./omega-serv.sh certs generate-self-signed --cn localhost --san-dns localhost --san-ip 127.0.0.1
./omega-serv.sh certs show
./omega-serv.sh certs check-expiry --warn-days 30

# Сертификаты TLS - локальный CA (9b)
./omega-serv.sh certs generate-ca --cn "Мой локальный CA" --days 3650
./omega-serv.sh certs generate-csr --cn server.local --san-dns server.local --key-out server.key --csr-out server.csr
./omega-serv.sh certs sign-csr --csr server.csr --ca-key secure/certificates/ca/root-ca.key --ca-cert secure/certificates/ca/root-ca.pem --out server.pem --fullchain-out fullchain.pem
./omega-serv.sh certs revoke --cert server.pem --ca-key secure/certificates/ca/root-ca.key --ca-cert secure/certificates/ca/root-ca.pem

# Сертификаты TLS - импорт (9c, например из хука Certbot)
./omega-serv.sh certs import --key privkey.pem --cert fullchain.pem

# Аутентификация HTTP Basic
./omega-serv.sh auth add-user --username alice
./omega-serv.sh auth create-zone --url-prefix /admin/ --allowed-users alice
./omega-serv.sh auth list

# Аудит безопасности (никогда не блокирует, информационный)
./omega-serv.sh audit security --format text --min-severity medium

# Резервное копирование конфигурации (конфигурация включается всегда; настоящие секреты
# по умолчанию никогда не шифруются, --confirm-secrets обязателен для их включения)
./omega-serv.sh config backup --description "перед миграцией"
./omega-serv.sh config backup --include-auth --include-certificates --confirm-secrets
./omega-serv.sh config backup --include-active-defense --description "угрозы/инциденты"
./omega-serv.sh config list-backups
./omega-serv.sh config restore --snapshot-id snapshot_20260908_170003_762484

# Системная служба (systemd/OpenRC/runit, автоматическое определение)
./omega-serv.sh service install --user omega-serv --group omega-serv
./omega-serv.sh service start
./omega-serv.sh service status
```

### Важные коды выхода

| Команда | Код | Значение |
|---|---:|---|
| `audit security` | `0` | Ничего серьёзного (нет `CRITICAL`/`HIGH`) |
| `audit security` | `1` | Хотя бы одна находка `CRITICAL` |
| `audit security` | `2` | Хотя бы одна `HIGH` без `CRITICAL` |
| `audit security` | `3` | Ошибка выполнения (конфигурация не найдена...) |
| `certs check-expiry` | `1` | Срок действия сертификата истёк |
| любая другая команда | `0`/`1` | Успех / ошибка проверки |

## 4. Совместимость с терминалами

Интерактивный интерфейс ([Textual](https://textual.textualize.io/), построенный на [Rich](https://rich.readthedocs.io/)) автоматически определяет возможности терминала (эмулятор, размер) и соответственно настраивает свою структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`), без ручного флага. Режим CLI всегда остаётся простым текстом, независимо от терминала. Политика общая для всего набора `omega-` (`omega-lib`, `terminal/policies.py`) — идентична политике `omega-check`/`omega-fire`.

### Профиль по обнаруженному эмулятору

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| TTY Linux, старый SSH | `mono` |
| Нераспознанный эмулятор | `reduced` (запасной вариант по умолчанию) |

### Профиль по размеру терминала

| Минимальный размер (столбцы × строки) | Предел профиля |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| меньше | `mono` |

Итоговый профиль — **более строгий из двух** (эмулятор и размер): Ghostty во весь экран, уменьшенный до 70 столбцов, опускается до `mono`, даже если его эмулятор допускает `complete`. Его можно обновить на лету клавишей `r` или вручную переопределить в Настройках приложения (клавиша `o`, §3).

## 5. Профили

| Профиль | Назначение |
|---|---|
| `minimal` | Демонстрация/простое локальное использование: только статика, ни один параметр не включён |
| `standard` | Статический сайт или небольшой продакшен: обычные заголовки, базовая CSP, список каталога/CGI/FastCGI отключены |
| `hardened` | Публикация с минимальными привилегиями: по умолчанию локальный bind (для Интернета рекомендуется обратный прокси), методы ограничены GET/HEAD, строгая CSP, защита от slowloris — WAF **никогда** не включается автоматически, даже здесь |
| `development` | Только локальная разработка, никогда не подаётся как подходящий для Интернета: обязательный bind на loopback, CSP в режиме report-only, подробные страницы ошибок |

Порядок слияния конфигурации: встроенные безопасные значения → выбранный профиль → сохраняются текущие активные параметры (переживают смену профиля) → явный пользовательский слой. Перед записью всегда показывается полный diff (`profile apply`).

## 6. Архитектура

Clean Architecture (`core / domain / ports / application / infrastructure / interfaces / bootstrap`) — `bootstrap/` служит корнем композиции (аналог `app/` в других инструментах набора). Осознанная особенность этого проекта, проверяемая `import-linter`, а не предполагаемая: `application/server/start_server.py` (а также `validate_config.py`, `run_audit.py`) играют роль **фабрики, зависящей от реальной конфигурации** (какой менеджер служб, включать ли WAF...) и напрямую создают конкретные адаптеры `infrastructure/` — в отличие от более строгого шаблона CHECK/TRACK, где `application/` использует только `ports/`. Единственное действительно соблюдаемое универсальное правило: `domain/`/`core/` никогда не зависят от внешних слоёв.

```text
src/omega_serv/
├── core/            Сквозной словарь (platform_info, константы)
├── domain/           Чистая бизнес-логика (HTTP, конфигурация, безопасность WAF/TLS/auth/аудит, маршрутизация)
├── ports/            Контракты (Protocol), которых ожидает приложение
├── application/      Сценарии использования - некоторые функции (build_server...) также собирают конкретные адаптеры (см. выше)
├── infrastructure/    Реальные реализации (asyncio, openssl как подпроцесс, systemd/OpenRC/runit, файлы)
├── interfaces/cli/    Неинтерактивный CLI на argparse
├── interfaces/tui/    Интерактивный интерфейс Textual (те же сценарии, никогда без дублирования логики)
└── bootstrap/         DependencyContainer, определение корня проекта
```

Правила, проверяемые `import-linter` (8 контрактов): `domain`/`core` никогда не зависят от внешних слоёв; `interfaces.tui` никогда не зависит напрямую от `infrastructure`; `textual` ограничен `interfaces.tui`; `subprocess` ограничен `infrastructure/process/subprocess_runner.py` (и `infrastructure/lnav/`, интерактивный поток PTY); `ssl` ограничен `infrastructure/tls/ssl_context_builder.py`; `jinja2` ограничен `infrastructure/exporters/html_exporter.py`; `sqlite3` ограничен `infrastructure/persistence/sqlite_active_defense_connection.py` (единственное реляционное хранилище проекта, зарезервированное для Active Defense — см. §11); `lupa` ограничена `infrastructure/waf/lua_waf_adapter.py` (дополнительный скрипт WAF « magnet », §7).

## 7. Необязательные модули

Во всех поставляемых профилях отключены по умолчанию — включение всегда явное (`option enable <имя>` или `config enable-tls`):

| Модуль | Роль |
|---|---|
| `waf` | Сигнатуры (чувствительные пути, UA/Referer сканеров, SQLi/XSS/CMDi в теле), списки, редактируемые как текстовый файл (ключевые слова или чувствительные пути с исключениями `!`, режим Наблюдения и собственное правило повторения для каждого списка — два поставляемых эталона, явная загрузка, см. §11b), ограничение частоты (token bucket, правила для папки и для IP/сети, см. §11c), список блокировки (CIDR + срок действия), репутация/эскалация, импорт существующего скрипта WAF `mod_magnet` от Lighttpd в качестве необязательного усиления типа « magnet » (без переписывания, дополнение `pip install -e ".[magnet]"` — аддитивно, никогда не может снять встроенную блокировку; проверка совместимости при импорте, отдельный экран TUI) — режим `log-only` структурно не способен блокировать |
| TLS | Прямой (самоподписанный, локальный CA или публичный через Let's Encrypt/Certbot с автоматическим продлением — см. §9), никогда mTLS/OCSP в V1 |
| Аутентификация | HTTP Basic по зонам (`url_prefix`), `hashlib.scrypt` с защитой от атак по времени (постоянное время даже для неизвестного пользователя) |
| FastCGI/PHP-FPM | Одна пара `(url_prefix, script_root)`, `script_root` по построению вынесен за пределы `webroot/` (статический обработчик никогда не может раскрыть исходный код PHP) |
| Исходящий обратный прокси | Omega-serv сам выступает прокси к одному или нескольким бэкендам (обратное направление по отношению к `server.tls.mode = "behind_proxy"`) — балансировка нагрузки (round-robin, взвешенная, least-connections, ip-hash, least-response-time, реальная нагрузка), привязка сессий и правила маршрутизации по заголовку, пассивная и активная проверка состояния, кэш ответов (несколько вариантов `Vary`), backpressure, защита от петель, API администрирования на лету — подробности в §7a |
| Upload | Изолированные зоны, квоты на зону, имена файлов генерируются на стороне сервера — без потоковой передачи в V1 (ограничено `server.max_request_size`) |
| `active_defense` | Deception + режим войны на основе уже вычисленных сигналов WAF (никогда второй оценки): статические приманки, целевые замедление/расширенное журналирование/ограничение частоты, инциденты + экспорт IoC — см. §11 |

### 7a. Исходящий обратный прокси — подробности

OMEGA-SERV может сам выступать обратным прокси к одному или нескольким бэкендам HTTP/HTTPS — никогда не путайте с `server.tls.mode = "behind_proxy"` (OMEGA-SERV **за** прокси, обратный механизм). Зоны настраиваются с полным CRUD (TUI: *Подробная настройка → Reverse Proxy*), один или несколько upstream на зону.

- **Балансировка нагрузки** — `round_robin` (по умолчанию), `weighted_round_robin`/`weighted_least_connections`/`ip_hash` (взвешенные), `least_connections`, `least_response_time`, `real_load` (реальная нагрузка). Режим `real_load` встроенный (зонд `/.omega-serv-load/`, использует тот же замер `psutil`, что и экран « Состояние и ресурсы », никогда второй вызов) или декларативный (сторонний HTTP-зонд, минимальный формат `{"load_percent": ...}` или просто число) — детализация на уровне upstream, одна зона может сочетать оба.
- **Привязка сессий и условная маршрутизация** — непрозрачный sticky-cookie (реальный host:port никогда не раскрывается клиенту) и правила по заголовку (равенство или префикс), оба фильтруются по доступности целевого upstream (корректно возвращаются к активной стратегии, если целевой upstream недоступен).
- **Состояние** — пассивное (последовательные сбои/успехи, раздельные пороги переключения down/up для ограничения flapping) **и** активное (периодический зонд, не зависящий от реального трафика, необязательный для каждого upstream, использует тот же механизм фоновых задач, что и реальная нагрузка). Состояния `DOWN` (всегда автоматическое), `DRAINING`/`MAINTENANCE` (всегда ручные, явно временные, никогда не сохраняются) — вручную переведённый upstream исключается из новых выборов, никогда не прерывая уже установленное соединение. Автоматический повтор на другом upstream — только для идемпотентных методов (GET/HEAD/OPTIONS) и только при ошибке соединения.
- **Backpressure** — настраиваемый для каждого upstream предел активных соединений; перегруженный upstream корректно отказывает с 503, что отличается от неработающего upstream (502, всё равно повторяется).
- **Кэш ответов** — только GET/HEAD, никогда ответ с ошибкой, никогда `Set-Cookie` без явного opt-in для зоны; соблюдает `Cache-Control`/`Vary` upstream (отключаемый, но опасный параметр, та же философия, что и у проверки TLS). Несколько вариантов одного ресурса (`Vary`) действительно сосуществуют на диске, а не по принципу « последний побеждает ». Защита от stampede (только один одновременный запрос действительно восстанавливает кэш). Диагностический заголовок `X-Omega-Cache: HIT`/`MISS`/`BYPASS` в каждом ответе. Наблюдение/очистка на отдельном экране TUI (*Кэш обратного прокси*).
- **Защита от петель** — hop-by-hop-заголовки удаляются, `X-Forwarded-*` всегда перезаписываются (никогда не объединяются с заголовками клиента), счётчик `X-Omega-Proxy-Hops` увеличивается при каждой передаче (корректный отказ после 5 переходов — выявляет косвенную петлю между двумя экземплярами, которую простая локальная проверка конфигурации никогда не увидит).
- **WebSocket** — upgrade разрешается для зоны, после установки туннеля один upstream закрепляется на всё время его существования, без тайм-аута приложения.
- **Администрирование на лету** — небольшой локальный HTTP API (`/.omega-serv-admin/`, защищён `trusted_proxy`, как и встроенный зонд нагрузки), позволяющий TUI читать/принудительно задавать состояние DRAINING/MAINTENANCE бэкенда и читать долю попаданий/промахов кэша **реально работающего сервера** (отдельный экран *Состояние бэкендов в реальном времени*) — поскольку TUI и сервер остаются двумя отдельными процессами без общей памяти, этот локальный HTTP-канал — единственный мост между ними.

## 8. Усиление HTTP (не отключается)

- Заголовок/строка запроса ограничиваются **во время** чтения (никогда задним числом), устаревшее сворачивание заголовков отклоняется, `Transfer-Encoding` всегда отклоняется (никогда не угадывается).
- Дублированный `Content-Length` отклоняется; `Expect: 100-continue` корректно отклоняется (417).
- Явный белый список методов (иначе 405 + `Allow`), заголовок `Host` проверяется (отсутствует/пустой/дублированный-даже-одинаковый/управляющий символ → 400).
- Заголовки безопасности и базовая CSP (`enforce`/`report-only`) применяются к **любому** ответу, включая ошибки, — их нельзя обойти никаким параметром. `Cross-Origin-Opener-Policy`/`Cross-Origin-Resource-Policy` всегда `same-origin`, без реального риска сломать сайт. `Cross-Origin-Embedder-Policy` всегда отправляется явно (никогда не отсутствует — так внешний сканер отличает « не рассматривалось » от « разрешительно намеренно »), по умолчанию `unsafe-none` во **всех** профилях, включая `hardened`: в отличие от двух предыдущих, `require-corp`/`credentialless` могут блокировать cross-origin ресурсы (шрифты, изображения, сторонние iframe), принадлежащие реально обслуживаемому сайту, — настраивается (`security.coep_mode`). Зоны CSP (`security.csp_zones`): **явные** исключения по префиксу пути (например, `unsafe-inline` только под `/какой-то-каталог/`, которому это действительно нужно), каждое полностью заменяет политику по умолчанию для своего префикса — никогда не слияние, никогда не глобальное ослабление; любое исключение остаётся видимым в `audit security` (CSP-001/CSP-002 проверяют и зоны), даже если оно сделано намеренно. Создание ведётся мастером директива за директивой (экран **Общая безопасность**), каждое поле заранее заполнено **текущим** значением глобальной политики — чтобы менять только то, что нужно, а не начинать с пустого поля, которое невольно пожертвовало бы остальными директивами; если собранная зона ослабляет `unsafe-inline`/`unsafe-eval`/общий источник `*`, требуется дополнительное явное подтверждение.
- Адреса IPv4, отображённые в IPv6 (`::ffff:x.x.x.x`), нормализуются перед любым сравнением (список блокировки, доверенный прокси, ограничение частоты) — иначе это известный обход.
- Проверено тестами свойств (`hypothesis`, тысячи сгенерированных примеров) для парсера HTTP и разрешателя путей, в дополнение к классическим модульным/интеграционным тестам.

## 9. TLS

### 9a. Самоподписанный сертификат (минимальный)

Покрывает реалистичное локальное/лабораторное/VPN-использование (Tailscale...): один слушатель, прямой `ssl.SSLContext`, RSA 2048/4096 или ECDSA P-256/P-384.

### 9b. Локальный CA

Для нескольких клиентских устройств, которые должны доверять без повторного импорта каждого сертификата: локальный центр сертификации подписывает столько серверных сертификатов, сколько нужно.

```text
secure/certificates/ca/
├── root-ca.key    # 0600 - самый чувствительный элемент проекта
├── root-ca.pem    # 0644 - импортируется в хранилище доверия клиентов
├── serial.txt     # 0600 - учёт следующего серийного номера
└── index.txt      # 0600 - учёт статуса V(alid)/R(evoked) для каждого подписанного сертификата
```

Порядок: `certs generate-ca` (пароль ключа CA **обязателен**, интерактивный ввод с двойным подтверждением, если `--password` не указан) → `certs generate-csr` (ключ + CSR сервера) → `certs sign-csr` (подписывает CA, копирует SAN из CSR, по запросу строит `fullchain.pem`) → указать в `tls.certificate.certificate_path` этот `fullchain.pem`. Скомпрометированный сертификат отзывается через `certs revoke` (помечает `index.txt`, сначала проверяет, что сертификат действительно выдан этим CA, — иначе отказывает). В V1 нет распространения CRL, внешнего CA/CSR для сторонней инстанции и mTLS (см. §15).

### 9c. Let's Encrypt / ACME (Certbot) — публичный, самостоятельный хостинг

Для действительно публичного сайта с сертификатом, признаваемым браузерами, полная схема самостоятельного хостинга: DDNS (Dynu или аналог, полностью на стороне оператора) → Certbot → Omega-serv. Только мастер TUI (`Подробная настройка → TLS → Мастер Let's Encrypt`) — вызывает `certbot certonly --webroot` как подпроцесс (**никогда** `--standalone`, порт 80 уже занят Omega-serv; **никогда** не переписанный заново клиент ACME) с `--config-dir`/`--work-dir`/`--logs-dir`, указывающими на `secure/certificates/letsencrypt/` проекта — **никогда** `/etc/letsencrypt/`, — благодаря чему сам Certbot работает полностью без привилегий. Полученный сертификат импортируется автоматически (тот же механизм, что и `certs import`, см. примеры CLI выше), и записывается скрипт-хук продления. Тестовый режим (staging) отмечен по умолчанию — снимите отметку, когда домен/webroot проверены как работающие, чтобы избежать реальных лимитов Let's Encrypt.

Требования полностью вне границ Omega-serv: домен, указывающий на публичный IP (DDNS), и порты 80/443, перенаправленные на эту машину.

### 9d. Автоматическое продление (Certbot)

`Подробная настройка → TLS → Автоматическое продление` подстраивается под реально обнаруженный менеджер служб **для этого экземпляра** (никогда не механизм, общий для нескольких экземпляров): systemd → создаёт и устанавливает таймер (`<service>-certbot-renew.timer`, два раза в день + случайная задержка, `certbot renew` ограничен `--config-dir` экземпляра); иначе → строка crontab (текущий пользователь, без привилегий), если доступен `crontab`; иначе → выводятся инструкции для ручной настройки, без принудительной записи. В некоторых дистрибутивах (в том числе Arch/Manjaro) пакет Certbot по умолчанию **не** устанавливает никакого таймера, в отличие от Debian/Ubuntu, — отсюда этот экран вместо простой проверки механизма, якобы уже существующего. После настройки продление автоматически повторно импортирует каждый продлённый сертификат (`certs import`), а затем перезапускает службу, без какого-либо дальнейшего ручного вмешательства.

## 10. Аудит безопасности

`audit security` **не блокирует**: он повторно выполняет уже блокирующие проверки `config check` как `CRITICAL`, а затем применяет рекомендательные правила (TLS, CSP, опасные методы, тайм-ауты, гигиена загрузки — в чистом виде; права файлов, срок действия сертификата, установленный unit systemd, размер журналов — с реальным вводом-выводом). `WAF-001` (WAF остался в `log-only`) отслеживается во времени через небольшой файл состояния (`var/run/waf-mode-state.json`) — срабатывает только после ≥14 дней наблюдения в `log-only` при повторных запусках, а не при первом `audit`.

## 11. Active Defense (deception + режим войны)

Необязательный модуль (`option enable active_defense`, по умолчанию отключён), который квалифицирует враждебное поведение на основе уже вычисленных сигналов WAF (`WafDecision`/репутация/список блокировки — никогда второго независимого расчёта оценки) и может перевести источник на приманку, замедлить его ответы и журналировать подробнее, собрать пригодный к использованию инцидент, а затем экспортировать индикаторы компрометации (IoC). Сам никогда не блокирует трафик — сетевая блокировка остаётся задачей `omega-fire`; Active Defense наблюдает, перенаправляет, замедляет и фиксирует.

**Угрозы и оценка**: каждый источник (`IP + хеш SHA-256 User-Agent`) накапливает оценку (`WAF-001` блокирующий +10, эскалация репутации +25, известный бан +25, POST на уже назначенную приманку +30 — снижение на -5 каждые 15 минут без новых событий), квалифицируемую как `normal`/`suspicious`/`hostile`/`contained` (`contained` дополнительно требует уже известного бана). `mode: monitor` наблюдает, не действуя; `mode: enforce` действительно применяет действия ниже.

**Режим войны** (`options.active_defense.settings.war_mode`): `DefensePlaybook` (`actions: ["redirect_to_decoy", "enrich_log", "delay", "rate_limit", "create_incident", "export_ioc"]`), запускаемый по настраиваемым порогам для любого источника, отличного от `normal`:
- `enrich_log` — отдельный журнал JSONL (`var/log/active-defense-enriched.jsonl`, никогда не смешивается с журналом WAF/продакшена), заголовки отредактированы, тело HTTP хешируется (SHA-256) или обрезается согласно `logging.capture_request_body`.
- `delay` — ограниченное замедление с джиттером (`war_mode.slowdown.minimum_ms`/`maximum_ms`/`jitter_ms`), никогда не блокирует цикл asyncio.
- `rate_limit` — отдельное ограничение частоты для источника (`war_mode.rate_limit.requests`/`window_seconds`), использует тот же механизм, что и WAF, под отдельным ключом.
- `create_incident` — автоматическое открытие/слияние инцидента при превышении `thresholds.incident_score`.

**Deception**: источник `hostile`/`contained` может быть назначен статической приманке (`fake_admin`, `fake_cms`, `fake_api`, `fake_secrets` — правдоподобные, но всегда фиксированные ответы, никогда реального чтения файлов или подпроцессов), выбираемой по наблюдаемому классу атаки (`deception.profiles.<имя>.match_attack_classes`, один или несколько из `scan`/`credential_stuffing`/`sqli`/`xss`/`path_traversal`/`upload_probe`/`api_probe`/`unknown`). Два уровня изоляции, осознанно принятые и задокументированные как таковые:
- **Уровень 1** (fixture внутри процесса, `isolation_level: "fixture"`, по умолчанию) — явно СЛАБАЯ изоляция: тот же процесс, тот же пользователь ОС, что и продакшен, допустимо только потому, что fixture никогда не делает ничего, кроме возврата статического шаблона. ИМЯ профиля должно точно совпадать с одной из 4 fixture выше — иначе оно отклоняется при проверке (`validate_active_defense_config`), чтобы избежать ловушки неверно названной приманки, которая тогда молча никогда не срабатывает.
- **Уровень 2** (действительно изолированный бэкенд, `isolation_level: "proxy"`) — передача отдельному процессу через `options.active_defense.settings.deception.decoy_zones.<имя>` (upstream `host`/`port` уже работающего сервера, никогда не создаётся автоматически; никогда не читается из `options.reverse_proxy` — приманка никогда не может случайно указать на зону продакшена, проверяется в `config check`), с повторным использованием того же механизма исходящего обратного прокси, что и в продакшене (`serve_proxy()` — upstream недоступен в момент реального запроса: атакующему возвращается 502, никогда сбой).

**Экран Настройки** (TUI, Активная безопасность → Active Defense → Настройки): полная настройка всего вышеперечисленного — режим, включение режима войны, охват/действия/пороги/замедление/лимит запросов, deception (поведение по умолчанию, CRUD профилей приманок и зон приманок с примерами значений в каждом поле), IoC, хранение и журналирование — проверяется теми же правилами, что и CLI, перед каждым сохранением, без необходимости вручную редактировать `config/omega-serve.json`. После любого изменения всегда требуется полный перезапуск (Active Defense никогда не перезагружается на лету).

**Инциденты и IoC**: полная хронология для каждого инцидента, извлечение индикаторов (IP, хешированный User-Agent), версионированный экспорт JSON/CSV, ограниченный передаваемыми IoC/отчёт Markdown, а также форматы обмена **STIX 2.1** (пакет для загрузки в OpenCTI, SIEM…) и **MISP** (событие для импорта через интерфейс MISP), по умолчанию с меткой TLP:AMBER — локальные файлы, никогда не отправляются; каждый экспорт сопровождается файлом `<export>.sha256` (стандартный формат `sha256sum`). Автоматический экспорт при закрытии инцидента, если `ioc.auto_export_on_close` (по умолчанию истина). Истёкшие состояния и журнал аудита очищаются автоматически, а размер базы ограничен (защита от заполнения диска); `active-defense purge` дополнительно закрывает затихшие инциденты.

**Имитация**: `active-defense simulate` (CLI) и кнопка "Имитация" (TUI, экран Активная безопасность) прогнозируют оценку/уровень и объясняют каждое действие, которое сработало бы, — строгий dry-run, никакой реальной записи, никакого влияния на сеть.

Резервное копирование/восстановление: `config backup --include-active-defense` включает в архив базу sqlite (угрозы/инциденты/назначения) — никогда секретов в открытом виде, поэтому `--confirm-secrets` не требуется, в отличие от `--include-auth`.

## 11b. Списки чувствительных путей (WAF)

WAF может загружать **редактируемые списки** в виде текстового файла, один путь (или ключевое слово) на строку, через **Активная безопасность → Custom → Добавить → « ЗАГРУЗИТЬ список »**. По умолчанию ничего не загружается: это явное действие.

- **Поставляемые эталоны**: `sensitive-paths-hostile` (298 путей без законного использования: секреты, резервные копии, VCS, консоли…) и `sensitive-paths-probe` (132 пути зондирования, иногда обслуживаемые настоящим сайтом: `/admin`, `/api`, мониторинг…). При загрузке создаётся **локальная копия** в `secure/waf/rules/keywords/`: именно её вы редактируете, обновление omega-serv никогда её не перезаписывает (« Новое в эталоне » затем предлагает новые записи поштучно).
- **Синтаксис**: `/admin` (→ `/admin` и `/admin/xxx`, никогда `/administrator`), `/.git/` (всё внутри), `/*.bak` (расширение), `!/api/v1` (исключение, всегда приоритетно). Пути декодируются так же, как в движке (`%2e`, двойное кодирование, полноширинные символы).
- **Серьёзность**: *Наблюдение* (только журнал, рекомендуется при первой загрузке), затем Средняя (никогда не блокирует сама) или Высокая (403 с первого обращения).
- **Собственное правило повторения для каждого списка**: 1-е обращение = информация или отказ; N обращений за M минут = временный бан на уровне приложения (ответ 451, даже через Tailscale); повторные блокировки = сетевой бан через omega-jail. Эталоны: hostile 2 обращения за 10 мин → 24 ч, зондирование 5 за 10 мин → 1 ч.
- **Никогда автоматического бана** для локального хоста, Tailscale (`100.64.0.0/10`) и локальной сети (`options.waf.reputation.never_auto_block`): забанен может быть только внешний трафик. За локальным прокси исключение для `127.0.0.1` требует активного `trusted_proxy`. `X-Forwarded-For` читается справа налево: клиент не может сам объявить себя локальным.
- **Защитные механизмы**: защищённые жизненно важные пути (`/`, `robots.txt`, `sitemap.xml`, `/.well-known/acme-challenge/`…), отказ блокирующего списка, который затронул бы реально обслуживаемый маршрут (псевдоним, обратный прокси, зона Auth, webroot), **« Сверить с журналами »** в редакторе (строки, которые затронули бы успешные запросы, исключение одним щелчком).
- **Встроенный редактор**: диагностика в реальном времени с номером строки, « Тест » пути, безопасная запись (права и группа сохраняются, символические ссылки отклоняются, внешнее изменение обнаруживается), проверка читаемости для учётной записи службы (« Исправить права ») и **честная** перезагрузка: отклоняется с указанием причины, если список не проходит проверку, при этом сервер сохраняет текущие правила.

## 11c. Лимит запросов для папки и для IP/сети (WAF)

Лимит запросов WAF (token bucket, `options.waf.rate_limit`, по умолчанию 60 запросов / 60 с на IP) можно уточнить в **Активная безопасность → Исключения и лимит запросов** (или вручную: `rate_limit.path_policies` / `rate_limit.source_policies`):

- **Правило для папки** (`prefix`, `requests`, `window_seconds`): оно **заменяет** глобальный лимит для этой папки, со своим счётчиком (`requests: 0` = без ограничения). Побеждает самый длинный префикс; `/images` покрывает `/images/a.png`, но никогда `/images2`. Типичный случай — тяжёлая страница (галерея изображений), которая возвращает 429.
- **Правило для IP/сети** (`network`, `requests`, `window_seconds`, `trusted`): тот же принцип; побеждает самая точная сеть. Приоритет: папка, затем IP/сеть, затем глобальный лимит.
- **Бан для публики без изменений**: превышение с публичного IP по-прежнему записывается как `"action": "block"` в `waf-alerts.log` и потому может быть забанено omega-jail (3 отказа за 10 мин → 12 ч). **Надёжный источник** — сеть `never_auto_block` или правило с пометкой `trusted: true` — всё так же получает 429, но записывается как `"action": "throttle"`, который jail никогда не учитывает.
- **Скрипт magnet**: его собственный лимит запросов (ответ 429) никогда не считается обнаружением и потому никогда не ведёт к автоматическому бану; для запроса, покрытого правилом папки или IP/сети, действует встроенное правило, а 429 от magnet игнорируется (его сигнатуры атак продолжают применяться).
- Правило лимита **никогда** не отключает проверку WAF; и наоборот, исключение из проверки (`exclusions.path_prefixes`) никогда не снимает лимит запросов. Без активного `trusted_proxy` правило для `127.0.0.1`/`::1` игнорируется (та же защита, что и у `never_auto_block`).

## 12. Службы и эксплуатация

Автоматическое определение systemd/OpenRC/runit (`service install/status/start/stop/restart/enable/disable/uninstall`). Создаваемый unit systemd по умолчанию применяет неоспоримое усиление: `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome`, `ReadWritePaths`, ограниченный `var/`, обязательные выделенные пользователь/группа, `UMask=0077`, `Restart=on-failure`. ### 13a. Удалённые источники (SSH)

По явному запросу централизует журнал бэкенд-сервера в той же локальной сети за обратным прокси (экран **Управление журналами → Библиотека → Удалённые источники (SSH)**). « Fetch » — ручное разовое действие, никогда не поток в реальном времени и не автоматический опрос: **копия** получается через `scp` в момент щелчка по *Получить сейчас*, записывается в `var/log/remote/`, а затем добавляется в Библиотеку как обычный журнал (колонка *Доступ* = `ssh`, колонка *Изменено* = дата **этого** получения — никогда дата удалённого файла); новое получение просто заменяет предыдущую копию более свежей.

Осознанные защитные механизмы (полное исследование см. в `OMEGA-SERV_ETUDE-FAISABILITE_LOGS_DISTANTS.md`): никакого автоматического сканирования сети, никакого подключения без явной настройки (метка/хост/удалённый путь, пользователь/порт/закрытый ключ необязательны — пустые значения позволяют `ssh`/`~/.ssh/config` решать так, как если бы команда вводилась вручную), никогда не запрашивается и не хранится пароль (закрытый ключ указывается только путём, Omega-serv никогда его не читает и не хранит), никакой проверки размера перед передачей. Возможность `scp` определяется локально в **Реестре возможностей** (только наличие программы, никогда не проверка доступности хоста); Samba намеренно оставлена в стороне (YAGNI, пока не подтвердится реальная потребность).
