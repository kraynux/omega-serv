# omega-serv เทียบกับเว็บเซิร์ฟเวอร์ในตลาด

**การเปรียบเทียบที่วัดผลจริง: nginx · lighttpd · Caddy · Apache · Traefik · omega-serv 2.0**

🌐 [Français](../../comparatif-serveurs-web.md) · [English](../en/comparatif-serveurs-web.md) · [Español](../es/comparatif-serveurs-web.md) · [Português (Brasil)](../pt-BR/comparatif-serveurs-web.md) · [Italiano](../it/comparatif-serveurs-web.md) · [Deutsch](../de/comparatif-serveurs-web.md) · [Nederlands](../nl/comparatif-serveurs-web.md) · [Polski](../pl/comparatif-serveurs-web.md) · [Русский](../ru/comparatif-serveurs-web.md) · [中文](../zh-CN/comparatif-serveurs-web.md) · [Tiếng Việt](../vi/comparatif-serveurs-web.md) · **ไทย** · [Bahasa Indonesia](../id/comparatif-serveurs-web.md) · [日本語](../ja/comparatif-serveurs-web.md) · [한국어](../ko/comparatif-serveurs-web.md) · [हिन्दी](../hi/comparatif-serveurs-web.md) · [العربية](../ar/comparatif-serveurs-web.md)

เอกสารนี้วาง omega-serv ไว้ท่ามกลางเว็บเซิร์ฟเวอร์ที่แพร่หลายที่สุด ไม่ได้พยายามชี้ว่า « เซิร์ฟเวอร์ที่ดีที่สุด » คือตัวใด: แต่ละเครื่องมือตอบโจทย์ความต้องการที่ต่างกัน เอกสารนี้ให้สามสิ่ง:

1. **การวัดจริง** บนเครื่องเดียวกัน ด้วยไคลเอนต์เดียวกันและไฟล์เดียวกัน และทำซ้ำได้
2. **การเปรียบเทียบฟังก์ชัน** ซึ่งแต่ละฟังก์ชันตรวจสอบกับเอกสารทางการของแต่ละเซิร์ฟเวอร์ (ลิงก์อยู่ท้ายเอกสาร) โดยแยกสิ่งที่มีในตัวออกจากสิ่งที่ต้องใช้โมดูลหรือปลั๊กอิน
3. สิ่งที่ omega-serv **ให้เพิ่มขึ้นจริง** และสิ่งที่ตัวอื่น **ทำได้ดีกว่า**

ตัวเลขทั้งหมดด้านล่างวัดเมื่อวันที่ 26 ตุลาคม 2026 ไม่มีตัวเลขใดนำมาจากเว็บไซต์อื่นหรือเป็นการประมาณ

## 1. สรุปสั้น

- **ปริมาณงานดิบกับไฟล์ขนาดเล็ก**: nginx และ lighttpd ซึ่งเขียนด้วย C ให้บริการคำขอต่อวินาทีได้ **มากกว่า 10 ถึง 20 เท่า** ของ omega-serv ซึ่งเขียนด้วย Python ส่วน Caddy ซึ่งเขียนด้วย Go อยู่ตรงกลาง นี่เป็นความต่างโดยธรรมชาติ ไม่ใช่เรื่องการปรับแต่ง: omega-serv ไม่ได้มุ่งแข่งในสนามนี้
- **ไฟล์ขนาดใหญ่**: ตั้งแต่เวอร์ชัน 2.0 omega-serv มอบการส่งให้เคอร์เนล (`sendfile`) จึงทำได้ **ในระดับปริมาณงานเดียวกัน** กับ nginx, lighttpd และ Caddy บนเครื่องนี้: 2.1 GB/s เทียบกับ 2.0 ถึง 2.4 GB/s
- **หน่วยความจำ**: lighttpd (1 MB) และ nginx (4 ถึง 5 MB) ยังเกินเอื้อม omega-serv ใช้ต่ำกว่า 30 MB ขณะรับโหลดด้วย 1 โปรเซส ส่วน Caddy ประมาณ 55 MB
- **จาก 1.0 ถึง 2.0**: ปริมาณงานไฟล์ใหญ่เพิ่มขึ้น 2.8 เท่า หน่วยความจำระหว่างดาวน์โหลดไฟล์ใหญ่ลดลง 45 เท่า สูงสุด +50 % กับไฟล์เล็กเมื่อใช้ 2 โปรเซส (โหมด boost) ต้นทุนของ Active Defense ลดลง 12 เท่า
- **สิ่งที่ omega-serv มีเพิ่ม**: การดูแลระบบครบถ้วนผ่านอินเทอร์เฟซเทอร์มินัล (TUI) ใน 17 ภาษา WAF และการป้องกันเชิงรุกในตัว ขีดจำกัดด้านความปลอดภัยที่ยังแม่นยำเมื่อใช้หลายโปรเซส การนำเข้าสคริปต์ mod_magnet ของ lighttpd การจัดการหลายอินสแตนซ์
- **สิ่งที่ไม่มี**: HTTP/2 และ HTTP/3 การค้นหาบริการ Docker/Kubernetes ไคลเอนต์ ACME ในตัว (ใช้ Certbot) และปริมาณงานระดับเซิร์ฟเวอร์ที่เขียนด้วย C

## 2. วิธีการวัด

### เครื่องและซอฟต์แวร์

| องค์ประกอบ | ค่า |
|---|---|
| โปรเซสเซอร์ | Intel Core i5 M480 2.67 GHz (2010): 2 คอร์จริง 4 เธรด |
| หน่วยความจำ | 8 GB |
| ระบบ | Manjaro Linux เคอร์เนล 6.18 |
| เครือข่าย | ลูปแบ็กภายในเครื่อง (127.0.0.1) |
| ไคลเอนต์สร้างโหลด | [oha](https://github.com/hatoo/oha) 1.16.0 (เขียนด้วย Rust) |
| nginx | 1.30.4 (แพ็กเกจ Manjaro) |
| lighttpd | 1.4.85 (แพ็กเกจ Manjaro) |
| Caddy | 2.11.4 (แพ็กเกจ Manjaro) |
| omega-serv | 1.0.0 (ไฟล์เก็บถาวรที่เผยแพร่) และ 2.0.0 บน Python 3.14.7 |

Apache และ Traefik ไม่ได้ถูกวัด เพราะไม่ได้ติดตั้งบนเครื่องนี้ อีกทั้ง Traefik ไม่ใช่เซิร์ฟเวอร์ไฟล์ (ดู §5) ทั้งสองจึงปรากฏเฉพาะในการเปรียบเทียบฟังก์ชัน

### ขั้นตอน

- **การแยกโปรเซสเซอร์**: แต่ละเซิร์ฟเวอร์ถูกตรึงไว้ที่คอร์จริง 0 (เธรด 0 และ 2) และไคลเอนต์ที่คอร์จริง 1 (เธรด 1 และ 3) ไคลเอนต์จึงไม่แย่งเวลาของเซิร์ฟเวอร์ และทุกเซิร์ฟเวอร์ได้ทรัพยากรเท่ากันทุกประการ
- **ไฟล์เดียวกันสำหรับทุกตัว**: `small.html` (1 KB), `medium.png` (100 KB) และ `large.bin` (5 MB) ให้บริการจากโฟลเดอร์เดียวกัน
- **เปิดล็อกการเข้าถึงทุกที่** เพราะเซิร์ฟเวอร์ใน production บันทึกล็อก
- **HTTP/1.1 แบบไม่เข้ารหัส การเชื่อมต่อแบบคงอยู่ (keep-alive)** การทำงานพร้อมกัน 32 การเชื่อมต่อสำหรับไฟล์ 1 KB และ 100 KB และ 8 สำหรับไฟล์ 5 MB
- **ระยะเวลา**: 10 วินาทีต่อไฟล์ต่อการตั้งค่า
- **การทำซ้ำ**: 3 รอบเต็ม สลับกัน (ทุกเซิร์ฟเวอร์ในรอบที่ 1 แล้วทุกเซิร์ฟเวอร์ในรอบที่ 2 เป็นต้น) ตารางแสดง **ค่ามัธยฐาน** ของสามรอบ
- **หน่วยความจำ**: PSS (*Proportional Set Size*) รวมของทุกโปรเซสของเซิร์ฟเวอร์ ต่างจาก RSS ตรงที่หน้าหน่วยความจำที่ใช้ร่วมกันระหว่างโปรเซสถูกนับเพียงครั้งเดียว วัดขณะว่าง แล้ววัดหลังรับโหลด
- **การตั้งค่า**: nginx, lighttpd และ Caddy ในการตั้งค่าพื้นฐาน (ไฟล์สแตติก ล็อกการเข้าถึง) omega-serv ใช้โปรไฟล์ `standard` โดยปิด WAF แล้วเปิดพร้อมกฎทั้งหมดที่จัดให้
- **จำนวนโปรเซส**: แต่ละเซิร์ฟเวอร์ถูกวัดด้วย 1 แล้ว 2 โปรเซส (nginx `worker_processes`, lighttpd `server.max-worker`, Caddy `GOMAXPROCS`, omega-serv `server.workers`)

### ข้อจำกัดที่ควรรู้

- **เครื่องธรรมดาและเก่า** ค่าสัมบูรณ์จะสูงกว่านี้มากบนเซิร์ฟเวอร์รุ่นใหม่ สิ่งที่มีความหมายคือ **อัตราส่วน** ระหว่างเซิร์ฟเวอร์ที่วัดในเซสชันเดียวกัน
- **ความแปรปรวนระหว่างเซสชัน**: ประมาณ 10 ถึง 30 % ตามโหลดเบื้องหลังของเครื่อง ส่วนรอบในเซสชันเดียวกันยังสอดคล้องกัน: ต่างกันไม่ถึง 5 % สำหรับ omega-serv และ Caddy มากกว่านั้นสำหรับ nginx และ lighttpd ซึ่งปริมาณงานสูงมากจึงไวต่อส่วนอื่นของเครื่องมากกว่า
- **ลูปแบ็กภายในเครื่อง**: การวัดไม่ได้ผ่านเครือข่ายจริง บนเครือข่ายจริง ปริมาณงานของไฟล์ใหญ่แทบจะถูกจำกัดด้วยแบนด์วิดท์เสมอ ไม่ใช่ด้วยเซิร์ฟเวอร์
- **ไม่มี TLS** ในการวัดเหล่านี้ เมื่อใช้ HTTPS omega-serv ใช้ `sendfile` ไม่ได้และส่งไฟล์เป็นบล็อก
- **ข้อมูลดิบ**: เผยแพร่พร้อมเอกสารนี้ใน [`docs/benchmarks/2026-10-26-campagne-brute.txt`](../../benchmarks/2026-10-26-campagne-brute.txt)

### การอ่านผล

- **กับไฟล์ขนาดเล็กและกลาง** ช่องว่างกับ nginx และ lighttpd อยู่ในระดับหนึ่งลำดับขนาด (×10 ถึง ×20) นี่คือต้นทุนของเซิร์ฟเวอร์ที่เขียนด้วย Python: ทุกคำขอผ่านตัวแปลภาษา ขณะที่ nginx และ lighttpd ประมวลผลด้วย C ที่คอมไพล์แล้ว โหมด boost ลดช่องว่างได้ แต่ไม่ปิดช่องว่าง
- **กับไฟล์ขนาดใหญ่** เซิร์ฟเวอร์ทั้งหมดมาบรรจบกัน เพราะเคอร์เนลเป็นผู้คัดลอกข้อมูล (`sendfile`) ด้วย 2 โปรเซส omega-serv 2.0 ทำได้ 2.1 GB/s อยู่ในช่วงเดียวกับตัวอื่น (2.0 ถึง 2.4 GB/s)
- **WAF ของ omega-serv มีต้นทุนประมาณ 17 %** กับไฟล์ขนาดเล็ก: มันตรวจทุกคำขอ nginx, lighttpd และ Caddy ถูกวัดโดยไม่มี WAF ส่วน WAF ที่เพิ่มให้เซิร์ฟเวอร์เหล่านี้ (ModSecurity, Coraza) ก็มีต้นทุนเช่นกัน ซึ่งไม่ได้วัดที่นี่
- **เพื่อให้เห็นภาพ**: 1 300 คำขอต่อวินาทีคือมากกว่า 110 ล้านคำขอต่อวันบนเครื่องปี 2010 นี้ ซึ่งเกินความต้องการของเว็บไซต์ส่วนตัว บริการภายใน หรือห้องแล็บไปมาก ซึ่งเป็นการใช้งานที่ omega-serv มุ่งเป้า

## 4. omega-serv 1.0 → 2.0: สิ่งที่เปลี่ยนไป พร้อมผลการวัด

### ประสิทธิภาพ

ทั้งสองเวอร์ชันถูกวัดในเซสชันเดียวกัน บนเครื่องเดียวกัน และด้วยขั้นตอนเดียวกัน

| การวัด | 1.0.0 | 2.0.0 | การเปลี่ยนแปลง |
|---|---:|---:|---:|
| ไฟล์เล็ก (1 KB), 1 โปรเซส | 1 304 req/s | 1 358 req/s | +4 % |
| ไฟล์เล็ก (1 KB), โหมด boost 2 โปรเซส | — | 1 953 req/s | **+50 %** เทียบกับ 1.0 |
| ไฟล์เล็กพร้อม WAF, 1 โปรเซส | 1 097 req/s | 1 130 req/s | +3 % |
| ไฟล์เล็กพร้อม WAF, 2 โปรเซส | — | 1 617 req/s | **+47 %** เทียบกับ 1.0 |
| ไฟล์ 100 KB, 1 โปรเซส | 1 064 req/s | 1 247 req/s | +17 % |
| ไฟล์ใหญ่ (5 MB), 1 โปรเซส | 584 MB/s | 1 658 MB/s | **×2.8** |
| ไฟล์ใหญ่ (5 MB), 2 โปรเซส | — | 2 115 MB/s | **×3.6** เทียบกับ 1.0 |
| หน่วยความจำหลังรับโหลด, 1 โปรเซส | 100 MB | 30 MB | **÷3** |

### การดาวน์โหลดไฟล์ใหญ่พร้อมกัน

การทดสอบ: ดาวน์โหลดไฟล์ 300 MB พร้อมกัน 3 รายการ ขณะที่มีการขอหน้าเล็ก ๆ ต่อเนื่อง การรันสองครั้งให้ผลเหมือนกัน

| การวัด | 1.0.0 | 2.0.0 |
|---|---:|---:|
| หน่วยความจำของเซิร์ฟเวอร์สูงสุด | 1 835 MB | 40 MB |
| หน้าเล็กระหว่างการดาวน์โหลด: มัธยฐาน | 3 ถึง 4 ms | 2 ms |
| หน้าเล็กระหว่างการดาวน์โหลด: กรณีแย่ที่สุด | 1.7 ถึง 1.8 วินาที | 5 ms |

เวอร์ชัน 1.0 โหลดแต่ละไฟล์ทั้งหมดเข้าหน่วยความจำก่อนส่ง เวอร์ชัน 2.0 ส่งเป็นบล็อกหรือมอบให้เคอร์เนล: หน่วยความจำไม่ขึ้นกับขนาดไฟล์อีกต่อไป และเซิร์ฟเวอร์ยังตอบสนองได้ระหว่างการดาวน์โหลด

### ต้นทุนของการป้องกันเชิงรุก

ต้นทุนของการบันทึกการสังเกตภัยคุกคามหนึ่งครั้งโดย Active Defense สำหรับแต่ละคำขอที่น่าสงสัย วัดบนดิสก์ (ext4) จากการสังเกต 2 000 ครั้ง:

| การวัด | 1.0.0 | 2.0.0 |
|---|---:|---:|
| มัธยฐาน | 2.84 ms | 0.23 ms |
| p99 | 11.6 ms | 2.3 ms |
| สูงสุด | 18 ถึง 20 ms | 37 ถึง 46 ms |

มัธยฐานลดลง 12 เท่า แต่ค่าสูงสุดในเวอร์ชัน 2.0 สูงกว่า: เป็นจุดพุ่งสูงเฉพาะครั้ง ที่เกี่ยวกับการเขียนล็อกของ SQLite ลงดิสก์เป็นระยะ

### ฟังก์ชันที่มาพร้อมเวอร์ชัน 2.0

**ตามทันมาตรฐานของตลาด**: nginx, lighttpd, Caddy และ Apache ทำทั้งหมดนี้ได้อยู่แล้ว omega-serv ตามทันพวกเขา

- คำขอแบบมีเงื่อนไข (ETag, Last-Modified, การตอบกลับ 304): การรีโหลดหน้าจะดาวน์โหลดใหม่เฉพาะสิ่งที่เปลี่ยน
- คำขอบางส่วน (Range, 206/416): ดาวน์โหลดต่อ เลื่อนวิดีโอ
- การส่งไฟล์ด้วย `sendfile` หรือเป็นบล็อก พร้อมหน่วยความจำที่คงที่
- ไฟล์ที่บีบอัดไว้ล่วงหน้า (`.gz`, `.br`) วางข้างต้นฉบับ
- Cache-Control เริ่มต้นตามประเภทไฟล์ (รูปภาพ ฟอนต์ CSS/JS) ปรับได้
- หลายโปรเซสเซิร์ฟเวอร์ (โหมด boost, `server.workers`)

**ฟังก์ชันที่ขยายมากขึ้น:**

- **Reverse proxy ฉบับสมบูรณ์** เวอร์ชัน 1.0 มีเพียงตัวส่งต่อธรรมดา (วนรอบ TLS ไปยังต้นทาง WebSocket) เวอร์ชัน 2.0 เพิ่ม:
  - กลยุทธ์การกระจาย 6 แบบ รวมเป็น 7 แบบ
  - การยึดเซสชันและการกำหนดเส้นทางตามเฮดเดอร์
  - การตรวจสุขภาพแบบรับและแบบรุกของเซิร์ฟเวอร์ต้นทาง
  - แคชการตอบกลับ
  - การป้องกันโหลดเกินและการวนลูป
  - การควบคุมขณะทำงาน
- **การจำกัดอัตราตามโฟลเดอร์และตามที่อยู่หรือเครือข่าย** นอกเหนือจากขีดจำกัดรวม
- **ตัวนับด้านความปลอดภัยที่ใช้ร่วมกันระหว่างโปรเซส** (ดู §7)
- **รายการพาธที่อ่อนไหว** พร้อมใช้ พร้อมโหมดสังเกตการณ์และตัวแก้ไขในตัว
- **การนำเข้าสคริปต์ mod_magnet ของ lighttpd** (ดู §7)
- **อินเทอร์เฟซใน 17 ภาษา** พร้อมภาษาแยกสำหรับหน้าที่ผู้เยี่ยมชมเห็นและสำหรับการส่งออก
- **ล็อกที่ปรับปรุงใหม่ทั้งหมด**:
  - คลังล็อก
  - ตัวดูสามแบบ รวมถึง lnav
  - การดึงล็อกระยะไกลผ่าน SSH

## 6. การดูแลระบบและความสะดวกในการใช้งาน

| เซิร์ฟเวอร์ | วิธีดูแลระบบหลัก | อินเทอร์เฟซ | การโหลดใหม่โดยไม่ขัดจังหวะ |
|---|---|---|---|
| nginx | ไฟล์การตั้งค่า | ไม่มี (แดชบอร์ด: NGINX Plus เชิงพาณิชย์) | ✅ `nginx -s reload` |
| lighttpd | ไฟล์การตั้งค่า | ไม่มี (mod_status อ่านอย่างเดียว) | ✅ การรีสตาร์ทแบบนุ่มนวล |
| Caddy | Caddyfile หรือ JSON | REST API สำหรับผู้ดูแล | ✅ ผ่าน API |
| Apache | ไฟล์การตั้งค่าและ `.htaccess` | ไม่มี (mod_status อ่านอย่างเดียว) | ✅ `graceful` |
| Traefik | ป้ายกำกับคอนเทนเนอร์ ไฟล์ หรือ Kubernetes | แดชบอร์ดเว็บ (อ่านอย่างเดียว) | ✅ การตั้งค่าแบบไดนามิก |
| omega-serv | อินเทอร์เฟซเทอร์มินัล (TUI) และบรรทัดคำสั่ง (CLI) ไม่ต้องแก้ไขไฟล์ JSON | **TUI ครบถ้วนด้วยแป้นพิมพ์และเมาส์ 17 ภาษา ความช่วยเหลือในตัว** | ✅ สำหรับการตั้งค่าส่วนใหญ่ แจ้งให้รีสตาร์ทสำหรับพอร์ต TLS และจำนวนโปรเซส |

ในทางปฏิบัติ กับ omega-serv การตั้งค่า ความปลอดภัย ล็อก บริการของระบบ การสำรอง และอินสแตนซ์ ล้วนจัดการได้จากอินเทอร์เฟซเดียว ทุกการตั้งค่ามีคำอธิบายและถูกตรวจสอบก่อนบันทึก ส่วนเซิร์ฟเวอร์อื่น ผู้ใช้แก้ไขไฟล์ข้อความ แล้วใช้เครื่องมือแยกต่างหาก (Certbot, fail2ban, logrotate, ModSecurity, เครื่องมือตรวจติดตาม…)

ในทางกลับกัน แนวทาง « ไฟล์การตั้งค่า » ของ nginx, Apache และ Caddy ทำงานอัตโนมัติได้ดีมาก (Ansible คอนเทนเนอร์ การควบคุมเวอร์ชัน) omega-serv มี CLI ที่เขียนสคริปต์ได้ แต่ระบบนิเวศด้านการทำงานอัตโนมัติยังจำกัด

## 7. สิ่งที่ omega-serv ให้เพิ่มขึ้น

ส่วนนี้เก็บไว้เฉพาะสิ่งที่ไม่มีเซิร์ฟเวอร์ใดในการเปรียบเทียบให้มาในตัว โดยไม่ต้องใช้โมดูลบุคคลที่สามหรือเครื่องมือภายนอก

1. **การดูแลระบบครบถ้วนผ่านอินเทอร์เฟซเทอร์มินัล**
   - อินเทอร์เฟซครอบคลุมทั้งเซิร์ฟเวอร์: เว็บไซต์ ความปลอดภัย ล็อก บริการ การสำรอง และอินสแตนซ์
   - ใช้ได้ด้วยแป้นพิมพ์และเมาส์ บนเซิร์ฟเวอร์ที่ไม่มีหน้าจอกราฟิก แม้ผ่าน SSH
   - มีให้ใช้ใน 17 ภาษา และอธิบายทุกการตั้งค่า
   - เซิร์ฟเวอร์อื่นไม่มีอินเทอร์เฟซดูแลระบบ (nginx, lighttpd, Apache) หรือมีเพียง API (Caddy) หรือแดชบอร์ดแบบอ่านอย่างเดียว (Traefik)
2. **ความปลอดภัยเชิงรุกในตัว ไม่ต้องประกอบโมดูล**
   - WAF ประกอบด้วยซิกเนเจอร์ รายการพาธที่แก้ไขได้ การกระทำซ้ำ รายการบล็อกพร้อมวันหมดอายุ ชื่อเสียง และโหมดสังเกตการณ์
   - Active Defense เพิ่มเหยื่อล่อ โหมดสงคราม การติดตามเหตุการณ์ การส่งออกตัวบ่งชี้การบุกรุก และการจำลองแบบไม่มีผล
   - ที่อื่น ฟังก์ชันเหล่านี้ต้องประกอบ ModSecurity หรือ Coraza ชุดกฎ และ fail2ban เข้าด้วยกัน
3. **ขีดจำกัดด้านความปลอดภัยที่แม่นยำเมื่อใช้หลายโปรเซส**
   - ในโหมด boost การจำกัดอัตราและการกระทำซ้ำของ WAF ใช้หน่วยความจำร่วมกันระหว่างโปรเซส ผู้โจมตีจึงไม่สามารถคูณขีดจำกัดของตนด้วยจำนวนโปรเซสได้
   - lighttpd ระบุกรณีตรงข้ามไว้ในเอกสาร: เมื่อใช้ `server.max-worker` `mod_evasive` และ `mod_status` นับแยกในแต่ละโปรเซส
   - nginx ก็ใช้ตัวนับร่วมกันเช่นกัน (โซน `limit_req`) แต่ไม่มี WAF ในตัว
4. **การนำเข้าสคริปต์ mod_magnet ของ lighttpd**
   - สคริปต์ป้องกัน Lua ที่เขียนไว้แล้วสำหรับ lighttpd นำเข้าได้โดยไม่ต้องเขียนใหม่
   - มันเพิ่มเข้าไปในการป้องกันในตัวโดยไม่มีทางทำให้อ่อนแอลง และตรวจสอบความเข้ากันได้ก่อนเปิดใช้งาน
5. **การจัดการหลายอินสแตนซ์**
   - ทะเบียนรวบรวมทุกอินสแตนซ์ และอินเทอร์เฟซสลับจากอินสแตนซ์หนึ่งไปอีกอินสแตนซ์หนึ่งได้
   - ยังถอนการติดตั้งอินสแตนซ์ได้ทั้งหมด
6. **การตรวจสอบความปลอดภัยของการตั้งค่า**: คำสั่ง `audit security` ให้ข้อมูล ไม่เคยขัดขวาง และส่งคืนรหัสออกที่ใช้ในสคริปต์ได้
7. **แหล่งล็อกระยะไกล**
   - อินเทอร์เฟซดึงล็อกของเซิร์ฟเวอร์อื่นผ่าน SSH ตามคำขอ โดยไม่บันทึกรหัสผ่าน
   - อ่านล็อกนั้นด้วย lnav ได้ โดยรวมกับล็อกในเครื่อง
8. **การเสริมความแข็งแกร่ง HTTP ที่ปิดไม่ได้** ทำงานตั้งแต่ติดตั้ง ไม่ว่าโปรไฟล์ใด:
   - ตรวจสอบเฮดเดอร์ Host อย่างเข้มงวด
   - ปฏิเสธความกำกวมของ Content-Length / Transfer-Encoding
   - เฮดเดอร์ความปลอดภัยและ CSP แม้ในหน้าข้อผิดพลาด
   - อ่าน X-Forwarded-For อย่างปลอดภัย
   - ปฏิเสธการเริ่มทำงานในฐานะ root

## 8. สิ่งที่ตัวอื่นทำได้ดีกว่า

- **ปริมาณงานและความหน่วง**: nginx และ lighttpd ให้บริการคำขอขนาดเล็กได้มากกว่า 10 ถึง 20 เท่า ด้วยความหน่วงต่ำกว่า 8 ถึง 10 เท่า สำหรับเว็บไซต์ที่มีทราฟฟิกสูง API สาธารณะ หรือ CDN ควรเลือกพวกเขา
- **หน่วยความจำ**: lighttpd (1 MB) และ nginx (4 ถึง 5 MB) เหมาะกับเครื่องที่มีทรัพยากรจำกัดมาก (ระบบฝังตัว Raspberry Pi รุ่นเริ่มต้น คอนเทนเนอร์ขนาดเล็ก)
- **โปรโตคอล**: HTTP/2 มีในทุกตัวอื่น HTTP/3 มีใน nginx, Caddy และ Traefik omega-serv ใช้ได้เพียง HTTP/1.1
- **HTTPS อัตโนมัติ**: Caddy และ Traefik มีในตัวเป็นค่าเริ่มต้น ส่วน nginx (`ngx_http_acme_module`) และ Apache (`mod_md`) ผ่านโมดูลทางการ omega-serv มอบหมายให้ Certbot พร้อมตัวช่วยและการต่ออายุตามกำหนดเวลา
- **สภาพแวดล้อมแบบคอนเทนเนอร์**: การค้นหาบริการอัตโนมัติของ Traefik (Docker, Kubernetes) ไม่มีสิ่งเทียบเท่าใน omega-serv
- **ระบบนิเวศ**: nginx และ Apache มีโมดูล คู่มือ และการเชื่อมต่อหลายพันรายการ Caddy มีระบบโมดูลด้วย Go omega-serv เป็นโปรเจกต์ใหม่ที่ดูแลโดยคนเพียงคนเดียว
- **การบีบอัดแบบทันที**: omega-serv ให้บริการเฉพาะไฟล์ที่บีบอัดไว้แล้ว

## 9. เซิร์ฟเวอร์ใดเหมาะกับการใช้งานใด

| ความต้องการ | ตัวเลือกที่แนะนำ |
|---|---|
| เว็บไซต์ทราฟฟิกสูง API สาธารณะ CDN ปริมาณงานสูงสุด | **nginx** |
| เครื่องที่มีทรัพยากรจำกัดมาก ระบบฝังตัว ไฟล์สแตติก | **lighttpd** |
| เริ่มต้นเร็วพร้อม HTTPS อัตโนมัติ การตั้งค่าสั้น | **Caddy** |
| แอปพลิเคชัน PHP รุ่นเก่า `.htaccess` โฮสติ้งแบบแชร์ | **Apache** |
| Docker, Kubernetes, ไมโครเซอร์วิส | **Traefik** |
| เว็บไซต์เล็ก บริการภายใน ห้องแล็บ VPN การดูแลระบบโดยไม่ต้องแก้ไขไฟล์ | **omega-serv** |
| เซิร์ฟเวอร์ที่เปิดสู่ภายนอกซึ่งต้องการดูและควบคุมความปลอดภัย (WAF การแบน เหยื่อล่อ) จากอินเทอร์เฟซเดียว | **omega-serv** |
| Reverse proxy ภายในพร้อมการกระจาย การตรวจสุขภาพ และแคช ควบคุมจากอินเทอร์เฟซ | **omega-serv** |
| เรียนรู้การเสริมความแข็งแกร่ง HTTP และการป้องกันเชิงรุก | **omega-serv** |

เครื่องมือเหล่านี้ยังใช้ร่วมกันได้ ตัวอย่างเช่น:
- nginx หรือ Traefik เป็นด่านหน้าบนอินเทอร์เน็ต โดยมี omega-serv อยู่ข้างหลังสำหรับบริการภายใน ความปลอดภัย และการดูแลระบบของบริการนั้น
- omega-serv เป็น reverse proxy ภายในหน้าแอปพลิเคชันเซิร์ฟเวอร์หลายตัว

## 10. ทำการวัดซ้ำ

เครื่องมือรวมอยู่ในคลังโค้ด ใต้ `tools/bench/` ต้องติดตั้ง nginx, lighttpd, Caddy และ oha รวมถึงสภาพแวดล้อมการพัฒนาของ omega-serv (`.venv`)

```sh
# 1. เตรียมโฟลเดอร์สำหรับการวัด (ไฟล์ทดสอบ การตั้งค่า omega-serv 1.0 และ 2.0)
tools/bench/compare/setup.sh /path/mesure omega-serv-1.0.0.tar.gz

# 2. 12 การตั้งค่า ทำซ้ำ 3 รอบแบบสลับกัน (ประมาณ 22 นาที)
tools/bench/compare/campaign.sh /path/mesure > results.txt

# 3. ค่ามัธยฐาน
python3 tools/bench/compare/summarize.py results.txt

# การดาวน์โหลดไฟล์ใหญ่ (หน่วยความจำและการตอบสนอง) 2.0 แล้ว 1.0
.venv/bin/python tools/bench/bigfile.py
BENCH_SRC=/path/mesure/v1-archive/omega-serv/src \
BENCH_EXTRA_PATH=/path/mesure/v1-archive/omega-serv/vendor/omega-lib/src \
  .venv/bin/python tools/bench/bigfile.py

# วัดเซิร์ฟเวอร์อื่นใดก็ได้ที่ทำงานอยู่แล้ว โดยไม่ต้องใช้ oha
python3 tools/bench/bench_any.py --make-files /srv/webroot-test
python3 tools/bench/bench_any.py --port 8080
```

โดยค่าเริ่มต้น เซิร์ฟเวอร์ถูกตรึงที่เธรด 0 และ 2 และไคลเอนต์ที่เธรด 1 และ 3 ซึ่งตรงกับเครื่องที่ใช้วัด ปรับการแบ่งนี้ให้เข้ากับโปรเซสเซอร์ของคุณ (`lscpu -e` แสดงโครงสร้าง) ด้วยตัวแปร `SRV_CPUS` และ `CLI_CPUS`

หากต้องการเผยแพร่ผลของคุณเอง ให้ระบุเครื่อง เวอร์ชัน การแบ่งโปรเซสเซอร์ และการทำซ้ำทั้งสามรอบ
