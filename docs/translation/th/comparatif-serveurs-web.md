# omega-serv เทียบกับเว็บเซิร์ฟเวอร์ในตลาด

**การเปรียบเทียบจากการวัดจริง: nginx · lighttpd · Apache · Caddy · Traefik · omega-serv 2.5**

🌐 [Français](../../comparatif-serveurs-web.md) · [English](../en/comparatif-serveurs-web.md) · [Español](../es/comparatif-serveurs-web.md) · [Português (Brasil)](../pt-BR/comparatif-serveurs-web.md) · [Italiano](../it/comparatif-serveurs-web.md) · [Deutsch](../de/comparatif-serveurs-web.md) · [Nederlands](../nl/comparatif-serveurs-web.md) · [Polski](../pl/comparatif-serveurs-web.md) · [Русский](../ru/comparatif-serveurs-web.md) · [中文](../zh-CN/comparatif-serveurs-web.md) · [Tiếng Việt](../vi/comparatif-serveurs-web.md) · **ไทย** · [Bahasa Indonesia](../id/comparatif-serveurs-web.md) · [日本語](../ja/comparatif-serveurs-web.md) · [한국어](../ko/comparatif-serveurs-web.md) · [हिन्दी](../hi/comparatif-serveurs-web.md) · [العربية](../ar/comparatif-serveurs-web.md)

เอกสารนี้ระบุตำแหน่งของ omega-serv ท่ามกลางเว็บเซิร์ฟเวอร์ที่ใช้กันมากที่สุด เอกสารไม่ได้มุ่งตัดสินว่า “เซิร์ฟเวอร์ไหนดีที่สุด” เพราะแต่ละเครื่องมือตอบโจทย์ความต้องการต่างกันและต่างก็มีจุดแข็ง เอกสารนี้ให้สามสิ่ง:

1. **การวัดจริง** บน**เครื่องสามเครื่อง**ที่แตกต่างกันมาก ด้วยไคลเอนต์ ไฟล์ และขั้นตอนเดียวกัน และทำซ้ำได้;
2. **การเปรียบเทียบฟีเจอร์** ซึ่งแต่ละข้อตรวจสอบกับเอกสารทางการของเซิร์ฟเวอร์นั้น (ลิงก์อยู่ท้ายเอกสาร) โดยแยกสิ่งที่มีในตัวออกจากสิ่งที่ต้องใช้โมดูลหรือปลั๊กอิน;
3. สิ่งที่ omega-serv **มีเพิ่มเติมจริง** และสิ่งที่เซิร์ฟเวอร์อื่น**ทำได้ดีกว่า**

การวัดประสิทธิภาพทั้งหมดทำเมื่อวันที่ 3 และ 4 พฤศจิกายน 2026 ไม่มีตัวเลขใดนำมาจากเว็บไซต์อื่นหรือเป็นการประมาณ ข้อมูลดิบเผยแพร่พร้อมกับเอกสารนี้

## 1. สรุปย่อ

- **omega-serv มีสองเอนจิน** **เอนจิน Python** จัดการทุกอย่าง **เอนจินเนทีฟ** เขียนด้วย C++ และมีตั้งแต่ 2.5 ให้บริการคำขอเอง Python ยังคงดูแลการตั้งค่าและการตัดสินใจด้านความปลอดภัย ส่วนเอนจินเนทีฟจะระบุเองว่าคำขอใดไม่ตรงกับกฎ WAF ข้อใด
- **ด้วยเอนจินเนทีฟ ไม่เปิด WAF** omega-serv ให้บริการไฟล์ขนาดเล็กได้ราว **0.7 ของ nginx** บนทั้งสามเครื่อง จึงอยู่**หน้า Apache และ Caddy แต่ตามหลัง nginx และ lighttpd**
- **ด้วยเอนจิน Python** omega-serv ตามหลังเซิร์ฟเวอร์อื่นทั้งหมดอยู่มาก: **3–11 % ของความเร็ว nginx**
- **เมื่อเปิด WAF** omega-serv ตรวจสอบทุกคำขอ ซึ่งเซิร์ฟเวอร์อื่นที่วัดไม่ได้ทำ ด้วยเอนจินเนทีฟ จะได้ **0.53–0.56** ของ nginx (ไม่มี WAF) บนเครื่อง A และ B และ 1.07 บนเครื่อง C (4 คอร์เทียบกับ 2): WAF ทำให้สูญเสียทรูพุตเพียง 5–22 % และยังอยู่หน้า Apache และ Caddy ที่วัดโดยไม่มี WAF
- **ไฟล์ขนาดกลาง (100 KB)**: เป็นจุดอ่อนปัจจุบันของเอนจินเนทีฟ ได้ **0.3–0.6** ของ nginx ตามหลัง Apache
- **ไฟล์ขนาดใหญ่ (5 MB)**: nginx, lighttpd, Apache และ omega-serv เนทีฟ ได้ทรูพุตในระดับเดียวกัน Caddy ช้ากว่าอย่างเห็นได้ชัดบนเครื่องที่เร็วที่สุด
- **หน่วยความจำ**: lighttpd (1 MB), nginx (4–5 MB) และ Apache (4–9 MB) ประหยัดมาก omega-serv ใช้ **30–65 MB** ตามโหมด Caddy ใช้ **50–67 MB**
- **สิ่งที่ omega-serv มีเพิ่ม**: การดูแลระบบทั้งหมดในอินเทอร์เฟซเทอร์มินัล 17 ภาษา; WAF และการป้องกันเชิงรุกในตัว; ขีดจำกัดความปลอดภัยที่แม่นยำเมื่อใช้หลายโปรเซส; นำเข้าสคริปต์ mod_magnet ของ lighttpd; จัดการหลายอินสแตนซ์
- **สิ่งที่ไม่มี**: HTTP/2 และ HTTP/3, การบีบอัดแบบทันที, การค้นหาบริการ Docker/Kubernetes, ไคลเอนต์ ACME ในตัว (ใช้ Certbot), ระบบนิเวศของโมดูล

## 2. วิธีอ่านการเปรียบเทียบนี้

มีแนวคิดบางอย่างที่ปรากฏตลอดเอกสาร

- **คำขอต่อวินาที (req/s)**: จำนวนไฟล์ที่เซิร์ฟเวอร์ส่งได้ในหนึ่งวินาที ยิ่งสูงยิ่งดี
- **ระยะห่างจาก nginx**: ค่าสัมบูรณ์ขึ้นกับเครื่องมาก บนเครื่องทั้งสามของเรา nginx ได้ตั้งแต่ 22 000 ถึง 440 000 req/s สิ่งที่คงที่คือ**อัตราส่วนระหว่างเซิร์ฟเวอร์** ตารางจึงแสดงอัตราส่วนเทียบกับ nginx ที่วัดในรอบเดียวกันไว้ข้างแต่ละค่า: **1.00 = เร็วเท่า nginx**, 0.50 = ช้าลงครึ่งหนึ่ง, 1.50 = เร็วกว่าหนึ่งเท่าครึ่ง
- **ความหน่วง p99**: เวลาตอบสนองที่คำขอ 99 % ไม่เกิน แสดงให้เห็น “ช่วงเวลาแย่ ๆ” ที่ค่าเฉลี่ยซ่อนไว้
- **PSS (*Proportional Set Size*)**: หน่วยความจำที่โปรเซสทั้งหมดของเซิร์ฟเวอร์ใช้จริง หน้าที่หลายโปรเซสใช้ร่วมกันจะนับเพียงครั้งเดียว
- **โปรเซสและคอร์**: เซิร์ฟเวอร์ใช้หลายคอร์ของโปรเซสเซอร์ได้ แต่ละตัวทำในแบบของตน nginx, lighttpd, Apache และ omega-serv ในโหมด Python เปิดหลายโปรเซส Caddy ซึ่งเขียนด้วย Go กระจายงานไปยังคอร์ต่าง ๆ เอนจินเนทีฟของ omega-serv เปิดหนึ่งเธรดต่อคอร์ที่มี เพื่อให้เปรียบเทียบอย่างยุติธรรม เราให้แต่ละเซิร์ฟเวอร์ใช้**คอร์ชุดเดียวกัน**
- **WAF (*Web Application Firewall*)**: ตัวกรองที่ตรวจสอบทุกคำขอเพื่อบล็อกการโจมตี (การแทรกโค้ด, สแกนเนอร์…) omega-serv มีในตัว เซิร์ฟเวอร์อื่นมีได้ในรูปโมดูล (ModSecurity, Coraza) แต่**วัดโดยไม่มีมัน** ด้วยการตั้งค่าพื้นฐาน

**สิ่งที่ควรทำ**: เปรียบเทียบอัตราส่วน ไม่ใช่ค่าสัมบูรณ์ และตรวจสอบเสมอว่าเปิด WAF หรือไม่

### ขั้นตอน

- **แยกโปรเซสเซอร์**: เซิร์ฟเวอร์และไคลเอนต์ถูกผูกกับคอร์ต่างกัน (ตารางด้านบน) ไคลเอนต์ไม่แย่งเวลาของเซิร์ฟเวอร์ และทุกเซิร์ฟเวอร์ได้ทรัพยากรเท่ากันทุกประการ
- **ไฟล์เดียวกันสำหรับทุกตัว**: `small.html` (1 KB), `medium.png` (100 KB) และ `large.bin` (5 MB) ให้บริการจากโฟลเดอร์เดียวกัน
- **เปิดบันทึกการเข้าถึงทุกตัว** เพราะเซิร์ฟเวอร์ที่ใช้งานจริงย่อมบันทึก log
- **HTTP/1.1 ไม่เข้ารหัส การเชื่อมต่อคงอยู่ (keep-alive)** ความพร้อมกัน 32 การเชื่อมต่อสำหรับไฟล์ 1 KB และ 100 KB และ 8 สำหรับไฟล์ 5 MB
- **ระยะเวลา**: 10 วินาทีต่อไฟล์และต่อการตั้งค่า
- **การทำซ้ำ**: 3 รอบเต็มแบบสลับกัน (ทุกการตั้งค่าในรอบที่ 1 แล้วทุกการตั้งค่าในรอบที่ 2 เป็นต้น) ตารางแสดง**ค่ามัธยฐาน**ของสามรอบ ความต่างระหว่างรอบส่วนใหญ่ต่ำกว่า 5 %
- **หน่วยความจำ**: PSS ของโปรเซสทั้งหมดของเซิร์ฟเวอร์ บันทึกขณะว่างแล้วบันทึกหลังโหลด
- **การตั้งค่า**:
  - nginx, lighttpd, Apache และ Caddy ใช้การตั้งค่าพื้นฐาน: ไฟล์สแตติกและบันทึกการเข้าถึง;
  - omega-serv ใช้โปรไฟล์ `standard` ปิด WAF แล้วเปิดพร้อมกฎทั้งหมดที่ให้มา (ไม่จำกัดอัตรา)
- **จำนวนโปรเซส**: แต่ละเซิร์ฟเวอร์วัดด้วย 1 แล้ว 2 โปรเซส: nginx `worker_processes`, lighttpd `server.max-worker`, Apache `StartServers`/`ServerLimit`, Caddy `GOMAXPROCS`, omega-serv `server.workers` สำหรับเอนจินเนทีฟของ omega-serv `server.workers` นับโปรเซสความปลอดภัย Python ส่วนเอนจินเนทีฟเองใช้คอร์ทั้งหมดที่ได้รับเสมอ
- **ไม่มีข้อผิดพลาดเลย**: ทุกการตอบกลับของทุกการวัดเป็น 200

### ข้อจำกัดที่ควรรู้

- **เราเปรียบเทียบอัตราส่วน** ค่าสัมบูรณ์บนฮาร์ดแวร์ของคุณหรือบนเซิร์ฟเวอร์เฉพาะจะต่างออกไป
- **อินเทอร์เฟซลูปแบ็ก (127.0.0.1)**: การวัดไม่ผ่านเครือข่ายจริง บนเครือข่ายจริง ทรูพุตของไฟล์ใหญ่แทบจะถูกจำกัดด้วยลิงก์เสมอ ไม่ใช่เซิร์ฟเวอร์ ทรูพุตหลายสิบ GB/s บนเครื่อง C เป็นไปได้เฉพาะบนลูปแบ็ก
- **ไม่มี TLS** ในการวัดเหล่านี้
- **เครื่อง A**: บริการ omega-serv ที่ใช้งานจริงของเครื่องนี้ทำงานอยู่เบื้องหลัง โดยไม่ได้รับทราฟฟิก
- **เครื่อง C**: โปรเซสเซอร์แบบไฮบริด (คอร์ Zen 5 และ Zen 5c) เซิร์ฟเวอร์ได้ 4 คอร์ที่เร็ว ไคลเอนต์ได้อีก 6 คอร์ที่เหลือ
- **การตั้งค่าพื้นฐาน**: ไม่มีเซิร์ฟเวอร์ใดถูกปรับแต่ง ผู้ดูแลที่มีประสบการณ์คงรีดประสิทธิภาพจากแต่ละตัวได้มากกว่านี้ รวมถึง omega-serv
- **ข้อมูลดิบ**: [`docs/benchmarks/`](../../benchmarks/) (หนึ่งไฟล์ต่อเครื่อง)

## 4. ประสิทธิภาพ: omega-serv เทียบกับ nginx, lighttpd, Apache และ Caddy

ในทุกตาราง ค่าอ้างอิงคือ **nginx ที่ 2 โปรเซส** (= 1.00) ซึ่งวัดในรอบเดียวกันบนเครื่องเดียวกัน บนเครื่อง A และ B นี่คือการตั้งค่าที่ใช้คอร์ทั้งหมดที่จัดให้เซิร์ฟเวอร์

### ไฟล์ขนาดเล็ก (1 KB): คำขอต่อวินาที

| เซิร์ฟเวอร์ | เครื่อง A | เครื่อง B | เครื่อง C |

### ข้อสรุป

- **เอนจินเนทีฟเปลี่ยนตำแหน่งของ omega-serv**
  - กับไฟล์ขนาดเล็ก จากเดิม 0.03–0.11 ของ nginx (เอนจิน Python) ขึ้นมาเป็นราว **0.7 ของ nginx** บนทุกเครื่อง
  - อยู่หน้า Apache และ Caddy และตามหลัง nginx และ lighttpd ซึ่งยังเร็วที่สุด
  - ความหน่วง p99 ใกล้เคียงกับ nginx
- **lighttpd เร็วที่สุดกับไฟล์ขนาดเล็กและกลาง** บนทั้งสามเครื่อง และประหยัดหน่วยความจำที่สุด อย่างไรก็ตาม เอกสารของมันไม่แนะนำ `server.max-worker` (หลายโปรเซส) ซึ่งเราใช้เพื่อเปรียบเทียบที่จำนวนโปรเซสเท่ากัน
- **ไฟล์ขนาดกลางเป็นจุดอ่อนปัจจุบันของเอนจินเนทีฟ**: 0.28–0.61 ของ nginx ตามหลัง Apache และไม่ดีขึ้นเมื่อเพิ่มคอร์ นี่เป็นแนวทางการปรับปรุงที่ระบุไว้แล้ว
- **กับไฟล์ขนาดใหญ่** เซิร์ฟเวอร์ต่าง ๆ ใกล้เคียงกัน เพราะเคอร์เนลของระบบเป็นผู้คัดลอกข้อมูล (`sendfile`) ข้อยกเว้นคือ Caddy บนเครื่อง C: เราไม่ได้พยายามปรับแต่งการตั้งค่าพื้นฐานของมัน
- **WAF มีต้นทุนต่ำสำหรับเอนจินเนทีฟ แต่ต้องอ่านอย่างตรงไปตรงมา**
  - เอนจินเนทีฟตรวจกฎ WAF เอง: คำขอที่ไม่ตรงกับกฎใดจะได้รับบริการโดยไม่ผ่าน Python เมื่อมีข้อสงสัยแม้เพียงเล็กน้อย (ตรงกับกฎ, ข้อความที่ไม่ใช่ ASCII, แหล่งที่ Active Defense เฝ้าดู, โซนยืนยันตัวตน…) Python จะเป็นผู้ตัดสิน เมื่อเปิด WAF เอนจินเนทีฟจึงรักษาทรูพุตไว้ได้ 78–95 % กับไฟล์ขนาดเล็ก และ 93–99 % กับไฟล์ 100 KB ก่อนการปรับแต่งนี้ ทรูพุตของมันถูกหารด้วย 4 ถึง 7
  - การจำกัดอัตราถูกนับโดยเอนจินเนทีฟ: การเปิดใช้ไม่เปลี่ยนตัวเลขเหล่านี้ (เครื่อง A: 11 391 req/s เมื่อเปิด, 11 330 เมื่อปิด) หากเปิด magnet ทุกคำขอยังคงผ่าน Python และต้นทุนกลับไปเหมือนเดิม
  - omega-serv ที่มี WAF ยังอยู่หน้า Apache และ Caddy ที่**ไม่มี** WAF
  - nginx, lighttpd, Apache และ Caddy วัดโดย**ไม่มี** WAF WAF ที่เพิ่มให้เซิร์ฟเวอร์เหล่านี้ (ModSecurity, Coraza) ก็มีต้นทุนเช่นกัน ซึ่งเราไม่ได้วัด การเปรียบเทียบ “มี WAF” จึงไม่เท่าเทียม และเราไม่ได้อ้างว่า omega-serv จะเร็วกว่าเซิร์ฟเวอร์อื่นที่มี WAF
- **โปรเซสความปลอดภัยหลายตัวไม่ช่วยทราฟฟิกปกติอีกต่อไป**: ทราฟฟิกปกติไม่ผ่านพวกมันแล้ว และทรูพุตที่ 2 โปรเซสยังเท่าเดิม (−2 ถึง −4 % อยู่ในสัญญาณรบกวนของการวัด) พวกมันมีประโยชน์เฉพาะเมื่อมีคำขอจำนวนมากผ่าน Python (เปิด magnet, ถูกโจมตี): ตามการวัดก่อนการปรับแต่ง ซึ่งทุกคำขอผ่านพวกมัน 2 โปรเซสความปลอดภัยเพิ่มทรูพุตที่มี WAF ได้ 1.5–1.7 เท่าบน 4 คอร์ แต่เพิ่มเพียง 5–12 % บน 2 คอร์
- **เอนจิน Python ขยายตามจำนวนโปรเซส** (×1.6–×2 ที่ 2 โปรเซส ราว ×3.5 ที่ 4) แต่ยังอยู่ที่ 5–11 % ของ nginx
- **หน่วยความจำ**: omega-serv ใช้มากกว่า nginx, lighttpd หรือ Apache หลายสิบ MB ส่วนใหญ่เพราะ Python และใกล้เคียงกับ Caddy ด้วยเอนจินเนทีฟที่ไม่มี WAF หน่วยความจำแทบไม่เปลี่ยนระหว่างโหลด
- **เพื่อให้เห็นภาพตัวเลขเหล่านี้**: แม้กรณีที่ช้าที่สุด คือเอนจิน Python ที่มี WAF บนเครื่อง B (564 req/s) ก็เกือบ 50 ล้านคำขอต่อวัน ซึ่งเกินความต้องการของเว็บไซต์ส่วนตัว บริการภายใน หรือห้องแล็บไปมาก ความเร็วจะเป็นตัวตัดสินจริง ๆ เฉพาะเว็บไซต์ที่มีทราฟฟิกสูง

วัดเมื่อ 26 ตุลาคม 2026 บนเครื่อง A และยังไม่ได้วัดใหม่: ต้นทุนของการบันทึกภัยคุกคามหนึ่งครั้งใน Active Defense สำหรับแต่ละคำขอที่น่าสงสัย วัดบนดิสก์ (ext4) ด้วยการบันทึก 2 000 ครั้ง

| การวัด | 1.0.0 | 2.0.0 |
|---|---:|---:|
| มัธยฐาน | 2.84 ms | 0.23 ms |
| p99 | 11.6 ms | 2.3 ms |
| สูงสุด | 18–20 ms | 37–46 ms |

ค่ามัธยฐานลดลง 12 เท่า ในทางกลับกัน ค่าสูงสุดใน 2.0 สูงกว่า: มีจุดพีคเดี่ยว ๆ ไม่กี่จุด ซึ่งเกิดจากการเขียน journal ของ SQLite ลงดิสก์เป็นระยะ

### ข้อสรุป

- **จาก 1.0 เป็น 2.0** ความก้าวหน้าอยู่ที่หน่วยความจำและไฟล์ใหญ่ ไม่ใช่ความเร็วของหน้าเล็ก:
  - หน่วยความจำหลังโหลดลดจาก 73–98 MB เหลือ 30–32 MB;
  - ระหว่างการดาวน์โหลดไฟล์ใหญ่ ลดจากมากกว่า 1.8 GB เหลือราว 40 MB และเซิร์ฟเวอร์ยังตอบสนองได้ (ไม่กี่มิลลิวินาที แทนที่จะเกือบ 2 วินาที);
  - ทรูพุตของไฟล์ใหญ่เพิ่มขึ้น 2.7–3.9 เท่า;
  - 2.0 เพิ่มการใช้หลายโปรเซส ซึ่งเพิ่มทรูพุตของหน้าเล็กได้ 25 % ถึงเกือบ 100 % ขึ้นกับเครื่อง
  1.0 โหลดไฟล์ทั้งไฟล์เข้าหน่วยความจำก่อนส่ง 2.0 ส่งเป็นบล็อกหรือมอบให้เคอร์เนลของระบบ
- **จาก 2.0 เป็น 2.5 เอนจิน Python ไม่เปลี่ยนความเร็ว**: ความต่างต่ำกว่า 4 % บนเครื่อง B และ C และอยู่ในสัญญาณรบกวนของการวัดบนเครื่อง A (−13 % ถึง +9 %) ซึ่งไวต่อโหลดเบื้องหลังที่สุด ประโยชน์ทั้งหมดของ 2.5 มาจาก**เอนจินเนทีฟ**: ราว ×10–×27 กับไฟล์ขนาดเล็กเมื่อเทียบกับเอนจิน Python และความหน่วงลดลง 5 ถึง 15 เท่า
- **เอนจินเนทีฟใช้หน่วยความจำขณะว่างมากกว่าเอนจิน Python ราว 5 MB** (PSS): นี่คือราคาของโปรแกรมตัวที่สอง เมื่อมี WAF จะใช้เพิ่มอีกราว 8 MB: นี่คือกฎที่โหลดเข้าเอนจินเนทีฟ

### สิ่งที่ควรรู้เกี่ยวกับเอนจินเนทีฟ

- เป็น**ตัวเลือก**: เอนจิน Python ยังเป็นเอนจินเริ่มต้นและเอนจินสำรอง
- ให้บริการเนื้อหาสแตติก การเปลี่ยนเส้นทาง การเขียนใหม่ alias แคช หน้าข้อผิดพลาด ส่วนหัวความปลอดภัย และ TLS เอง
- ตรวจกฎ WAF เอง และให้บริการคำขอที่ไม่ตรงกับกฎใดเอง คำขออื่นทั้งหมด (WAF ตรงกับกฎหรือสงสัย, Active Defense, การยืนยันตัวตน) Python เป็นผู้ตัดสิน ด้วยการตรวจและบันทึกเดียวกันทุกประการ การตรวจที่ตั้งค่าได้ยังคงส่งคำขอที่สะอาดหนึ่งในทุก N คำขอให้ Python เพื่อยืนยันว่าทั้งสองให้คำตัดสินเดียวกัน
- การแสดงรายการไดเรกทอรีและหน้าภายในจะขอจาก Python ส่วน reverse proxy, FastCGI, การอัปโหลดไฟล์ และ WebSocket จะมอบให้ Python ตลอดการเชื่อมต่อ ฟีเจอร์เหล่านี้จึงคงความเร็วของเอนจิน Python
- เมื่อใช้ TLS โดยตรง เอนจินเนทีฟไม่รองรับ reverse proxy, FastCGI และการอัปโหลดไฟล์: เอนจิน Python จะให้บริการแทน และอินเทอร์เฟซจะแสดงให้เห็น
- ต้องใช้ glibc 2.38 ขึ้นไปและ OpenSSL 3 หากเริ่มทำงานไม่ได้ การติดตั้งจะคอมไพล์ใหม่ในเครื่อง และหากทำไม่ได้ omega-serv จะใช้เอนจิน Python ต่อไป

## 7. การดูแลระบบและความสะดวก

| เซิร์ฟเวอร์ | วิธีดูแลหลัก | อินเทอร์เฟซ | โหลดใหม่โดยไม่ขัดจังหวะ |
|---|---|---|---|
| nginx | ไฟล์การตั้งค่า | ไม่มี (แดชบอร์ด: NGINX Plus เชิงพาณิชย์) | ✅ `nginx -s reload` |
| lighttpd | ไฟล์การตั้งค่า | ไม่มี (mod_status อ่านอย่างเดียว) | ✅ รีสตาร์ตแบบนุ่มนวล |
| Caddy | Caddyfile หรือ JSON | REST API สำหรับดูแลระบบ | ✅ ผ่าน API |
| Apache | ไฟล์การตั้งค่าและ `.htaccess` | ไม่มี (mod_status อ่านอย่างเดียว) | ✅ `graceful` |

ในทางปฏิบัติ omega-serv จัดการการตั้งค่า ความปลอดภัย log บริการของระบบ การสำรองข้อมูล และอินสแตนซ์ จากอินเทอร์เฟซเดียว การตั้งค่าแต่ละรายการมีคำอธิบายและถูกตรวจสอบก่อนบันทึก กับเซิร์ฟเวอร์อื่น ต้องแก้ไฟล์ข้อความแล้วใช้เครื่องมือแยกต่างหาก (Certbot, fail2ban, logrotate, ModSecurity, เครื่องมือเฝ้าระวัง…)

ในทางกลับกัน แนวทาง “ไฟล์การตั้งค่า” ของ nginx, Apache และ Caddy ทำระบบอัตโนมัติได้ดีมาก (Ansible, คอนเทนเนอร์, การควบคุมเวอร์ชัน) omega-serv มี CLI สำหรับสคริปต์ แต่ระบบนิเวศด้านอัตโนมัติยังจำกัด

## 8. สิ่งที่ omega-serv มีเพิ่ม

ส่วนนี้มีเฉพาะสิ่งที่ไม่มีเซิร์ฟเวอร์ใดในการเปรียบเทียบให้ได้ในรูปแบบนี้ โดยไม่ต้องใช้โมดูลบุคคลที่สามหรือเครื่องมือภายนอก

1. **การดูแลระบบทั้งหมดในอินเทอร์เฟซเทอร์มินัล**
   - อินเทอร์เฟซครอบคลุมเซิร์ฟเวอร์ทั้งหมด: เว็บไซต์ ความปลอดภัย log บริการ การสำรองข้อมูล และอินสแตนซ์
   - ใช้ได้ด้วยคีย์บอร์ดและเมาส์ บนเซิร์ฟเวอร์ที่ไม่มีสภาพแวดล้อมกราฟิก แม้ผ่าน SSH
   - มี 17 ภาษาและอธิบายการตั้งค่าแต่ละรายการ
   - เซิร์ฟเวอร์อื่นไม่มีอินเทอร์เฟซดูแลระบบ (nginx, lighttpd, Apache) หรือมีเพียง API (Caddy) หรือแดชบอร์ดอ่านอย่างเดียว (Traefik)
2. **ความปลอดภัยเชิงรุกในตัว โดยไม่ต้องประกอบโมดูล**
   - WAF ประกอบด้วยลายเซ็น รายการพาธที่แก้ไขได้ การนับการทำซ้ำ รายการบล็อกที่มีวันหมดอายุ ชื่อเสียง และโหมดสังเกตการณ์
   - Active Defense เพิ่มเหยื่อล่อ โหมดสงคราม การติดตามเหตุการณ์ การส่งออกตัวบ่งชี้การบุกรุก และการจำลองแบบไม่มีผลจริง
   - RIPOSTE ตอบสนองตามเวลา: จดจำที่อยู่ที่กลับมาซ้ำและใช้การตอบสนองแบบไล่ระดับกับที่อยู่เหล่านั้น การแบนที่นานขึ้นเรื่อย ๆ (ค่าเริ่มต้น 1 ชม., 6 ชม., 24 ชม., 7 วัน) ในเครื่องผ่านรายการบล็อก หรือระดับเครือข่ายผ่าน fail2ban (omega-jail) หรือเหยื่อล่อที่ยืดเวลา แต่ละนโยบายวัดได้จาก log จริงและจำลองได้ก่อนเปิดใช้; ทุกการกระทำมองเห็นได้และยกเลิกได้ พร้อมการหยุดฉุกเฉิน
   - กับเซิร์ฟเวอร์อื่น ฟีเจอร์เหล่านี้ต้องประกอบ ModSecurity หรือ Coraza ชุดกฎ และ fail2ban เข้าด้วยกัน
3. **ขีดจำกัดความปลอดภัยที่แม่นยำเมื่อใช้หลายโปรเซส**
   - เมื่อใช้หลายโปรเซส การจำกัดอัตราและการนับการทำซ้ำของ WAF ใช้ร่วมกันในหน่วยความจำ ผู้โจมตีจึงไม่สามารถคูณขีดจำกัดของตนด้วยจำนวนโปรเซสได้
   - lighttpd บันทึกกรณีตรงข้ามไว้: เมื่อใช้ `server.max-worker` `mod_evasive` และ `mod_status` จะนับแยกในแต่ละโปรเซส
   - nginx ก็ใช้ตัวนับร่วมกัน (โซน `limit_req`) แต่ไม่มี WAF ในตัว
4. **สองเอนจิน พฤติกรรมเดียว** เอนจินเนทีฟและเอนจิน Python ให้การตอบกลับและ log เดียวกัน ซึ่งตรวจสอบโดยอัตโนมัติบนชุดทดสอบเปรียบเทียบ เครื่องมือที่อ่าน log (เช่น fail2ban) จะไม่เห็นความแตกต่างใด ๆ
5. **นำเข้าสคริปต์ mod_magnet ของ lighttpd**
   - สคริปต์ป้องกันภาษา Lua ที่เขียนไว้แล้วสำหรับ lighttpd นำเข้าได้โดยไม่ต้องเขียนใหม่
   - เสริมการป้องกันในตัวโดยไม่สามารถทำให้อ่อนลงได้ และตรวจความเข้ากันได้ก่อนเปิดใช้
6. **การจัดการหลายอินสแตนซ์**
   - ทะเบียนเก็บรายการอินสแตนซ์ทั้งหมด และอินเทอร์เฟซสลับไปมาระหว่างกันได้
   - ยังถอนการติดตั้งอินสแตนซ์ได้ทั้งหมดด้วย
7. **การตรวจสอบความปลอดภัยของการตั้งค่า**: คำสั่ง `audit security` ให้ข้อมูลเท่านั้น ไม่บล็อกใด ๆ และคืนรหัสออกที่ใช้ในสคริปต์ได้
8. **แหล่ง log ระยะไกล**
   - อินเทอร์เฟซดึง log ของเซิร์ฟเวอร์อื่นผ่าน SSH ตามต้องการ โดยไม่เก็บรหัสผ่าน
   - อ่านได้ใน lnav โดยรวมกับ log ในเครื่อง
9. **การเสริมความแข็งแกร่ง HTTP ที่ปิดไม่ได้** ทำงานตั้งแต่ติดตั้ง ไม่ว่าโปรไฟล์หรือเอนจินใด:
   - ตรวจส่วนหัว Host อย่างเข้มงวด;
   - ปฏิเสธความกำกวมระหว่าง Content-Length / Transfer-Encoding;
   - ส่วนหัวความปลอดภัยและ CSP ในการตอบกลับของเว็บไซต์ รวมถึงหน้าข้อผิดพลาด;
   - อ่าน X-Forwarded-For อย่างปลอดภัย;
   - ปฏิเสธการเริ่มทำงานด้วยสิทธิ์ root

## 9. สิ่งที่เซิร์ฟเวอร์อื่นทำได้ดีกว่า

- **ทรูพุต**: lighttpd และ nginx ยังเร็วที่สุดกับไฟล์ขนาดเล็กและกลาง บนทั้งสามเครื่อง แม้ด้วยเอนจินเนทีฟ omega-serv ได้ราว 0.7 ของ nginx และ 0.5 ของ lighttpd กับไฟล์ขนาดเล็ก และ 0.3–0.6 ของ nginx กับไฟล์ 100 KB สำหรับเว็บไซต์ที่มีทราฟฟิกสูง API สาธารณะ หรือ CDN ควรเลือกพวกมัน
- **ไฟล์ขนาดกลาง**: Apache ให้บริการไฟล์ 100 KB ได้เร็วกว่าเอนจินเนทีฟของ omega-serv บนทั้งสามเครื่อง
- **หน่วยความจำ**: lighttpd (1 MB), nginx (4–5 MB) และ Apache (4–9 MB) เหมาะกับเครื่องที่ทรัพยากรจำกัดมาก (ระบบฝังตัว, คอนเทนเนอร์ขนาดเล็ก) omega-serv ต้องใช้ 30–65
- **ต้นทุนของความปลอดภัย**: WAF ยังมีต้นทุน ด้วยเอนจินเนทีฟ มันทำให้สูญเสียทรูพุต 5–22 % กับไฟล์ขนาดเล็ก รวมการจำกัดอัตรา: omega-serv ที่มี WAF ได้ 0.53–0.56 ของ nginx ที่ไม่มี WAF บนเครื่อง A และ B คำขอที่น่าสงสัยหรือไม่แน่ชัด (ตรงกับกฎ, ข้อความที่ไม่ใช่ ASCII, แหล่งที่ Active Defense เฝ้าดู) จะผ่าน Python เสมอและได้รับบริการด้วยความเร็วของเอนจิน Python เมื่อเปิด magnet ทุกคำขอผ่าน Python และ WAF จะหารทรูพุตของเอนจินเนทีฟด้วย 4 ถึง 7 เหมือนก่อนการปรับแต่ง
- **โปรโตคอล**: HTTP/2 มีในเซิร์ฟเวอร์อื่นทุกตัว HTTP/3 มีใน nginx, Caddy และ Traefik omega-serv รองรับเพียง HTTP/1.1
- **HTTPS อัตโนมัติ**: Caddy และ Traefik เปิดเป็นค่าเริ่มต้น nginx (`ngx_http_acme_module`) และ Apache (`mod_md`) ผ่านโมดูลทางการ omega-serv มอบให้ Certbot พร้อมตัวช่วยและการต่ออายุตามกำหนด
- **สภาพแวดล้อมคอนเทนเนอร์**: การค้นหาบริการอัตโนมัติของ Traefik (Docker, Kubernetes) ไม่มีสิ่งเทียบเท่าใน omega-serv
- **ระบบนิเวศและความสุกงอม**: nginx และ Apache มีโมดูล คู่มือ และการผสานรวมนับพัน และมีประสบการณ์ใช้งานจริงหลายสิบปี Caddy มีระบบโมดูล Go omega-serv เป็นโครงการใหม่ที่ดูแลโดยคนคนเดียว และเอนจินเนทีฟยังใหม่มาก
- **การบีบอัดแบบทันที**: omega-serv ให้บริการเฉพาะไฟล์ที่บีบอัดไว้แล้ว

## 10. เซิร์ฟเวอร์ไหนสำหรับความต้องการไหน

| ความต้องการ | ตัวเลือกที่แนะนำ |
|---|---|
| เว็บไซต์ทราฟฟิกสูง, API สาธารณะ, CDN, ทรูพุตสูงสุด | **nginx** หรือ **lighttpd** |
| เครื่องที่ทรัพยากรจำกัดมาก, ระบบฝังตัว, ไฟล์สแตติก | **lighttpd** |
| เริ่มเร็วพร้อม HTTPS อัตโนมัติ การตั้งค่าสั้น | **Caddy** |
| แอปพลิเคชัน PHP รุ่นเก่า, `.htaccess`, โฮสติ้งร่วม | **Apache** |
| Docker, Kubernetes, ไมโครเซอร์วิส | **Traefik** |
| เว็บไซต์ขนาดเล็กหรือกลาง, บริการภายใน, ห้องแล็บ, VPN, ดูแลระบบโดยไม่ต้องแก้ไฟล์ | **omega-serv** (เอนจินเนทีฟถ้าเป็นไปได้) |
| เซิร์ฟเวอร์ที่เปิดสู่อินเทอร์เน็ต ซึ่งต้องการเห็นและควบคุมความปลอดภัย (WAF, การแบนแบบไล่ระดับ, เหยื่อล่อ) จากอินเทอร์เฟซเดียว | **omega-serv** |
| Reverse proxy ภายในพร้อมการกระจายโหลด การตรวจ และแคช จัดการจากอินเทอร์เฟซ | **omega-serv** |
| เรียนรู้การเสริมความแข็งแกร่ง HTTP และการป้องกันเชิงรุก | **omega-serv** |

เครื่องมือเหล่านี้ยังใช้ร่วมกันได้ ตัวอย่างเช่น:
- nginx หรือ Traefik อยู่ด้านหน้ารับอินเทอร์เน็ต และ omega-serv อยู่ด้านหลังสำหรับบริการภายใน ความปลอดภัย และการดูแลระบบ;
- omega-serv เป็น reverse proxy ภายในหน้าเซิร์ฟเวอร์แอปพลิเคชันหลายเครื่อง

## 11. การทำซ้ำการวัด

เครื่องมือมาพร้อมกับคลังโค้ด ใน `tools/bench/` ต้องติดตั้ง nginx, lighttpd, Apache, Caddy และ oha, สภาพแวดล้อมพัฒนาของ omega-serv (`.venv`) และสำหรับเอนจินเนทีฟ ไบนารีที่คอมไพล์ไว้ใน `native/omega-http-core/build-release`

```sh
# 1. เตรียมโฟลเดอร์การวัด (ไฟล์ทดสอบ, การตั้งค่า, omega-serv 1.0, 2.0 และเวอร์ชันปัจจุบัน)
tools/bench/compare/setup.sh /path/measures omega-serv-1.0.0.tar.gz omega-serv-2.0.0.tar.gz

# 2. 21 การตั้งค่า, ทำซ้ำสลับกัน 3 รอบ (40–60 นาที)
#    SRV_CPUS / CLI_CPUS: คอร์ของเซิร์ฟเวอร์และไคลเอนต์ (lscpu -e แสดงโครงสร้าง)
SRV_CPUS=0,1 CLI_CPUS=2,3 tools/bench/compare/campaign.sh /path/measures > results.txt

# 3. ค่ามัธยฐาน
python3 tools/bench/compare/summarize.py results.txt

# รายการการตั้งค่าอื่น เช่น 4 โปรเซส
CONFIGS="nginx-4 lighttpd-4 caddy-4 apache-4 omega-v2-1-0-native omega-v2-4-1-native" \
  tools/bench/compare/campaign.sh /path/measures > results-4.txt

# การดาวน์โหลดไฟล์ใหญ่ (หน่วยความจำและการตอบสนอง): เวอร์ชันปัจจุบัน เอนจิน Python แล้วเนทีฟ แล้ว 1.0
.venv/bin/python tools/bench/bigfile.py
BENCH_ENGINE=native .venv/bin/python tools/bench/bigfile.py
BENCH_SRC=/path/measures/v1-archive/omega-serv/src \
BENCH_EXTRA_PATH=/path/measures/v1-archive/omega-serv/vendor/omega-lib/src \
  .venv/bin/python tools/bench/bigfile.py

# วัดเซิร์ฟเวอร์อื่นใดก็ได้ที่ทำงานอยู่แล้ว โดยไม่ต้องใช้ oha
python3 tools/bench/bench_any.py --make-files /srv/webroot-test
python3 tools/bench/bench_any.py --port 8080
```

ชื่อการตั้งค่า: `nginx-N`, `lighttpd-N`, `apache-N`, `caddy-N` (N โปรเซส หรือ N คอร์สำหรับ Caddy); `omega-vX-N-W` สำหรับ omega-serv (เวอร์ชัน `v1`, `v20` หรือ `v2` สำหรับเวอร์ชันปัจจุบัน, N โปรเซส, W = 0 ไม่มี WAF หรือ 1 มี WAF) ต่อท้ายด้วย `-native` สำหรับเอนจินเนทีฟ

หากต้องการเผยแพร่ผลของคุณเอง ให้ระบุเครื่อง เวอร์ชัน การจัดสรรคอร์ และการทำซ้ำสามรอบ
