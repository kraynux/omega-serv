# 🔒 OMEGA-SERV

**เว็บเซิร์ฟเวอร์ HTTP/1.1 แบบอิสระ พกพาได้ และเสริมความแข็งแกร่งเป็นค่าเริ่มต้น**

OMEGA-SERV ให้บริการเว็บไซต์แบบสแตติก และถ้าต้องการ ก็รัน PHP ผ่าน PHP-FPM ได้ ออกแบบมาให้เริ่มใช้งานง่าย ดูแลจากเทอร์มินัลได้สะดวก และใช้ผิดได้ยาก: การตรวจสอบโปรโตคอล HTTP ทำงานตั้งแต่เริ่มต้น ส่วนฟังก์ชันขั้นสูง — WAF, TLS, การยืนยันตัวตน, reverse proxy — ยังเป็นตัวเลือก และต้องเปิดใช้งานด้วยความตั้งใจ

**OMEGA-SERV** คือเซิร์ฟเวอร์ HTTP/1.1 ที่เขียนด้วย Python ล้วน (แกนเซิร์ฟเวอร์ใช้เฉพาะไลบรารีมาตรฐาน) ออกแบบมาเพื่อให้บริการเนื้อหาแบบสแตติก และให้บริการ PHP-FPM เป็นตัวเลือก โดยมีการเสริมความแข็งแกร่งของโปรโตคอลที่เปิดใช้งานเป็นค่าเริ่มต้น และมีโมดูลความปลอดภัย (WAF, TLS, การยืนยันตัวตน) ที่ซ้อนเพิ่มได้ตามต้องการแทนที่จะถูกบังคับใช้ เอนจินเนทีฟ C++ ที่เป็นตัวเลือกสามารถให้บริการคำขอแทนเอนจิน Python ได้ โดยมีการตรวจสอบความปลอดภัยแบบเดียวกัน มันทำงานกับเครื่องที่ตัวเองติดตั้งอยู่ ไม่ใช่กับเป้าหมายระยะไกล (กลุ่มเดียวกับ `omega-fire`) จัดโครงสร้างตาม Clean Architecture โดยมี `bootstrap/` ทำหน้าที่เป็นรากของการประกอบ (composition root)

## 1. วิสัยทัศน์และขอบเขต

ลำดับความสำคัญที่ประกาศไว้คือ **ความแข็งแรง/ความปลอดภัยของแกน HTTP มาก่อน** — WAF และ TLS เป็นโมดูลเสริมที่วางทับไว้ด้านบน ไม่เคยเป็นสิ่งที่ต้องมีก่อน เซิร์ฟเวอร์ที่ทำหลายอย่าง (ให้บริการไฟล์ อาจรวม PHP, reverse proxy...) แต่ทำได้อย่างถูกต้อง พร้อมการเสริมความแข็งแกร่งของโปรโตคอลที่ข้ามไม่ได้จริง ดีกว่าเซิร์ฟเวอร์ที่ทำสิ่งต่าง ๆ มากมายแต่ทำได้เพียงครึ่ง ๆ กลาง ๆ

### สิ่งที่ OMEGA-SERV ทำ

- ให้บริการเนื้อหาสแตติก (ไฟล์ การแสดงรายการไดเรกทอรีแบบเลือกได้ alias การเปลี่ยนเส้นทาง การเขียน URL ใหม่ แคช) พร้อมการแปลงพาธอย่างปลอดภัย (traversal, การเข้ารหัสซ้ำ, ลิงก์สัญลักษณ์) ไฟล์ขนาดใหญ่ถูกส่งเป็นบล็อกจากดิสก์ ไม่เคยโหลดทั้งไฟล์เข้าหน่วยความจำ ทุกไฟล์มี `ETag` และ `Last-Modified` (การรีโหลด = การตอบกลับ 304 ที่ว่างเปล่า) รองรับคำขอบางส่วน `Range` (ดาวน์โหลดต่อ, วิดีโอ) รูปภาพ สื่อ ฟอนต์ CSS และ JS ได้รับ `Cache-Control` เริ่มต้น ซึ่งแก้ไขได้ในหน้าจอแคช ไฟล์ข้อความที่บีบอัดไว้ล่วงหน้า: ถ้ามี `site.css.br` หรือ `site.css.gz` อยู่ข้าง `site.css` (สร้างด้วย `brotli -k site.css` หรือ `gzip -k site.css`) และเบราว์เซอร์รองรับ ไฟล์เหล่านั้นจะถูกส่งแทน โดยไม่เคยส่งฉบับที่เก่ากว่าต้นฉบับ
- เสริมความแข็งแกร่งของโปรโตคอล HTTP เป็นค่าเริ่มต้น: วิเคราะห์คำขออย่างเคร่งครัดโดยไม่มีตัวเลือกให้ปิด (ปฏิเสธความกำกวมระหว่าง `Content-Length`/`Transfer-Encoding`), รายการเมธอดที่อนุญาตอย่างชัดเจน, ตรวจสอบเฮดเดอร์ `Host`, เฮดเดอร์ความปลอดภัยและ CSP พื้นฐานบนการตอบกลับของเว็บไซต์และหน้าข้อผิดพลาดของเว็บไซต์
- ตัวเลือกเสริม: การกรองด้วย WAF (ซิกเนเจอร์, การจำกัดอัตรา, รายการบล็อก), TLS โดยตรง (ใบรับรองแบบลงนามเอง, ลงนามโดย CA ภายใน หรือสาธารณะผ่าน Let's Encrypt/Certbot พร้อมต่ออายุอัตโนมัติ), การยืนยันตัวตน HTTP Basic ตามโซน, PHP ผ่าน FastCGI/PHP-FPM, โซนอัปโหลดที่ถูกจำกัดขอบเขต
- ใช้หลายโปรเซสเซิร์ฟเวอร์ สูงสุดหนึ่งโปรเซสต่อคอร์จริงของเครื่องเมื่อใช้เอนจิน Python (หน้าจอความทนทานและขีดจำกัด) ตัวนับด้านความปลอดภัย (rate limit, การกระทำซ้ำ) ใช้ร่วมกันระหว่างโปรเซสและยังคงแม่นยำ
- ตรวจสอบการตั้งค่าของตัวเอง (`audit security`) และติดตั้งตัวเองเป็นบริการของระบบได้ (systemd/OpenRC/runit)
- CLI แบบไม่โต้ตอบที่เขียนสคริปต์ได้ตั้งแต่ต้นจนจบ **และอินเทอร์เฟซแบบโต้ตอบ (Textual)** ที่ห่อหุ้มกรณีการใช้งานเดียวกันทุกประการ อินเทอร์เฟซ **ควบคุมได้ทั้งหมดด้วยเมาส์และ/หรือคีย์บอร์ด**: ทะเบียนความสามารถ, โปรไฟล์/ตัวเลือก, การตั้งค่าโดยละเอียด (alias/การเปลี่ยนเส้นทาง/rewrite/FastCGI/dirlisting/การยืนยันตัวตน/แคช/WAF/พร็อกซีที่เชื่อถือ/reverse proxy ขาออก/TLS), การจัดการล็อก (คลัง/รายการโปรด, ตัวดู 3 แบบ — แบบง่าย/แบบคลาสสิก/lnav แบบรวม —, ดูและจัดการ IP, สถิติ, แหล่งระยะไกล SSH, หมุนเวียน/สำรอง/อัตโนมัติ/กู้คืน/ล้าง/ส่งออก, สุขภาพล็อก), บริการของระบบ, หลายอินสแตนซ์ (ทะเบียน, การสร้าง), ตรวจสอบ/จำลอง/ตรวจประเมิน, สำรองและกู้คืนการตั้งค่า, ตัวช่วยตั้งค่าครั้งแรก, การตั้งค่าแอปพลิเคชัน (ธีม, โปรไฟล์การแสดงผล, พาธของการส่งออก/ภาพหน้าจอ), คู่มือช่วยเหลือตามบริบท (เอกสารประจำแต่ละหน้าจอพร้อมตัวอย่างที่ชัดเจน, FAQ, ส่งออก HTML, ครอบคลุมครบถ้วนโดยตรวจสอบด้วยการทดสอบ), การบอกเสมอว่าต้องโหลดใหม่หรือรีสตาร์ทหลังการบันทึกแต่ละครั้ง, การตั้งค่า Active Defense ครบถ้วนโดยไม่ต้องแก้ไขไฟล์ด้วยมือ

### สิ่งที่ OMEGA-SERV ไม่ทำ

- CGI แบบดิบ (แต่รองรับ FastCGI/PHP-FPM)
- การยืนยันตัวตนแบบ TLS สองทาง (mTLS), OCSP stapling (ส่วน ACME/Let's Encrypt ผ่าน Certbot นั้นมีให้ใช้)
- แคช HTTP ที่ใช้ร่วมกันระหว่างโปรเซส
- การสแกน/ตรวจประเมินเป้าหมายระยะไกล (ใช้ `omega-check`/`omega-scan`/`omega-deep` สำหรับงานนั้น — Omega-serv ตรวจประเมินตัวเองเท่านั้น ไม่เคยตรวจบุคคลที่สาม)

### OMEGA-SERV เทียบกับเว็บเซิร์ฟเวอร์ในตลาด

ดู [การวัดและการเปรียบเทียบ](comparatif-serveurs-web.md)  
การเปรียบเทียบที่วัดผลจริงระหว่าง: [Nginx](https://nginx.org/) · [Lighttpd](https://www.lighttpd.net/) · [Caddy](https://caddyserver.com/) · [Apache](https://www.apache.org) · [Traefik](https://traefik.io/) · [Omega-Serv](https://kraynux.snake-mackarel.ts.net/omega-serv/translation/th/)

### คำเตือนการใช้งาน

Omega-serv **ปฏิเสธการเริ่มทำงานในฐานะ root** ไม่มีโมดูลความปลอดภัยใด (WAF, TLS, การยืนยันตัวตน) เปิดใช้งานเป็นค่าเริ่มต้นในโปรไฟล์ใดที่จัดให้ รวมถึง `hardened` — การเปิดใช้งานเป็นการกระทำที่ชัดเจนเสมอ (`config enable-tls`, `option enable waf`...) โปรไฟล์ `hardened` เองก็แนะนำให้ใช้ reverse proxy เมื่อเปิดสู่อินเทอร์เน็ตจริง แทนที่จะทำหน้าที่แทน reverse proxy

### สิ่งที่ต้องมี

- Python 3.10+
- `openssl` (ไฟล์โปรแกรม ไม่ใช่ไลบรารี Python) สำหรับทุกอย่างที่เกี่ยวกับใบรับรอง TLS — ฟังก์ชันอื่นทำงานได้โดยไม่ต้องมี
- เอนจินเนทีฟ (ตัวเลือก มีให้แบบคอมไพล์แล้วสำหรับ x86_64): ต้องใช้ glibc 2.38 ขึ้นไปและ OpenSSL 3 ซึ่งเป็นไลบรารีระบบสองตัวที่ Python ใช้อยู่แล้ว หากมันเริ่มทำงานไม่ได้ `install.sh` จะคอมไพล์ใหม่บนเครื่องเมื่อมี cmake, คอมไพเลอร์ C++20 และเฮดเดอร์ของ OpenSSL มิฉะนั้น omega-serv จะทำงานด้วยเอนจิน Python

## 2. การติดตั้ง

```bash
tar -xzf omega-serv-2.6.1.tar.gz
cd omega-serv/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. สร้างสภาพแวดล้อมเสมือน `.venv` ถ้ายังไม่มี
2. ติดตั้งแพ็กเกจ (`pip install -e .`) — **ไม่มี dependency ภายนอก** สำหรับแกนของเซิร์ฟเวอร์
3. ทำให้ `omega-serv.sh` และ `install.sh` เรียกใช้งานได้
4. ตรวจว่าเอนจินเนทีฟที่ให้มาเริ่มทำงานบนเครื่องได้หรือไม่ และคอมไพล์ใหม่บนเครื่องหากจำเป็นและทำได้ — โดยไม่ขัดขวางการติดตั้งเลย
5. เพิ่ม alias `serv` ลงใน `~/.bashrc` และ `~/.zshrc` (ไม่ซ้ำถ้ามีอยู่แล้ว)

### การอัปเดต

ถ้ามี `omega-serv/` อยู่แล้ว (การติดตั้งครั้งก่อน) **ห้ามรัน `tar` จากภายในโฟลเดอร์นี้เด็ดขาด**: มันจะพยายามสร้าง `omega-serv/omega-serv/` ซ้อนกันและล้มเหลว ต่างจาก omega-fire ตรงที่ `install.sh` ไม่เคยแตะสิทธิ์ของโฟลเดอร์ (ไม่มีขั้นตอนใดต้องใช้ `sudo`) — จึงไม่มีความเสี่ยงที่โฟลเดอร์จะเป็นของ `root` ที่นี่ การแตกไฟล์ทับการติดตั้งเดิมโดยตรงจึงปลอดภัย

```bash
# จากโฟลเดอร์แม่ของ omega-serv/ (ห้ามทำจากภายใน)
tar -xzf omega-serv-2.6.1.tar.gz
cd omega-serv/
./install.sh
```

ไฟล์เก็บถาวรตั้งใจไม่รวมสถานะที่ใช้งานอยู่ทั้งหมด (`var/db/`, `var/log/`, `var/backups/`, `secure/secrets/`, `secure/certificates/*.key`, `config/omega-serve.json`, **`webroot/` — เว็บไซต์ที่ให้บริการจริง**...) — การแตกไฟล์ทับไม่เคยแตะข้อมูล ใบรับรอง การตั้งค่า หรือเนื้อหาที่ให้บริการอยู่ มีเพียงโค้ดของแอปพลิเคชันที่ถูกแทนที่ `install.sh` ใช้ `.venv` ที่มีอยู่ซ้ำ และเพียงติดตั้ง dependency ทับลงไป

โฟลเดอร์ `var/` และ `secure/auth/` ไม่อยู่ในไฟล์เก็บถาวร แม้จะว่างเปล่า: การแตกไฟล์ทับจึงไม่รีเซ็ตสิทธิ์ของโฟลเดอร์เหล่านี้อีก (ซึ่งใช้ร่วมกับบัญชีของบริการ systemd) — ไม่ต้องใช้ « บริการ → ซ่อมสิทธิ์ » หลังการอัปเดตอีกต่อไป `install.sh` จะสร้างโฟลเดอร์เหล่านี้ถ้ายังไม่มี โดยไม่แตะโฟลเดอร์ที่มีอยู่แล้ว

> ⚠️ **ถ้ามีบริการทำงานอยู่ ขั้นตอนข้างต้นยังไม่พอ** มันแทนที่โค้ดบนดิสก์ แต่โปรเซสที่กำลังทำงานยังคงรันโค้ดเก่าที่โหลดไว้ในหน่วยความจำ — หลังจากนั้นจึงต้อง **รีสตาร์ทเต็มรูปแบบ** ทุกครั้ง:
> ```bash
> sudo systemctl restart <ชื่อบริการ>
> ```
> **ห้ามแค่โหลดใหม่** (`systemctl reload` หรือหน้าจอ SERVICE → *โหลดใหม่*): การโหลดใหม่อ่านเพียงตัวเลือกการตั้งค่าบางอย่าง (กฎ WAF, โซนการยืนยันตัวตน...) **ไม่เคยอ่านโค้ด Python ใหม่** ถ้า `systemctl status <ชื่อบริการ>` แสดงเวลาเริ่มทำงานที่เก่ากว่าการอัปเดตของคุณ แสดงว่ามันยังรันโค้ดเก่าอยู่ ถ้าคุณอัปเดตด้วยการเขียนทับโฟลเดอร์เดิมเสมอ (กรณีมาตรฐานด้านบน) การรีสตาร์ทนี้คือขั้นตอนเดียวที่ขาดไป — ไม่ต้องติดตั้งบริการใหม่ จะมีข้อความแจ้งในพื้นที่การแจ้งเตือน: เพียงรีสตาร์ทบริการจากเมนู « SERVICE »

> ⚠️ **ถ้าบริการรีสตาร์ทวนซ้ำไม่หยุดหลังจากนั้น** (`systemctl status` สลับระหว่าง active/inactive, `journalctl -u <ชื่อบริการ>` แสดง `PermissionError` ขณะเขียนไฟล์ใน `var/`): การแตกไฟล์ด้วย `tar` จะคืนสิทธิ์ของโฟลเดอร์ตามที่บันทึกไว้ในไฟล์เก็บถาวร ซึ่งอาจลบการแบ่งปันสิทธิ์ที่ตั้งไว้ให้บัญชีระบบเฉพาะตอนติดตั้งครั้งแรก — แม้ `install.sh` เองจะไม่เคยแตะก็ตาม ไม่ต้องติดตั้ง unit ใหม่: หน้าจอ SERVICE → **ซ่อมสิทธิ์** (นำการแบ่งปันสิทธิ์บน `var/` และ `secure/auth/` กลับมาใช้ใหม่ โดยไม่แตะ unit ของ systemd)

### Dependency

แกนเซิร์ฟเวอร์ (ตัวแยกวิเคราะห์ HTTP/1.1, ไคลเอนต์ FastCGI, การแฮชรหัสผ่านด้วย `hashlib.scrypt`) ยังคงเป็น Python ล้วน/stdlib และทุกอย่างที่เกี่ยวกับใบรับรอง TLS ทำผ่านไฟล์โปรแกรม `openssl` แบบโปรเซสย่อย แทนที่จะใช้ไลบรารีเข้ารหัสของ Python — **ไม่มี dependency ภายนอกสำหรับส่วนนี้** มีเพียงอินเทอร์เฟซแบบโต้ตอบ ที่เพิ่ม dependency: `omega-lib` (ธีม, การตรวจจับเทอร์มินัล — ไลบรารีที่ใช้ร่วมกันในชุดเครื่องมือ ไม่ได้เผยแพร่บน PyPI และรวมมาในไฟล์เก็บถาวรสำหรับแจกจ่าย), `textual` และ `pyte` (การจำลองเทอร์มินัลเพื่อแสดง `lnav` แบบรวมในอินเทอร์เฟซ), `jinja2` (การส่งออก HTML ตามธีม) และ `psutil` (หน้าจอสถานะและทรัพยากร — CPU/RAM/ดิสก์/เครือข่าย) Dependency สำหรับการพัฒนา/ทดสอบแบบเลือกได้ (`pip install -e ".[test]"`): `hypothesis` (การทดสอบคุณสมบัติของตัวแยกวิเคราะห์ HTTP และตัวแปลงพาธ ไม่เคยใช้ใน production) เครื่องมือด้านคุณภาพ (`pip install -e ".[dev]"`): `pytest`, `ruff`, `mypy`, `import-linter` ส่วนเสริมแบบเลือกได้อีกตัว (`pip install -e ".[magnet]"`): `lupa` (การผูก Lua แบบฝัง, wheel ที่คอมไพล์ไว้แล้ว ไม่ต้องมีตัวแปลภาษา `lua` ของระบบ) ใช้เฉพาะกับสคริปต์ WAF เสริม « magnet » — ไม่เคยติดตั้งเป็นค่าเริ่มต้น การไม่มีจะถูกแจ้ง (ความสามารถ `waf-magnet`, หน้าจอ **ความสามารถ**) พร้อมคำสั่งติดตั้งที่ถูกต้อง โดยไม่ขัดขวางส่วนอื่นของเซิร์ฟเวอร์

### เครื่องมือเสริมที่แนะนำ

อินเทอร์เฟซทำงานในโหมดลดความสามารถถ้าไม่มีเครื่องมือเหล่านี้:

- `openssl` — จำเป็นสำหรับทุกอย่างที่เกี่ยวกับใบรับรอง TLS (ลงนามเอง, CA ภายใน, การนำเข้า) ถ้าไม่มี คำสั่ง `certs *` จะล้มเหลว แต่ส่วนอื่นของเซิร์ฟเวอร์ทำงานตามปกติ
- `certbot` — จำเป็นเฉพาะสำหรับตัวช่วย **Let's Encrypt** และการต่ออายุอัตโนมัติของมัน TLS แบบลงนามเอง/CA ภายในไม่ต้องใช้
- `lnav` — การวิเคราะห์ล็อกขั้นสูงที่รวมอยู่ในหน้าจอ **จัดการล็อก** มีข้อความผิดพลาดที่ชัดเจนถ้าไม่พบไฟล์โปรแกรม ไม่มีการแครช ส่วนอื่นของหน้าจอ (ดู/ติดตาม/หมุนเวียน/สถิติ) ทำงานตามปกติโดยไม่ต้องมี
- `scp` (แพ็กเกจ `openssh`/`openssh-clients` ซึ่งแทบจะมีอยู่แล้วเสมอ) — จำเป็นเฉพาะสำหรับ **แหล่งระยะไกล (SSH)** ถ้าไม่มี การดึงข้อมูลจะล้มเหลวพร้อมข้อความที่ชัดเจน ส่วนอื่นของคลังทำงานตามปกติ
- `python-psutil` (แพ็กเกจระบบที่เทียบเท่า `psutil` บน PyPI) — `pip install -e .` ติดตั้งให้อัตโนมัติในทุกกรณี (เป็น dependency ที่จำเป็นของแพ็กเกจ หน้าจอ **สถานะและทรัพยากร** ต้องใช้เสมอ) แต่การติดตั้งไว้ก่อนผ่านตัวจัดการแพ็กเกจของระบบช่วยให้ `pip` ไม่ต้องคอมไพล์ wheel เอง
- `cmake`, คอมไพเลอร์ C++20 (`g++`), ไฟล์ส่วนหัวของ OpenSSL 3 และ PCRE2 — จำเป็นเฉพาะเมื่อเอนจินเนทีฟที่มาพร้อมไม่สามารถเริ่มทำงานได้ (glibc เก่ากว่า 2.38): `install.sh` จะคอมไพล์ใหม่บนเครื่องนั้น หากไม่มี PCRE2 เอนจินที่คอมไพล์เองจะให้ Python ตรวจทุกคำขอเมื่อเปิด WAF (ช้ากว่า) หากไม่มีเครื่องมือเหล่านี้ omega-serv จะใช้เอนจิน Python ต่อไป
- ฟอนต์อีโมจิ (Noto Color Emoji) — ไม่บังคับ ใช้กับไอคอนของตัวดูแบบง่าย (การจัดการบันทึก) หากไม่มี ไอคอนบางตัวจะแสดงเป็นกล่องสี่เหลี่ยม ส่วนอื่นไม่ได้รับผลกระทบ Nerd Font ไม่มีอีโมจิเหล่านี้


## 3. การใช้งาน

อินเทอร์เฟซสองแบบที่เทียบเท่ากันทุกประการในด้านการทำงาน โดยไม่มีตรรกะซ้ำซ้อนระหว่างกัน: CLI แบบไม่โต้ตอบ (เขียนสคริปต์ได้ ใช้ในตัวอย่างด้านล่าง) และอินเทอร์เฟซแบบโต้ตอบ Textual (เมนู แบบฟอร์ม ตาราง) — ทุกการกระทำของฝั่งหนึ่งมีอยู่ใน CLI อินเทอร์เฟซเพียงห่อหุ้มกรณีการใช้งานเดียวกัน

### โหมดโต้ตอบ (TUI)

แนะนำสำหรับการใช้งานประจำวัน — เรียกใช้โดยไม่ใส่อาร์กิวเมนต์:

```bash
./omega-serv.sh
```
ถ้าคุณสร้าง alias ไว้แล้ว เพียงพิมพ์ `serv` ในเทอร์มินัล:
```bash
serv
```

### ภาษาของอินเทอร์เฟซ

17 ภาษา: ฝรั่งเศส อังกฤษ สเปน โปรตุเกส (บราซิล) อิตาลี เยอรมัน ดัตช์ โปแลนด์ รัสเซีย จีน เวียดนาม ไทย อินโดนีเซีย ญี่ปุ่น เกาหลี ฮินดี อาหรับ เลือกได้ในการตั้งค่า (ปุ่ม `o`, « Langue / Language » ซึ่งเป็นป้ายที่ไม่เคยแปล) หรือชั่วคราวด้วย `OMEGA_SERV_LANG=en serv` ในคอนโซลข้อความของ Linux (TTY) ภาษาที่ฟอนต์คอนโซลไม่มีตัวอักษรรองรับ (เวียดนาม จีน ไทย ญี่ปุ่น เกาหลี ฮินดี อาหรับ) จะแสดงเป็นภาษาอังกฤษสำหรับเซสชันนั้น สำหรับภาษาฮินดี เทอร์มินัลที่ประกอบตัวอักษรเชื่อมเอง (Kitty, Ghostty, Konsole) ทำให้กรอบและคอลัมน์เลื่อน ซึ่งต่างกันไปตามฟอนต์: จะมีคำเตือนแสดงเมื่อเริ่มต้น ส่วน Terminator, GNOME Terminal, Xfce Terminal และ Alacritty แสดงภาษาฮินดีได้ตรงแนว มีการตั้งค่าแยกอีกสองอย่าง: **ภาษาของหน้าสำหรับผู้เยี่ยมชม** (หน้าข้อผิดพลาด, รายการโฟลเดอร์ — หน้าจอหน้าข้อผิดพลาด ค่าเริ่มต้นเป็นภาษาฝรั่งเศส) และ **ภาษาของการส่งออก** (HTML และรายงานเหตุการณ์ — การตั้งค่า ค่าเริ่มต้นเป็น « เหมือนอินเทอร์เฟซ ») ล็อกของเซิร์ฟเวอร์ (`journalctl`) ยังคงเป็นภาษาฝรั่งเศส

### ภาพรวมการใช้งาน

หน้าจอเริ่มต้น (splash ปิดเมื่อกดปุ่มหรือคลิก) → เมนูหลัก (ตัวช่วยตั้งค่าครั้งแรก / ทะเบียนความสามารถ / โปรไฟล์ / การตั้งค่าโดยละเอียด / ความปลอดภัยเชิงรุก / จัดการล็อก / บริการ / หลายอินสแตนซ์ / สถานะและทรัพยากร / ตรวจประเมิน / สำรองข้อมูล) → เลือกหัวข้อแล้วเลือกการกระทำ ทุกแบบฟอร์มตรวจสอบช่องที่จำเป็นก่อนดำเนินการต่อ → ยืนยันอย่างชัดเจนก่อนการดำเนินการที่อ่อนไหวหรือทำลายข้อมูล (รีสตาร์ท ลบ กู้คืน...) → บอกขั้นตอนถัดไปเสมอ (โหลดใหม่ขณะทำงานโดยอัตโนมัติ หรือยืนยันการรีสตาร์ทเต็มรูปแบบ) หลังทุกการบันทึกที่เปลี่ยนการตั้งค่าที่ให้บริการอยู่ การปรับให้เข้ากับเทอร์มินัล (สี ขนาด การลดระดับโครงสร้างของโปรไฟล์การแสดงผล) เป็นไปโดยอัตโนมัติไม่ต้องใช้แฟล็กด้วยมือ

#### คีย์ลัด (อินเทอร์เฟซแบบโต้ตอบ)

| ปุ่ม | การกระทำ |
|---|---|
| `↑` / `↓` | เลื่อนไปมาระหว่างองค์ประกอบของหน้าจอ |
| `Tab` / `Shift+Tab` | เลื่อนไปมาระหว่างช่องของแบบฟอร์ม |
| `Esc` | กลับไปหน้าจอก่อนหน้า (ยืนยันการออกเมื่ออยู่ที่หน้าหลัก) |
| `t` | ธีมถัดไป (ใช้ทันที ไม่ต้องยืนยัน) |
| `r` | รีเฟรชการตรวจจับเทอร์มินัล |
| `F1` | ความช่วยเหลือของหน้าจอปัจจุบัน (เอกสารตามบริบท — ดู "คู่มือช่วยเหลือ" ด้านล่าง) |
| `a` | คู่มือช่วยเหลือฉบับสมบูรณ์ (เมนูที่เลื่อนดูได้ + FAQ) |
| `o` | การตั้งค่าแอปพลิเคชัน (ธีม โปรไฟล์การแสดงผล พาธของการส่งออก/ภาพหน้าจอ — ดูด้านล่าง) |
| `q` | ออก (มีการยืนยัน) |
| `Ctrl+P` | ชุดคำสั่ง (ธีม, ภาพหน้าจอ, ตัวเลือก...) |

> **ข้อยกเว้น — ตัวแก้ไขรายการ (WAF → Custom)**: ไม่มีคีย์ลัดใด ทุกอย่างทำด้วยเมาส์ แป้นพิมพ์ใช้สำหรับพิมพ์เท่านั้น (ตัวอักษร Enter ลูกศร Home/End Page Up/Down Backspace Delete) `Esc`, `F1` และ `Ctrl+P` ไม่ทำงานในตัวแก้ไข (ใช้ปุ่ม **ช่วยเหลือ**) มีเพียง `Ctrl+Q` ที่ยังทำงาน พร้อมการยืนยันถ้ามีการแก้ไขที่ยังไม่ได้บันทึก

#### คู่มือช่วยเหลือ (ปุ่ม `F1`/`a`)

ระบบช่วยเหลือในตัว ไม่ใช่แค่ข้อความคงที่: ทุกหน้าจอที่มีเอกสาร (เอกสารนิยาม/ช่องที่ต้องกรอกพร้อมตัวอย่างที่ชัดเจน/การกระทำที่ถูกเรียก/ผลตอบสนอง — โหลดใหม่ รีสตาร์ท หรือไม่มี) เปิดได้โดยตรงจากหน้าจอนั้นด้วย `F1` ปุ่ม `a` เปิดเมนูฉบับสมบูรณ์ (โครงสร้างเหมือนการนำทางจริงของแอปพลิเคชันทุกประการ) พร้อมทางเข้าสู่ FAQ (กับดักที่พบในการใช้งานจริง เช่น ประเภทการโจมตีของ Active Defense, สิทธิ์ของบริการที่ใช้ร่วมกัน) และการส่งออก HTML แบบเปิดดูได้อิสระ (คงธีมที่ใช้อยู่) ของคู่มือทั้งหมด มีหน้าจออ้างอิงทั่วไปเป็นทางสำรองในขณะที่ยังไม่มีเอกสารเฉพาะ — ปัจจุบันครอบคลุมครบถ้วน ตรวจสอบด้วยการทดสอบ

#### ติดต่อและสนับสนุน (คู่มือช่วยเหลือ)

คู่มือช่วยเหลือ (ปุ่ม `a`) มีหน้าจอ **ติดต่อและสนับสนุน**: *เลี้ยงกาแฟ* (หน้า PayPal ของผู้พัฒนา) *ติดต่อฝ่ายสนับสนุน* (แบบฟอร์มติดต่อของเว็บไซต์ พร้อมแสดงที่อยู่อีเมล) และ *ลงทะเบียนเป็นผู้ใช้ (นิรนาม)* การลงทะเบียนเป็นไปโดยสมัครใจและปิดไว้โดยค่าเริ่มต้น ใช้เพื่อนับจำนวนผู้ใช้เท่านั้น และหากต้องการ ทวีปหรือประเทศของผู้ใช้ (รายการแบบปิด ไม่มีข้อความอิสระ) ข้อมูลที่ส่งคือคีย์แบบสุ่ม เวอร์ชันของ omega-serv และโหมดที่เลือก (*ครั้งเดียว* หรือ *ทุกวัน* ซึ่งแบบหลังทำให้นับการติดตั้งที่ใช้งานอยู่ได้) ไม่ส่งชื่อ ชื่อเครื่อง เนื้อหา หรือบันทึกเด็ดขาด การส่งรายวันทำงานในโปรเซสแยกและไม่ทำให้เซิร์ฟเวอร์ช้าลง ที่อยู่ IP ไม่ถูกบันทึกในการลงทะเบียน แต่เช่นเดียวกับการเข้าชมทั่วไป จะผ่านการตรวจสอบความปลอดภัยและบันทึกของเซิร์ฟเวอร์ปลายทาง ถอนได้ทุกเมื่อจากหน้าจอเดียวกันหรือด้วย `omega-serv declaration withdraw` และ `DO_NOT_TRACK=1` จะหยุดการส่งอัตโนมัติทั้งหมด

#### เมนูหลัก (อินเทอร์เฟซแบบโต้ตอบ)

- **ตัวช่วยตั้งค่าครั้งแรก** — เส้นทางแบบมีผู้นำทาง 8 ขั้นตอน (ต้อนรับ → ความสามารถแบบอ่านอย่างเดียว → เลือกโปรไฟล์ → bind/พอร์ต → TLS แบบเลือกได้ → ตรวจสอบ → สรุป + บันทึก → เสนอให้ติดตั้งบริการ) ช่วยสร้างการตั้งค่าที่สมบูรณ์และเริ่มเซิร์ฟเวอร์ได้โดยไม่ต้องรู้จัก CLI
- **ทะเบียนความสามารถ** — การตรวจสอบระบบแบบอ่านอย่างเดียว (ระบบ init, พอร์ตที่ตั้งไว้ถูกใช้อยู่หรือไม่, มี `openssl`/`logrotate`/`tailscale`/`lnav` หรือไม่, พื้นที่ดิสก์, ขีดจำกัด file descriptor...) ส่งออก JSON/HTML ได้
- **โปรไฟล์** — กรณีการใช้งานเดียวกับ `profile` ใน CLI แสดง diff ก่อนบันทึกเสมอ
- **การตั้งค่าโดยละเอียดของเซิร์ฟเวอร์** — CRUD ครบถ้วนสำหรับ alias/การเปลี่ยนเส้นทาง/rewrite/dirlisting/พร็อกซีที่เชื่อถือ/reverse proxy ขาออก/FastCGI/แคช/การยืนยันตัวตน/การควบคุมการเข้าถึง/หน้าข้อผิดพลาด รวมถึงเมนูย่อย **TLS** (สถานะ, สร้างใบรับรองลงนามเอง, ตัวช่วย CA ภายใน, ตัวช่วย Let's Encrypt/Certbot, การต่ออายุอัตโนมัติ, การเพิกถอน, เปิด/ปิด) กรอบที่สอง **ตัวเลือกและการตรวจสอบ** รวมทางลัดไปยัง **ตัวเลือก** (`option` ใน CLI) และ **ตรวจสอบการตั้งค่า** (`config check` ใน CLI) — เส้นทางเดียวกับการปรับการตั้งค่าแล้วตรวจสอบ สองหน้าจอนี้ไม่ได้เข้าถึงโดยตรงจากเมนูหลักอีกต่อไป WAF ไม่ได้อยู่ที่นี่แล้ว (ดู "ความปลอดภัยเชิงรุก" ด้านล่าง): มันแสดงสถานะการทำงานที่เปลี่ยนแปลงตลอดเวลาเป็นหลัก ไม่ใช่แบบฟอร์มตั้งค่าคงที่ธรรมดา ทุกการบันทึกบอกขั้นตอนถัดไปเสมอ: โหลดใหม่ขณะทำงานโดยอัตโนมัติและเงียบ ๆ ถ้ามีบริการทำงานอยู่ (dirlisting, การเข้าถึง, alias/การเปลี่ยนเส้นทาง/rewrite, แคช, หน้าข้อผิดพลาด, พร็อกซีที่เชื่อถือ, โซน reverse proxy/FastCGI, ผู้ใช้/โซนการยืนยันตัวตน) หรือยืนยันการรีสตาร์ทเต็มรูปแบบอย่างชัดเจนเมื่อการเปลี่ยนแปลงกระทบซ็อกเก็ตที่รอรับการเชื่อมต่อ, TLS หรือ Active Defense — ไม่มีหน้าจอใดปล่อยให้คุณต้องเดาอีกว่าต้องรีสตาร์ทเซิร์ฟเวอร์หรือไม่
- **ความปลอดภัยเชิงรุก** — หน้าจอเดียวที่รวมสามส่วนไว้เคียงกันตามลำดับของการโจมตี: **WAF**, **Active Defense** และ **RIPOSTE** (การตอบโต้แบบเป็นขั้นตามระยะเวลา) **Active Defense** (สถานะ, ภัยคุกคามที่ติดตามพร้อมคะแนน/ระดับ, เหตุการณ์พร้อมลำดับเวลา/การส่งออก IoC/รายงาน, การกำหนด Deception, จำลองการตัดสินใจแบบ dry-run, **การตั้งค่า** — ตั้งค่าครบถ้วนโดยไม่ต้องแก้ไข `config/omega-serve.json` ด้วยมือ) และ **WAF** (สถานะ, โมดูล — โหมด/ชุดกฎ/รายการบล็อก, ทดสอบคำขอ, Custom — สร้างกฎเองและโหลดรายการพาธ/คีย์เวิร์ดที่แก้ไขได้ด้วยเมาส์, Magnet — นำเข้าสคริปต์ `mod_magnet` ภายนอกพร้อมตรวจสอบความเข้ากันได้ก่อนเปิดใช้งาน) ใต้สามบล็อกคือ **การแทรกแซงด้วยตนเอง**: แบนหรือยกเลิกแบนที่อยู่ IP ด้วยตนเอง และสถานะการแบนทั้งหมด
- **จัดการล็อก** — เมนูสองคอลัมน์ คอลัมน์ **คลัง**: ศูนย์กลางที่อ้างอิงทุกล็อกที่ต้องจัดการ (เพิ่มด้วยมือ คลิกเดียวเพิ่มล็อกของอินสแตนซ์ทันที — access/error/WAF แบบเนทีฟ + สคริปต์ magnet ถ้าเปิดใช้ — หรือ **แหล่งระยะไกล** ที่ดึงมาผ่าน SSH ดูด้านล่าง); **รายการโปรด** (ชุดล็อก + ตัวดูที่บันทึกไว้ภายใต้ชื่อหนึ่ง เปิดได้ทันที); **ดูล็อก** พร้อมตัวดู 3 แบบให้เลือกตามจำนวนล็อกที่เลือก — แบบง่าย (tail สด + สถิติทั่วไปของ IP/ข้อผิดพลาด/รหัส HTTP กับทุกรูปแบบ), แบบคลาสสิก (อ่าน + ติดตาม), `lnav` แบบรวม (แสดงผลเทอร์มินัลจริงในอินเทอร์เฟซ รวมล็อก magnet ไว้เสมอ + พาธที่เพิ่มด้วยมือแบบ **ปักหมุด** เพื่อเก็บไว้ข้ามเซสชัน); **ดูและจัดการ IP** (IP ที่พบบ่อยที่สุดในล็อกหนึ่งหรือหลายล็อกที่เลือก ช่วงเวลา 24 ชม./7 วัน/30 วัน/ทั้งไฟล์ คำนวณเบื้องหลังพร้อมตัวแสดงความคืบหน้า การลบ IP); **สถิติ** (รายงานฉบับเต็มของล็อกหนึ่งหรือหลายล็อก — สรุป สถานะ HTTP IP ที่พบบ่อยที่สุด พาธ การกระจายรายชั่วโมง แนวโน้มรายวัน — ส่งออกเป็น JSON/HTML ได้) คอลัมน์ **การบำรุงรักษา**: หมุนเวียน/เก็บถาวรด้วยมือหรืออัตโนมัติตามเกณฑ์ขนาด สร้างการสำรองทันที ตั้งค่า/จัดการงานอัตโนมัติตามกำหนดเวลา (เรียกใช้ทุกคืนโดยตัวจับเวลา systemd หรือโดยบรรทัด crontab บน OpenRC/runit) กู้คืน/ล้างไฟล์เก็บถาวร ส่งออกรายการ; **สุขภาพล็อก** (การตรวจสอบแบบอ่านอย่างเดียวของล็อก ดิสก์ และไฟล์เก็บถาวร — สิทธิ์ ล็อกที่เงียบหรือเสียหาย การหมุนเวียน logrotate จำนวนวันก่อนดิสก์เต็ม — พร้อมสิ่งที่ต้องทำสำหรับแต่ละข้อที่พบ การแก้ไขสิทธิ์ — ใช้ sudo ถ้าจำเป็น — ส่งออก JSON/HTML/TXT) เมื่อบัญชีของคุณอ่านล็อกไม่ได้ สถิติ และ ดูและจัดการ IP จะขอรหัสผ่าน sudo ของคุณแล้วจึงอ่านล็อกนั้น
- **บริการ** — การกระทำเดียวกับ `service` ใน CLI ยกระดับสิทธิ์ด้วย `sudo` ครั้งต่อครั้งในแต่ละการกระทำ ไม่เคยรันทั้งแอปพลิเคชันในฐานะ root
- **หลายอินสแตนซ์** — ทะเบียนส่วนกลาง (`~/.config/omega-serv/instances.json` อยู่นอกไดเรกทอรีโปรเจกต์ใด ๆ) ของการติดตั้งที่รู้จักบนเครื่อง พร้อมสถานะ systemd ของแต่ละรายการ สร้างอินสแตนซ์ใหม่ (คัดลอกโครงสร้างไดเรกทอรี สภาพแวดล้อมเสมือนและ dependency ของตัวเอง การตั้งค่าใหม่พร้อมพอร์ตแยกต่างหาก ตรวจสอบว่าไม่ซ้อนกันและพอร์ตไม่ชนกัน) ได้โดยตรงจากอินเทอร์เฟซ ปุ่มนี้แทบไม่แสดงสำหรับการติดตั้งเพียงชุดเดียว (ป้าย "หลายอินสแตนซ์" กลายเป็น "Instances (N)" เมื่อรู้จักตั้งแต่ 2 ชุดขึ้นไป) สลับไปยังอินสแตนซ์อื่นได้เต็มรูปแบบ (`os.execv` ยืนยันอย่างชัดเจน มี splash เฉพาะประกาศการสลับเมื่อเริ่มใหม่) ถอนการติดตั้งอินสแตนซ์ได้ทั้งหมด (ถอด unit ถอดบัญชีระบบเฉพาะถ้าไม่มีอินสแตนซ์อื่นใช้แล้ว และลบไดเรกทอรีได้ตามเลือก ไม่เคยลบเป็นค่าเริ่มต้น)
- **สถานะและทรัพยากร** — ภาพรวมในแวบเดียว รีเฟรชทุก 2 วินาที: สถานะเซิร์ฟเวอร์ (โปรเซส/PID, สถานะบริการของระบบ, โปรไฟล์/ตัวเลือกที่เปิด/TLS/พอร์ต), กระแสล็อกการเข้าถึงแบบสด (อัตรา, การกระจายตามรหัสสถานะ, IP ไม่ซ้ำ, อัตราข้อผิดพลาด), ทรัพยากรระบบ (CPU/RAM/ดิสก์/swap/โหลด/เครือข่าย ผ่าน `psutil`) และยังรวมทางลัด **จำลองคำขอ** (กรณีการใช้งานเดียวกับคำสั่ง CLI ที่สอดคล้อง)
- **ตรวจสอบความปลอดภัย** — กรณีการใช้งานเดียวกับคำสั่ง CLI ที่สอดคล้อง
- **สำรองข้อมูลการตั้งค่า** — ไฟล์เก็บถาวร tar.gz ของไฟล์การตั้งค่า และเมื่อเลือกอย่างชัดเจน รวมกฎ WAF/โซนการยืนยันตัวตน/ใบรับรอง (ต้องยืนยันเมื่อรวมความลับจริง)/ฐานข้อมูล Active Defense การกู้คืน การแสดงรายการ การลบ

> หมายเหตุเกี่ยวกับงานหมุนเวียนอัตโนมัติตามกำหนดเวลา: งานอัตโนมัติรายการแรกจะติดตั้งงานรายวัน — ตัวจับเวลา systemd (ขอรหัสผ่าน sudo) มิฉะนั้นเป็นบรรทัดใน crontab ของคุณ (OpenRC, runit หรือไม่มีตัวจัดการบริการ ต้องมีเดมอน cron ทำงานอยู่) มิฉะนั้นจะแสดงบรรทัดที่คุณต้องเพิ่มเอง ทุกคืน `omega-serv logs run-automations` จะเก็บถาวรล็อกแต่ละตัวที่ถึงกำหนดภายใต้บัญชีของคุณ การลบงานอัตโนมัติรายการสุดท้ายจะถอนงานนั้นออก

#### การตั้งค่าแอปพลิเคชัน (ปุ่ม `o` หรือชุดคำสั่ง)

เป็นค่ากำหนดของอินเทอร์เฟซเท่านั้น — ไม่เคยปนกับ `config/omega-serve.json` (การตั้งค่าเซิร์ฟเวอร์): ธีมที่ใช้, โปรไฟล์การแสดงผล (`complete`/`standard`/`reduced`/`mono` ต้องรีสตาร์ท), พาธของการส่งออก (ค่าเริ่มต้น `var/exports/`), พาธของภาพหน้าจอ (ค่าเริ่มต้น `var/screenshots/`), ล้างโฟลเดอร์ใดโฟลเดอร์หนึ่ง (ต้องยืนยัน)

```bash
# เรียกใช้เซิร์ฟเวอร์ (เบื้องหน้า, SIGTERM = หยุดอย่างเรียบร้อยพร้อมช่วงผ่อนผัน, SIGHUP = โหลด WAF/Auth ใหม่ขณะทำงาน)
./omega-serv.sh serve

# การตั้งค่า
./omega-serv.sh config init                # สร้าง config/omega-serve.json (ค่าปลอดภัยเป็นค่าเริ่มต้น)
./omega-serv.sh config check                # ตรวจสอบโดยไม่เริ่มทำงาน (ด่านกั้นเดียวกับตอนเริ่มทำงาน)
./omega-serv.sh config show
./omega-serv.sh config enable-tls --cert ... --key ... --mode direct
./omega-serv.sh config disable-tls

# โปรไฟล์ (minimal / standard / hardened / development)
./omega-serv.sh profile list
./omega-serv.sh profile show hardened
./omega-serv.sh profile apply hardened --dry-run   # ดู diff ก่อนใช้เสมอ

# ตัวเลือก (aliases, redirects, rewrites, dirlisting, cache, waf, upload, fastcgi, reverse_proxy...)
./omega-serv.sh option list
./omega-serv.sh option enable waf
./omega-serv.sh option disable waf

# จำลองคำขอโดยไม่เรียกใช้เซิร์ฟเวอร์ (มีประโยชน์ในการตรวจสอบกฎก่อนเปิดใช้งาน)
./omega-serv.sh simulate-request --method GET --url /index.html

# WAF (ทำงานได้แม้ตัวเลือกถูกปิด ผ่าน --force โดยนัย)
./omega-serv.sh waf test --method GET --path /admin --remote-ip 203.0.113.1
./omega-serv.sh blocklist list
./omega-serv.sh blocklist add --network 203.0.113.0/24 --reason "scan detecte" --duration-seconds 3600
./omega-serv.sh blocklist remove --network 203.0.113.0/24

# Active Defense (deception + โหมดสงคราม, ตัวเลือก "active_defense")
./omega-serv.sh active-defense status
./omega-serv.sh active-defense simulate --ip 203.0.113.42 --path /wp-login.php --attack-class scan --score 40
./omega-serv.sh active-defense purge
./omega-serv.sh threats list --level hostile
./omega-serv.sh threats show 203.0.113.42:ab12cd34
./omega-serv.sh incidents list --status open
./omega-serv.sh incidents show <incident-id>
./omega-serv.sh incidents close <incident-id>
./omega-serv.sh incidents export-ioc <incident-id> --format json,csv
./omega-serv.sh incidents generate-report <incident-id>
./omega-serv.sh deception list
./omega-serv.sh deception release --subject 203.0.113.42:ab12cd34

# RIPOSTE (การตอบโต้แบบเป็นขั้นตามระยะเวลา ตัวเลือก "riposte")
./omega-serv.sh riposte status
./omega-serv.sh riposte simulate --ip 203.0.113.7 --class scan --returns 3
./omega-serv.sh riposte actions list
./omega-serv.sh riposte stop

# ใบรับรอง TLS - ลงนามเอง (9a)
./omega-serv.sh certs generate-self-signed --cn localhost --san-dns localhost --san-ip 127.0.0.1
./omega-serv.sh certs show
./omega-serv.sh certs check-expiry --warn-days 30

# ใบรับรอง TLS - CA ภายใน (9b)
./omega-serv.sh certs generate-ca --cn "Mon CA locale" --days 3650
./omega-serv.sh certs generate-csr --cn serveur.local --san-dns serveur.local --key-out server.key --csr-out server.csr
./omega-serv.sh certs sign-csr --csr server.csr --ca-key secure/certificates/ca/root-ca.key --ca-cert secure/certificates/ca/root-ca.pem --out server.pem --fullchain-out fullchain.pem
./omega-serv.sh certs revoke --cert server.pem --ca-key secure/certificates/ca/root-ca.key --ca-cert secure/certificates/ca/root-ca.pem

# ใบรับรอง TLS - นำเข้า (9c เช่น จาก hook ของ Certbot)
./omega-serv.sh certs import --key privkey.pem --cert fullchain.pem

# การยืนยันตัวตน HTTP Basic
./omega-serv.sh auth add-user --username alice
./omega-serv.sh auth create-zone --path-prefix /admin/ --realm "Administration" --allowed-users alice
./omega-serv.sh auth list

# ตรวจสอบความปลอดภัย (ไม่เคยขัดขวาง ให้ข้อมูลเท่านั้น)
./omega-serv.sh audit security --format text --min-severity medium

# สำรองการตั้งค่า (รวมการตั้งค่าเสมอ ความลับจริง
# ไม่เคยถูกเข้ารหัสเป็นค่าเริ่มต้น ต้องใช้ --confirm-secrets เพื่อรวมความลับ)
./omega-serv.sh config backup --description "avant migration"
./omega-serv.sh config backup --include-auth --include-certificates --confirm-secrets
./omega-serv.sh config backup --include-active-defense --description "menaces/incidents"
./omega-serv.sh config list-backups
./omega-serv.sh config restore --snapshot-id snapshot_20260908_170003_762484

# บริการของระบบ (systemd/OpenRC/runit ตรวจจับอัตโนมัติ)
./omega-serv.sh service install --user omega-serv --group omega-serv
./omega-serv.sh service start
./omega-serv.sh service status
```

### ความช่วยเหลือคำสั่งฉบับเต็ม

คำสั่งด้านบนเป็นเพียงตัวอย่าง สำหรับคำสั่งทั้งหมดและตัวเลือก:

```bash
./omega-serv.sh help                    # แผนผังคำสั่งทั้งหมด
./omega-serv.sh help riposte            # เฉพาะสาขาเดียว
./omega-serv.sh riposte actions --help  # รายละเอียดของคำสั่ง
man omega-serv                          # หน้าคู่มือ (ติดตั้งโดย install.sh)
```

เอกสารอ้างอิงฉบับเต็ม: [docs/HELP.md](../../HELP.md).

### รหัสออกที่ควรทราบ

| คำสั่ง | รหัส | ความหมาย |
|---|---:|---|
| `audit security` | `0` | ไม่มีอะไรร้ายแรง (ไม่มี `CRITICAL`/`HIGH`) |
| `audit security` | `1` | มีข้อค้นพบ `CRITICAL` อย่างน้อยหนึ่งรายการ |
| `audit security` | `2` | มี `HIGH` อย่างน้อยหนึ่งรายการโดยไม่มี `CRITICAL` |
| `audit security` | `3` | ข้อผิดพลาดในการทำงาน (ไม่พบการตั้งค่า...) |

## 4. ความเข้ากันได้กับเทอร์มินัล

อินเทอร์เฟซแบบโต้ตอบ ([Textual](https://textual.textualize.io/) สร้างบน [Rich](https://rich.readthedocs.io/)) ตรวจจับความสามารถของเทอร์มินัล (โปรแกรมจำลอง ขนาด) โดยอัตโนมัติ และปรับสไตล์ชีตเชิงโครงสร้างให้เหมาะสม (`complete`/`standard`/`reduced`/`mono`) โดยไม่ต้องใช้แฟล็กด้วยมือ โหมด CLI เป็นข้อความธรรมดาเสมอ ไม่ขึ้นกับเทอร์มินัล เป็นนโยบายที่ใช้ร่วมกันทั้งชุด `omega-` (`omega-lib`, `terminal/policies.py`) — เหมือนกับของ `omega-check`/`omega-fire`

| xterm, urxvt, SSH รุ่นใหม่ | `reduced` |
| TTY ของ Linux, SSH รุ่นเก่า | `mono` |
| โปรแกรมจำลองที่ไม่รู้จัก | `reduced` (ค่าสำรองเริ่มต้น) |

| ขนาดขั้นต่ำ (คอลัมน์ × บรรทัด) | เพดานของโปรไฟล์ |

## 5. โปรไฟล์

| โปรไฟล์ | การใช้งานที่ตั้งใจไว้ |
|---|---|
| `minimal` | การสาธิต/ใช้ในเครื่องแบบง่าย: สแตติกเท่านั้น ไม่เปิดตัวเลือกใด |
| `standard` | เว็บไซต์สแตติกหรือ production ขนาดเล็ก: เฮดเดอร์ทั่วไป, CSP พื้นฐาน, ปิด dirlisting/CGI/FastCGI |
| `hardened` | เปิดสู่ภายนอกด้วยสิทธิ์น้อยที่สุด: bind เฉพาะในเครื่องเป็นค่าเริ่มต้น (แนะนำ reverse proxy สำหรับอินเทอร์เน็ต), จำกัดเมธอดเป็น GET/HEAD, CSP เข้มงวด, ป้องกัน slowloris — WAF **ไม่เคย** ถูกเปิดอัตโนมัติ แม้แต่ที่นี่ |
| `development` | สำหรับการพัฒนาในเครื่องเท่านั้น ไม่เคยถูกนำเสนอว่าเหมาะกับอินเทอร์เน็ต: บังคับ bind แบบ loopback, CSP แบบ report-only, หน้าข้อผิดพลาดแบบละเอียด |

## 6. สถาปัตยกรรม

Clean Architecture (`core / domain / ports / application / infrastructure / interfaces / bootstrap`) — `bootstrap/` คือรากของการประกอบ (เทียบเท่า `app/` ของเครื่องมืออื่นในชุด) ลักษณะเฉพาะที่ยอมรับไว้ของโปรเจกต์นี้ ซึ่งตรวจสอบด้วย `import-linter` ไม่ใช่แค่สมมติ: `application/server/start_server.py` (และ `validate_config.py`, `run_audit.py`) ทำหน้าที่เป็น **โรงงานประกอบที่ขึ้นกับการตั้งค่าจริง** (ใช้ตัวจัดการบริการใด เปิด WAF หรือไม่...) และสร้างอะแดปเตอร์ `infrastructure/` จริงโดยตรง — ต่างจากรูปแบบที่เข้มงวดกว่าของ CHECK/TRACK ที่ `application/` ใช้เพียง `ports/` กฎสากลข้อเดียวที่บังคับใช้จริง: `domain/`/`core/` ไม่เคยขึ้นกับชั้นภายนอก

```text
src/omega_serv/
├── core/            คำศัพท์ที่ใช้ร่วมกันทุกชั้น (platform_info, ค่าคงที่)
├── domain/           ตรรกะทางธุรกิจล้วน (HTTP, การตั้งค่า, ความปลอดภัย WAF/TLS/auth/audit, การกำหนดเส้นทาง)
├── ports/            สัญญา (Protocol) ที่แอปพลิเคชันต้องการ
├── application/      กรณีการใช้งาน - บางฟังก์ชัน (build_server...) ประกอบอะแดปเตอร์จริงด้วย (ดูด้านบน)
├── infrastructure/    การใช้งานจริง (asyncio, openssl ผ่าน subprocess, systemd/OpenRC/runit, ไฟล์)
├── interfaces/cli/    CLI argparse แบบไม่โต้ตอบ
├── interfaces/tui/    อินเทอร์เฟซแบบโต้ตอบ Textual (กรณีการใช้งานเดียวกัน ไม่มีตรรกะซ้ำซ้อน)
└── bootstrap/         DependencyContainer, การหารากของโปรเจกต์
```

กฎที่ตรวจสอบด้วย `import-linter` (8 สัญญา): `domain`/`core` ไม่เคยขึ้นกับชั้นภายนอก; `interfaces.tui` ไม่เคยขึ้นกับ `infrastructure` โดยตรง; `textual` อยู่เฉพาะใน `interfaces.tui`; `subprocess` อยู่เฉพาะใน `infrastructure/process/subprocess_runner.py` (และ `infrastructure/lnav/` กระแส PTY แบบโต้ตอบ); `ssl` อยู่เฉพาะใน `infrastructure/tls/ssl_context_builder.py`; `jinja2` อยู่เฉพาะใน `infrastructure/exporters/html_exporter.py`; `sqlite3` อยู่เฉพาะใน `infrastructure/persistence/sqlite_active_defense_connection.py` (ที่เก็บข้อมูลเชิงสัมพันธ์แห่งเดียวของโปรเจกต์ สงวนไว้ให้ Active Defense); `lupa` อยู่เฉพาะใน `infrastructure/waf/lua_waf_adapter.py` (สคริปต์ WAF เสริม « magnet »)

## 6b. เอนจิน HTTP และจำนวนโปรเซส

มีสองเอนจินที่ให้บริการคำขอได้ เมื่อใช้ **เอนจิน Python** ซึ่งเป็นค่าเริ่มต้น ตัวแปลภาษา Python จะจัดการคำขอทั้งหมด **เอนจินเนทีฟ** (C++, `bin/omega-http-core`) อ่าน วิเคราะห์ และให้บริการคำขอเอง ส่วนเซิร์ฟเวอร์ Python ยังคงดูแลการตั้งค่า การเฝ้าระวัง และการตัดสินใจด้านความปลอดภัย

- **การตั้งค่าสองอย่าง**: เอนจิน (หน้าจอ **การตั้งค่าพื้นฐาน**) และจำนวนโปรเซส (หน้าจอ **ความทนทานและขีดจำกัด**) จำนวนโปรเซสถูกจำกัดตามเอนจินและโปรเซสเซอร์ที่ตรวจพบ: กับเอนจิน Python สูงสุดหนึ่งโปรเซสต่อคอร์จริง; กับเอนจินเนทีฟซึ่งใช้ทุกคอร์อยู่แล้ว จะเป็นโปรเซสของการตรวจสอบความปลอดภัย คือ 1 หรือ 2 เมื่อมีตั้งแต่ 4 คอร์จริง หน้าจอบอกว่าการเพิ่มให้ประโยชน์อะไรบนเครื่องนี้ และปฏิเสธค่าที่มากเกินไป สิ่งที่ทำงานอยู่จะแสดงตามจริง (« เอนจินเนทีฟ 1 โปรเซส ») การเปลี่ยนเอนจินหรือจำนวนโปรเซสต้องรีสตาร์ทแบบเต็ม สิ่งที่การเลือกเปลี่ยนไป จากการวัด: FAQ ของคู่มือ และ[การเปรียบเทียบเว็บเซิร์ฟเวอร์](comparatif-serveurs-web.md)
- **คำตอบเหมือนกัน บันทึกเหมือนกัน**: เมื่อใช้เอนจินเนทีฟ เนื้อหาสแตติก การเปลี่ยนเส้นทาง การเขียนใหม่ alias แคช หน้าข้อผิดพลาด และเฮดเดอร์ความปลอดภัย จะให้บริการโดยเอนจินเนทีฟ มันตรวจหากฎของ WAF เองและให้บริการคำขอที่ไม่ตรงกับกฎใดเลยด้วยตัวเอง ส่วนคำขออื่นทั้งหมด (WAF ตรงกับกฎหรือมีข้อสงสัย, Active Defense, การยืนยันตัวตน) จะผ่านโปรเซส Python ที่ใช้การตรวจสอบแบบเดียวกันทุกประการและเขียนบันทึกด้านความปลอดภัยแบบเดียวกัน (RIPOSTE และ omega-jail ไม่เห็นความแตกต่างใดเลย) การแสดงรายการไดเรกทอรีและหน้าภายในจะขอจาก Python ส่วน reverse proxy, FastCGI, การส่งไฟล์ และ WebSocket จะส่งต่อให้ Python ตลอดการเชื่อมต่อ TLS โดยตรงจัดการโดยเอนจินเนทีฟด้วยไลบรารีเดียวกันและการตั้งค่าเดียวกัน
- **ไม่มีการผสมกัน**: กฎเพียงข้อเดียวตัดสินเอนจินที่ใช้จริง และทุกที่แสดงเอนจินนั้น (หน้าจอ **สถานะและทรัพยากร**, `omega-serv engine status`) หากเอนจินเนทีฟให้บริการทั้งหมดไม่ได้ (TLS โดยตรงร่วมกับ reverse proxy, FastCGI หรือการส่งไฟล์) หรือเริ่มทำงานไม่ได้ เอนจิน Python จะเป็นผู้ให้บริการ และแสดงเหตุผล ใน **การตั้งค่าพื้นฐาน** ตัวเลือกเอนจินเนทีฟจะเป็นสีเทาตราบที่ฟังก์ชันที่เปิดอยู่ยังขัดขวาง พร้อมบอกสิ่งที่ต้องเปลี่ยนเพื่อให้ใช้ได้ การตั้งค่าที่บันทึกในที่อื่นซึ่งจะทำให้เสียเอนจินเนทีฟไปจะขอการยืนยันก่อน
- **หากการตรวจของ Python ไม่ตอบสนอง** `waf.on_internal_error` จะตัดสิน: ให้บริการโดยไม่ตรวจหรือปฏิเสธ (503) โซนการยืนยันตัวตนจะถูกปฏิเสธเสมอในกรณีนี้ และที่อยู่ที่ถูกแบนอยู่แล้วก็ยังถูกปฏิเสธ (451)

## 7. โมดูลเสริม

ทั้งหมดปิดเป็นค่าเริ่มต้นในทุกโปรไฟล์ที่จัดให้ — การเปิดใช้งานต้องทำอย่างชัดเจนเสมอ (`option enable <ชื่อ>` หรือ `config enable-tls`):

| โมดูล | บทบาท |
|---|---|
| `waf` | ซิกเนเจอร์ (พาธที่อ่อนไหว, UA/Referer ของเครื่องสแกน, SQLi/XSS/CMDi ในเนื้อหา), รายการที่แก้ไขได้เป็นไฟล์ข้อความ (คีย์เวิร์ด หรือพาธที่อ่อนไหวพร้อมข้อยกเว้น `!`, โหมดสังเกตการณ์และการกระทำซ้ำเฉพาะของแต่ละรายการ — มีรายการอ้างอิงจัดให้สองชุด โหลดอย่างชัดเจน), การจำกัดอัตรา (token bucket, กฎตามโฟลเดอร์และตาม IP/เครือข่าย), รายการบล็อก (CIDR + วันหมดอายุ), ชื่อเสียง/การยกระดับ, การนำเข้าสคริปต์ WAF `mod_magnet` ของ Lighttpd ที่มีอยู่แล้วเพื่อเสริมกำลังแบบ « magnet » (ไม่ต้องเขียนใหม่ ส่วนเสริม `pip install -e ".[magnet]"` — เพิ่มเติมเท่านั้น ไม่สามารถยกเลิกการบล็อกของ WAF เนทีฟได้ ตรวจสอบความเข้ากันได้ตอนนำเข้า มีหน้าจอ TUI เฉพาะ) — โหมด `log-only` ไม่สามารถบล็อกได้โดยโครงสร้าง |
| TLS | โดยตรง (ลงนามเอง, CA ภายใน หรือสาธารณะผ่าน Let's Encrypt/Certbot พร้อมต่ออายุอัตโนมัติ) ไม่มี mTLS/OCSP ใน V1 |
| การยืนยันตัวตน | HTTP Basic ตามโซน (`url_prefix`), `hashlib.scrypt` พร้อมการป้องกันการโจมตีด้วยเวลา (ใช้เวลาคงที่แม้ผู้ใช้ไม่มีอยู่จริง) |
| FastCGI/PHP-FPM | `(url_prefix, script_root)` เพียงชุดเดียว `script_root` ถูกจำกัดให้อยู่นอก `webroot/` โดยการออกแบบ (ตัวจัดการไฟล์สแตติกไม่มีทางเปิดเผยซอร์ส PHP) |
| Reverse proxy ขาออก | Omega-serv ทำหน้าที่เป็นพร็อกซีไปยังแบ็กเอนด์หนึ่งหรือหลายตัวเอง (ทิศทางตรงข้ามกับ `server.tls.mode = "behind_proxy"`) — การกระจายโหลด (round-robin, แบบถ่วงน้ำหนัก, least-connections, ip-hash, least-response-time, โหลดจริง), การยึดเซสชันและกฎการกำหนดเส้นทางตามเฮดเดอร์, การตรวจสุขภาพแบบรับและแบบรุก, แคชการตอบกลับ (หลายรูปแบบตาม `Vary`), backpressure, การป้องกันการวนลูป, API ผู้ดูแลแบบขณะทำงาน |
| การอัปโหลด | โซนที่จำกัดขอบเขต, โควตาต่อโซน, ชื่อไฟล์สร้างโดยเซิร์ฟเวอร์ — ไม่มีการสตรีมใน V1 (จำกัดด้วย `server.max_request_size`) |
| `active_defense` | Deception + โหมดสงครามจากสัญญาณ WAF ที่คำนวณไว้แล้ว (ไม่เคยเป็นคะแนนชุดที่สอง): เหยื่อล่อแบบสแตติก, การทำให้ช้าลง/การบันทึกล็อกแบบละเอียด/การจำกัดอัตราแบบเจาะจง, เหตุการณ์ + การส่งออก IoC |
| `riposte` | การตอบโต้แบบเป็นขั้นตามระยะเวลา: จดจำการกระทำซ้ำตามที่อยู่ แบนนานขึ้นเรื่อย ๆ (blocklist ของ WAF, แบนระดับเครือข่ายผ่าน omega-jail) หรือขยายเวลาเหยื่อล่อ การยกเลิกและการหยุดฉุกเฉิน |

### 7a. Reverse proxy ขาออก — รายละเอียด

OMEGA-SERV สามารถทำหน้าที่เป็น reverse proxy ไปยังแบ็กเอนด์ HTTP/HTTPS หนึ่งหรือหลายตัวได้เอง — อย่าสับสนกับ `server.tls.mode = "behind_proxy"` (OMEGA-SERV **อยู่หลัง** พร็อกซี ซึ่งเป็นกลไกตรงข้าม) โซนตั้งค่าได้ด้วย CRUD ครบถ้วน (TUI: *การตั้งค่าโดยละเอียด → Reverse Proxy*) มี upstream หนึ่งหรือหลายตัวต่อโซน

- **การกระจายโหลด** — `round_robin` (ค่าเริ่มต้น), `weighted_round_robin`/`weighted_least_connections`/`ip_hash` (แบบถ่วงน้ำหนัก), `least_connections`, `least_response_time`, `real_load` (โหลดจริง) โหมด `real_load` แบบเนทีฟ (โพรบ `/.omega-serv-load/` ใช้ค่าที่วัดด้วย `psutil` ชุดเดียวกับหน้าจอ « สถานะและทรัพยากร » ไม่เคยเรียกซ้ำเป็นครั้งที่สอง) หรือแบบประกาศ (โพรบ HTTP ของบุคคลที่สาม รูปแบบขั้นต่ำ `{"load_percent": ...}` หรือตัวเลขเปล่า) — ละเอียดถึงระดับ upstream โซนเดียวกันผสมทั้งสองแบบได้
- **การยึดเซสชันและการกำหนดเส้นทางตามเงื่อนไข** — คุกกี้ sticky ที่ทึบแสง (ไม่เคยเปิดเผย host:port จริงให้ไคลเอนต์) และกฎตามเฮดเดอร์ (เท่ากันหรือคำนำหน้า) ทั้งสองถูกกรองตามคุณสมบัติของ upstream เป้าหมาย (ย้อนกลับไปใช้กลยุทธ์ปัจจุบันอย่างเรียบร้อยถ้า upstream เป้าหมายไม่พร้อม)
- **สุขภาพ** — แบบรับ (ความล้มเหลว/ความสำเร็จติดต่อกัน เกณฑ์สลับ down/up แยกกันเพื่อลดการกระพริบ) **และ** แบบรุก (โพรบเป็นระยะที่ไม่ขึ้นกับทราฟฟิกจริง เลือกได้ต่อ upstream ใช้กลไกงานเบื้องหลังเดียวกับโหลดจริง) สถานะ `DOWN` (อัตโนมัติเสมอ), `DRAINING`/`MAINTENANCE` (ด้วยมือเสมอ ชั่วคราวอย่างชัดเจน ไม่เคยถูกบันทึกถาวร) — upstream ที่ถูกตั้งด้วยมือจะถูกตัดออกจากการเลือกใหม่ โดยไม่เคยตัดการเชื่อมต่อที่สร้างไว้แล้ว ลองใหม่อัตโนมัติกับ upstream อื่น เฉพาะเมธอด idempotent (GET/HEAD/OPTIONS) และเฉพาะเมื่อเชื่อมต่อผิดพลาดเท่านั้น
- **Backpressure** — เพดานการเชื่อมต่อที่ใช้งานอยู่ตั้งค่าได้ต่อ upstream upstream ที่เต็มจะปฏิเสธอย่างเรียบร้อยด้วย 503 ต่างจาก upstream ที่ล่ม (502 ซึ่งยังลองใหม่)
- **แคชการตอบกลับ** — เฉพาะ GET/HEAD ไม่เคยแคชการตอบกลับที่ผิดพลาด ไม่เคยแคช `Set-Cookie` เว้นแต่เปิดอย่างชัดเจนต่อโซน เคารพ `Cache-Control`/`Vary` ของ upstream (ตัวเลือกที่ปิดได้แต่อันตราย ปรัชญาเดียวกับการตรวจสอบ TLS) ทรัพยากรเดียวกันหลายรูปแบบ (`Vary`) อยู่ร่วมกันบนดิสก์จริง ไม่เคยเป็นแค่ « มาทีหลังชนะ » มีล็อกป้องกัน stampede (มีเพียงคำขอเดียวที่สร้างแคชใหม่จริงในเวลาเดียวกัน) เฮดเดอร์วินิจฉัย `X-Omega-Cache: HIT`/`MISS`/`BYPASS` ในทุกการตอบกลับ การตรวจติดตาม/ล้างในหน้าจอ TUI เฉพาะ (*แคชของ reverse proxy*)
- **การป้องกันการวนลูป** — ลบเฮดเดอร์ hop-by-hop, `X-Forwarded-*` ถูกเขียนทับเสมอ (ไม่เคยรวมกับของไคลเอนต์), ตัวนับ `X-Omega-Proxy-Hops` เพิ่มขึ้นในทุกการส่งต่อ (ปฏิเสธอย่างเรียบร้อยเมื่อเกิน 5 ทอด — ตรวจจับลูปทางอ้อมระหว่างสองอินสแตนซ์ ซึ่งการตรวจสอบการตั้งค่าในเครื่องอย่างเดียวมองไม่เห็นเลย)
- **WebSocket** — อนุญาตการอัปเกรดได้ต่อโซน upstream เดียวถูกตรึงไว้ตลอดอายุของท่อเมื่อสร้างแล้ว ไม่มี timeout ระดับแอปพลิเคชัน
- **การจัดการขณะทำงาน** — API HTTP ภายในขนาดเล็ก (`/.omega-serv-admin/` ป้องกันด้วย `trusted_proxy` เช่นเดียวกับโพรบโหลดแบบเนทีฟ) ให้ TUI อ่าน/บังคับสถานะ DRAINING/MAINTENANCE ของแบ็กเอนด์ และอ่านอัตรา hit/miss ของแคช **ของเซิร์ฟเวอร์ที่กำลังทำงานจริง** (หน้าจอเฉพาะ *สถานะสดของแบ็กเอนด์*) — TUI และเซิร์ฟเวอร์เป็นสองโปรเซสแยกกันโดยไม่มีหน่วยความจำร่วม ช่องทาง HTTP ภายในนี้จึงเป็นสะพานเดียวระหว่างทั้งสอง

## 8. การเสริมความแข็งแกร่ง HTTP (เปิดใช้งานเป็นค่าเริ่มต้น)

- การวิเคราะห์คำขอ ไม่มีตัวเลือกให้ปิด: เฮดเดอร์/บรรทัดคำขอถูกจำกัด**ระหว่าง**การอ่าน (ไม่เคยหลังจากนั้น) ปฏิเสธการพับเฮดเดอร์แบบเก่า `Transfer-Encoding` ถูกปฏิเสธเสมอ (ไม่เคยเดา)
- `Content-Length` ซ้ำถูกปฏิเสธ เฮดเดอร์ `Expect` (เช่น `100-continue`) ถูกปฏิเสธอย่างเรียบร้อย (417)
- รายการเมธอดที่อนุญาตอย่างชัดเจน (มิฉะนั้น 405 + `Allow`) ตรวจสอบเฮดเดอร์ `Host` (หายไป/ว่าง/ซ้ำแม้เหมือนกัน/อักขระควบคุม → 400) การตรวจนี้เปิดใช้งานเป็นค่าเริ่มต้น และปิดได้เฉพาะในการตั้งค่า (`security.require_valid_host`)
- เฮดเดอร์ความปลอดภัยและ CSP พื้นฐาน (`enforce`/`report-only`) ใช้กับการตอบกลับของเว็บไซต์ รวมถึงหน้าข้อผิดพลาดของเว็บไซต์ (403, 404…) และไม่เคยถูกโมดูลใดลบหรือเขียนทับ ข้อยกเว้น: การตอบกลับที่ส่งก่อนการประมวลผลคำขอใด ๆ (คำขอผิดรูปแบบหรือใหญ่เกินไป หมดเวลา `Host` ไม่ถูกต้อง เมธอดถูกปฏิเสธ เซิร์ฟเวอร์รับภาระเต็ม) จะออกไปโดยไม่มีเฮดเดอร์เหล่านี้ — เป็นหน้าข้อผิดพลาดสั้น ๆ ที่ไม่มีเนื้อหาของเว็บไซต์ เปิดใช้งานเป็นค่าเริ่มต้น ปิดได้เฉพาะในหน้าจอ **ความปลอดภัยทั่วไป** (`security.security_headers_enabled`) `Cross-Origin-Opener-Policy`/`Cross-Origin-Resource-Policy` เป็น `same-origin` เสมอ โดยไม่มีความเสี่ยงจริงที่จะทำให้เว็บไซต์เสียหาย `Cross-Origin-Embedder-Policy` ถูกส่งอย่างชัดเจนเสมอ (ไม่เคยขาดหาย — เครื่องสแกนภายนอกแยกได้ระหว่าง « ไม่ได้พิจารณา » กับ « อนุญาตโดยตั้งใจ ») ค่าเริ่มต้น `unsafe-none` ใน **ทุก** โปรไฟล์รวมถึง `hardened`: ต่างจากสองตัวก่อนหน้า `require-corp`/`credentialless` อาจบล็อกทรัพยากร cross-origin (ฟอนต์ รูปภาพ iframe ของบุคคลที่สาม) ของเว็บไซต์ที่ให้บริการจริง — ปรับได้ (`security.coep_mode`) โซน CSP (`security.csp_zones`): ข้อยกเว้น **ที่ชัดเจน** ตามคำนำหน้าพาธ (เช่น `unsafe-inline` เฉพาะใต้ `/mot-dossier/` ที่ต้องใช้จริง) แต่ละโซนแทนที่นโยบายเริ่มต้นทั้งหมดสำหรับคำนำหน้าของตน — ไม่เคยรวมกัน ไม่เคยผ่อนปรนทั้งระบบ ทุกข้อยกเว้นยังคงมองเห็นได้ใน `audit security` (CSP-001/CSP-002 สแกนโซนด้วย) แม้จะตั้งใจก็ตาม สร้างได้ด้วยตัวช่วยทีละ directive (หน้าจอ **ความปลอดภัยทั่วไป**) ทุกช่องเติมค่า **ปัจจุบัน** ของนโยบายส่วนกลางไว้ล่วงหน้า — เพื่อแก้เฉพาะสิ่งที่ต้องเปลี่ยน แทนที่จะเริ่มจากช่องว่างซึ่งจะทิ้ง directive อื่นโดยไม่ตั้งใจ และจะขอการยืนยันเพิ่มเติมอย่างชัดเจนถ้าโซนที่ประกอบผ่อนปรน `unsafe-inline`/`unsafe-eval`/แหล่งทั่วไป `*`
- ที่อยู่ IPv4 ที่แมปเป็น IPv6 (`::ffff:x.x.x.x`) ถูกทำให้เป็นมาตรฐานก่อนการเปรียบเทียบใด ๆ (รายการบล็อก พร็อกซีที่เชื่อถือ การจำกัดอัตรา) — มิฉะนั้นจะเป็นช่องโหว่ที่รู้จักกันดี
- ตรวจสอบด้วยการทดสอบคุณสมบัติ (`hypothesis` ตัวอย่างที่สร้างขึ้นหลายพันรายการ) กับตัวแยกวิเคราะห์ HTTP และตัวแปลงพาธ นอกเหนือจากการทดสอบหน่วย/การทดสอบรวมแบบปกติ

## 9. TLS

### 9a. ใบรับรองแบบลงนามเอง (ขั้นต่ำ)

ครอบคลุมการใช้งานจริงในเครื่อง/แล็บ/VPN (Tailscale...): ตัวรอรับการเชื่อมต่อเดียว `ssl.SSLContext` โดยตรง RSA 2048/4096 หรือ ECDSA P-256/P-384

### 9b. CA ภายใน

สำหรับอุปกรณ์ไคลเอนต์หลายเครื่องที่ต้องเชื่อถือโดยไม่ต้องนำเข้าใบรับรองทีละใบ: หน่วยงานออกใบรับรองภายในลงนามใบรับรองเซิร์ฟเวอร์ได้มากเท่าที่ต้องการ

```text
secure/certificates/ca/
├── root-ca.key    # 0600 - องค์ประกอบที่อ่อนไหวที่สุดของโปรเจกต์
├── root-ca.pem    # 0644 - นำเข้าที่ที่เก็บใบรับรองที่เชื่อถือของไคลเอนต์
├── serial.txt     # 0600 - ติดตามหมายเลขซีเรียลถัดไป
└── index.txt      # 0600 - ติดตามสถานะ V(ใช้ได้)/R(ถูกเพิกถอน) ของแต่ละใบรับรองที่ลงนาม
```

ขั้นตอน: `certs generate-ca` (รหัสผ่านของคีย์ CA **บังคับ** พิมพ์แบบโต้ตอบพร้อมยืนยันสองครั้งถ้าไม่ระบุ `--password`) → `certs generate-csr` (คีย์ + CSR ของเซิร์ฟเวอร์) → `certs sign-csr` (ลงนามด้วย CA คัดลอก SAN จาก CSR สร้าง `fullchain.pem` ถ้าต้องการ) → ชี้ `tls.certificate.certificate_path` ไปที่ `fullchain.pem` นี้ ใบรับรองที่ถูกเจาะจะถูกถอนด้วย `certs revoke` (ทำเครื่องหมายใน `index.txt` โดยตรวจสอบก่อนว่าใบรับรองมาจาก CA นี้จริง — มิฉะนั้นจะปฏิเสธ) ไม่มีการแจกจ่าย CRL ใน V1 ไม่มี CA ภายนอก/CSR สำหรับหน่วยงานบุคคลที่สาม และไม่มี mTLS

### 9c. Let's Encrypt / ACME (Certbot) — สาธารณะ โฮสต์เอง

สำหรับเว็บไซต์สาธารณะจริงที่ใช้ใบรับรองที่เบราว์เซอร์ยอมรับ รูปแบบโฮสต์เองแบบสมบูรณ์: DDNS (Dynu หรือเทียบเท่า ผู้ดูแลรับผิดชอบเองทั้งหมด) → Certbot → Omega-serv มีเฉพาะตัวช่วยใน TUI (`การตั้งค่าโดยละเอียด → TLS → ตัวช่วย Let's Encrypt`) — เรียก `certbot certonly --webroot` เป็นโปรเซสย่อย (**ไม่เคย** `--standalone` เพราะ Omega-serv ใช้พอร์ต 80 อยู่แล้ว **ไม่เคย** เขียนไคลเอนต์ ACME ขึ้นใหม่) โดยชี้ `--config-dir`/`--work-dir`/`--logs-dir` ไปที่ `secure/certificates/letsencrypt/` ของโปรเจกต์ — **ไม่เคย** `/etc/letsencrypt/` — ซึ่งทำให้ Certbot เองไม่ต้องใช้สิทธิ์พิเศษเลย ใบรับรองที่ได้จะถูกนำเข้าอัตโนมัติ (กลไกเดียวกับ `certs import` ดูตัวอย่าง CLI ด้านบน) และมีการเขียนสคริปต์ hook สำหรับการต่ออายุ โหมดทดสอบ (staging) ถูกเลือกไว้เป็นค่าเริ่มต้น — ยกเลิกเมื่อตรวจสอบแล้วว่าโดเมน/webroot ทำงานได้ เพื่อหลีกเลี่ยงขีดจำกัดอัตราจริงของ Let's Encrypt

สิ่งที่ต้องมีซึ่งอยู่นอกขอบเขตของ Omega-serv ทั้งหมด: โดเมนที่ชี้ไปยัง IP สาธารณะ (DDNS) และพอร์ต 80/443 ที่ถูกส่งต่อมายังเครื่องนี้

### 9d. การต่ออายุอัตโนมัติ (Certbot)

`การตั้งค่าโดยละเอียด → TLS → การต่ออายุอัตโนมัติ` ปรับตามตัวจัดการบริการที่ตรวจพบจริง **สำหรับอินสแตนซ์นี้** (ไม่เคยเป็นกลไกที่ใช้ร่วมกันระหว่างหลายอินสแตนซ์): systemd → สร้างและติดตั้งตัวจับเวลา (`<service>-certbot-renew.timer` วันละสองครั้ง + ดีเลย์แบบสุ่ม `certbot renew` จำกัดอยู่ใน `--config-dir` ของอินสแตนซ์) มิฉะนั้น → บรรทัด crontab (ผู้ใช้ปัจจุบัน ไม่ต้องใช้สิทธิ์พิเศษ) ถ้ามี `crontab` มิฉะนั้น → แสดงคำแนะนำให้ทำเอง โดยไม่เขียนอะไรแบบบังคับ ในบางดิสทริบิวชัน (รวมถึง Arch/Manjaro) แพ็กเกจ Certbot **ไม่ได้** ติดตั้งตัวจับเวลาใดเป็นค่าเริ่มต้น ต่างจาก Debian/Ubuntu — จึงมีหน้าจอนี้แทนที่จะแค่ตรวจสอบกลไกที่สมมติว่ามีอยู่แล้ว เมื่อตั้งค่าแล้ว การต่ออายุจะนำเข้าใบรับรองที่ต่ออายุแต่ละใบใหม่โดยอัตโนมัติ (`certs import`) แล้วรีสตาร์ทบริการ โดยไม่ต้องลงมือเองอีกเลย

## 10. การตรวจสอบความปลอดภัย

## 11. Active Defense (deception + โหมดสงคราม)

โมดูลเสริม (`option enable active_defense` ปิดเป็นค่าเริ่มต้น) ที่ประเมินพฤติกรรมที่เป็นปฏิปักษ์จากสัญญาณ WAF ที่คำนวณไว้แล้ว (`WafDecision`/ชื่อเสียง/รายการบล็อก — ไม่เคยคำนวณคะแนนอิสระซ้ำ) และสามารถสลับแหล่งที่มาไปยังเหยื่อล่อ ทำให้การตอบกลับช้าลงและบันทึกล็อกละเอียดขึ้น สร้างเหตุการณ์ที่นำไปใช้ได้ แล้วส่งออกตัวบ่งชี้การบุกรุก (IoC) ไม่เคยบล็อกทราฟฟิกเอง — การบล็อกระดับเครือข่ายยังเป็นหน้าที่ของ `omega-fire` ส่วน Active Defense สังเกต เบี่ยงเบน ทำให้ช้าลง และบันทึก

**ภัยคุกคามและคะแนน**: ทุกแหล่งที่มา (`IP + แฮช SHA-256 ของ User-Agent`) สะสมคะแนน (`WAF-001` ที่บล็อก +10, การยกระดับชื่อเสียง +25, การแบนที่รู้จักแล้ว +25, POST ไปยังเหยื่อล่อที่ถูกกำหนดแล้ว +30 — ลดลง -5 ทุก 15 นาทีที่ไม่มีเหตุการณ์ใหม่) จัดระดับเป็น `normal`/`suspicious`/`hostile`/`contained` (`contained` ต้องมีการแบนที่รู้จักแล้วด้วย) `mode: monitor` สังเกตโดยไม่ลงมือ `mode: enforce` ใช้การกระทำด้านล่างจริง

**โหมดสงคราม** (`options.active_defense.settings.war_mode`): `DefensePlaybook` (`actions: ["redirect_to_decoy", "enrich_log", "delay", "rate_limit", "create_incident", "export_ioc"]`) ที่ถูกเรียกตามเกณฑ์ที่ตั้งค่าได้ สำหรับทุกแหล่งที่มาที่ไม่ใช่ `normal`:
- `enrich_log` — ล็อก JSONL แยกต่างหาก (`var/log/active-defense-enriched.jsonl` ไม่เคยปนกับล็อก WAF/production) เฮดเดอร์ถูกปกปิด เนื้อหา HTTP ถูกแฮช (SHA-256) หรือตัดทอนตาม `logging.capture_request_body`
- `delay` — การทำให้ช้าลงแบบมีขอบเขตและมี jitter (`war_mode.slowdown.minimum_ms`/`maximum_ms`/`jitter_ms`) ไม่เคยบล็อกลูป asyncio
- `rate_limit` — การจำกัดอัตราเฉพาะต่อแหล่งที่มา (`war_mode.rate_limit.requests`/`window_seconds`) ใช้กลไกเดียวกับ WAF ภายใต้คีย์แยกต่างหาก
- `create_incident` — เปิด/รวมเหตุการณ์อัตโนมัติเมื่อเกิน `thresholds.incident_score`

**Deception**: แหล่งที่มาที่เป็น `hostile`/`contained` สามารถถูกกำหนดให้ไปยังเหยื่อล่อแบบสแตติก (`fake_admin`, `fake_cms`, `fake_api`, `fake_secrets` — การตอบกลับดูน่าเชื่อแต่คงที่เสมอ ไม่เคยอ่านไฟล์จริงหรือรันโปรเซสย่อย) ที่เลือกตามประเภทการโจมตีที่สังเกตได้ (`deception.profiles.<ชื่อ>.match_attack_classes` หนึ่งหรือหลายค่าจาก `scan`/`credential_stuffing`/`sqli`/`xss`/`path_traversal`/`upload_probe`/`api_probe`/`unknown`) การแยกมีสองระดับ ซึ่งยอมรับและบันทึกไว้ตามนั้น:
- **ระดับ 1** (fixture ภายในโปรเซส, `isolation_level: "fixture"` เป็นค่าเริ่มต้น) — การแยกที่อ่อนอย่างชัดเจน: โปรเซสเดียวกัน ผู้ใช้ OS เดียวกับ production ยอมรับได้เพียงเพราะ fixture ไม่เคยทำอะไรนอกจากส่งคืนเทมเพลตสแตติก ชื่อของโปรไฟล์ต้องตรงกับหนึ่งใน 4 fixture ข้างต้นทุกประการ — มิฉะนั้นจะถูกปฏิเสธตอนตรวจสอบ (`validate_active_defense_config`) เพื่อหลีกเลี่ยงกับดักที่เหยื่อล่อตั้งชื่อผิดแล้วไม่เคยทำงานโดยไม่มีใครรู้
- **ระดับ 2** (แบ็กเอนด์ที่แยกจริง, `isolation_level: "proxy"`) — ส่งต่อไปยังโปรเซสแยกผ่าน `options.active_defense.settings.deception.decoy_zones.<ชื่อ>` (upstream `host`/`port` ของเซิร์ฟเวอร์ที่ทำงานอยู่แล้ว ไม่เคยสร้างอัตโนมัติ ไม่เคยอ่านจาก `options.reverse_proxy` — เหยื่อล่อไม่มีทางชี้ไปยังโซน production โดยบังเอิญ ตรวจสอบที่ `config check`) โดยใช้กลไก reverse proxy ขาออกเดียวกับ production (`serve_proxy()` — upstream ติดต่อไม่ได้ขณะมีคำขอจริง: ส่ง 502 กลับไปยังผู้โจมตี ไม่เคยแครช)

**หน้าจอการตั้งค่า** (TUI, ความปลอดภัยเชิงรุก → Active Defense → การตั้งค่า): ตั้งค่าทุกอย่างข้างต้นได้ครบถ้วน — โหมด การเปิดโหมดสงคราม ขอบเขต/การกระทำ/เกณฑ์/การทำให้ช้าลง/ขีดจำกัดคำขอ deception (พฤติกรรมเริ่มต้น CRUD ของโปรไฟล์เหยื่อล่อและโซนเหยื่อล่อ พร้อมค่าตัวอย่างแสดงในทุกช่อง) IoC การจัดเก็บและการบันทึกล็อก — ตรวจสอบด้วยกฎเดียวกับ CLI ก่อนทุกการบันทึก โดยไม่ต้องแก้ไข `config/omega-serve.json` ด้วยมือเลย ต้องรีสตาร์ทเต็มรูปแบบทุกครั้งหลังการเปลี่ยนแปลงใด ๆ (Active Defense ไม่เคยถูกโหลดใหม่ขณะทำงาน)

**เหตุการณ์และ IoC**: ลำดับเวลาครบถ้วนต่อเหตุการณ์ การดึงตัวบ่งชี้ (IP, User-Agent ที่แฮชแล้ว) การส่งออก JSON แบบมีเวอร์ชัน/CSV เฉพาะ IoC ที่แชร์ได้/รายงาน Markdown และรูปแบบแลกเปลี่ยน **STIX 2.1** (bundle สำหรับโหลดเข้า OpenCTI, SIEM…) และ **MISP** (เหตุการณ์สำหรับนำเข้าผ่านอินเทอร์เฟซของ MISP) ทำเครื่องหมาย TLP:AMBER เป็นค่าเริ่มต้น — เป็นไฟล์ในเครื่อง ไม่เคยถูกส่งออกไป ทุกการส่งออกมาพร้อมไฟล์ `<export>.sha256` (รูปแบบ `sha256sum` มาตรฐาน) ส่งออกอัตโนมัติเมื่อปิดเหตุการณ์ถ้า `ioc.auto_export_on_close` (ค่าเริ่มต้นเป็นจริง) สถานะที่หมดอายุและล็อกการตรวจสอบถูกล้างอัตโนมัติ ฐานข้อมูลมีเพดาน (ป้องกันดิสก์เต็ม) ส่วน `active-defense purge` ยังปิดเหตุการณ์ที่กลับมาเงียบแล้วด้วย

**การจำลอง**: `active-defense simulate` (CLI) และปุ่ม "จำลอง" (TUI หน้าจอความปลอดภัยเชิงรุก) คาดการณ์คะแนน/ระดับ และอธิบายแต่ละการกระทำที่จะเกิดขึ้น — dry-run อย่างเคร่งครัด ไม่มีการเขียนจริง ไม่มีผลกระทบต่อเครือข่าย

การสำรอง/กู้คืน: `config backup --include-active-defense` รวมฐานข้อมูล sqlite (ภัยคุกคาม/เหตุการณ์/การกำหนด) ไว้ในไฟล์เก็บถาวร — ไม่เคยมีความลับเป็นข้อความธรรมดา จึงไม่ต้องใช้ `--confirm-secrets` ต่างจาก `--include-auth`

## 11b. รายการพาธที่อ่อนไหว (WAF)

WAF สามารถโหลด **รายการที่แก้ไขได้** เป็นไฟล์ข้อความ หนึ่งพาธ (หรือหนึ่งคีย์เวิร์ด) ต่อบรรทัด จาก **ความปลอดภัยเชิงรุก → WAF → Custom → เพิ่ม → « โหลดรายการ »** ไม่มีอะไรถูกโหลดเป็นค่าเริ่มต้น: เป็นการกระทำที่ชัดเจน

- **รายการอ้างอิงที่จัดให้**: `sensitive-paths-hostile` (298 พาธที่ไม่มีการใช้งานที่ชอบธรรม: ความลับ, ไฟล์สำรอง, VCS, คอนโซล…) และ `sensitive-paths-probe` (132 พาธสำหรับการสำรวจ ซึ่งบางครั้งเว็บไซต์จริงก็ให้บริการ: `/admin`, `/api`, การตรวจติดตาม…) เมื่อโหลด จะมีการสร้าง **สำเนาในเครื่อง** ใน `secure/waf/rules/keywords/`: คุณแก้ไขสำเนานั้น และการอัปเดต omega-serv ไม่เคยเขียนทับ (« รายการใหม่ในต้นแบบ » จะเสนอรายการใหม่ให้ทีละช่อง)
- **ไวยากรณ์**: `/admin` (→ `/admin` และ `/admin/xxx` ไม่เคย `/administrator`), `/.git/` (ทุกอย่างที่อยู่ข้างใต้), `/*.bak` (นามสกุล), `!/api/v1` (ข้อยกเว้น มีความสำคัญเหนือกว่าเสมอ) พาธถูกถอดรหัสเหมือนในเอนจิน (`%2e`, การเข้ารหัสซ้ำ, อักขระเต็มความกว้าง)
- **ความรุนแรง**: *สังเกตการณ์* (บันทึกล็อกเท่านั้น แนะนำสำหรับการโหลดครั้งแรก) แล้วจึงเป็นปานกลาง (ไม่เคยบล็อกด้วยตัวเอง) หรือสูง (403 ตั้งแต่การเข้าถึงครั้งแรก)
- **การกระทำซ้ำเฉพาะของแต่ละรายการ**: การเข้าถึงครั้งที่ 1 = ข้อมูลหรือการปฏิเสธ; N ครั้งใน M นาที = การแบนชั่วคราวระดับแอปพลิเคชัน (ตอบกลับ 451 แม้ผ่าน Tailscale); การบล็อกซ้ำ ๆ = การแบนระดับเครือข่ายโดย omega-jail ค่าอ้างอิง: hostile 2 ครั้งใน 10 นาที → 24 ชม., probe 5 ครั้งใน 10 นาที → 1 ชม.
- **ไม่เคยแบนอัตโนมัติ** สำหรับเครื่องในพื้นที่ Tailscale (`100.64.0.0/10`) และเครือข่ายในพื้นที่ (`options.waf.reputation.never_auto_block`): เฉพาะทราฟฟิกภายนอกเท่านั้นที่ถูกแบนได้ เมื่ออยู่หลังพร็อกซีในเครื่อง การยกเว้น `127.0.0.1` ต้องเปิด `trusted_proxy` `X-Forwarded-For` ถูกอ่านจากขวาไปซ้าย: ไคลเอนต์ไม่สามารถอ้างตัวว่าอยู่ในเครื่องได้
- **มาตรการป้องกัน**: พาธที่สำคัญถูกป้องกัน (`/`, `robots.txt`, `sitemap.xml`, `/.well-known/acme-challenge/`…) ปฏิเสธรายการที่บล็อกซึ่งจะกระทบเส้นทางที่ให้บริการจริง (alias, reverse proxy, โซน Auth, webroot) **« ตรวจกับล็อกของฉัน »** ในตัวแก้ไข (บรรทัดที่จะกระทบคำขอที่สำเร็จ เพิ่มข้อยกเว้นได้ในคลิกเดียว)
- **ตัวแก้ไขในตัว**: การวินิจฉัยแบบสดพร้อมหมายเลขบรรทัด « ทดสอบ » พาธ การเขียนอย่างปลอดภัย (คงสิทธิ์และกลุ่มไว้ ปฏิเสธลิงก์สัญลักษณ์ ตรวจจับการแก้ไขจากภายนอก) ตรวจสอบว่าบัญชีของบริการอ่านได้ (« แก้ไขสิทธิ์ ») และการโหลดใหม่อย่าง **ซื่อตรง**: ถูกปฏิเสธพร้อมเหตุผลถ้ารายการไม่ผ่านการตรวจสอบ โดยเซิร์ฟเวอร์ยังคงใช้กฎปัจจุบัน

## 11c. การจำกัดอัตราตามโฟลเดอร์และตาม IP/เครือข่าย (WAF)

การจำกัดอัตราของ WAF (token bucket, `options.waf.rate_limit` ค่าเริ่มต้น 60 คำขอ / 60 วินาทีต่อ IP) ปรับละเอียดได้จาก **ความปลอดภัยเชิงรุก → WAF → ข้อจำกัด** (หรือด้วยมือ `rate_limit.path_policies` / `rate_limit.source_policies`):

- **กฎตามโฟลเดอร์** (`prefix`, `requests`, `window_seconds`): **แทนที่** ขีดจำกัดรวมสำหรับโฟลเดอร์นั้น พร้อมตัวนับของตัวเอง (`requests: 0` = ไม่จำกัด) คำนำหน้าที่ยาวที่สุดชนะ `/images` ครอบคลุม `/images/a.png` แต่ไม่เคยครอบคลุม `/images2` โดยทั่วไปใช้กับหน้าที่หนัก (แกลเลอรีรูปภาพ) ที่ส่งคืน 429
- **กฎตาม IP/เครือข่าย** (`network`, `requests`, `window_seconds`, `trusted`): หลักการเดียวกัน เครือข่ายที่แม่นยำที่สุดชนะ ลำดับความสำคัญ: โฟลเดอร์ แล้ว IP/เครือข่าย แล้วขีดจำกัดรวม
- **การแบนไม่เปลี่ยนสำหรับสาธารณะ**: การเกินขีดจำกัดโดย IP สาธารณะยังถูกบันทึกเป็น `"action": "block"` ใน `waf-alerts.log` จึงถูก omega-jail แบนได้ (ปฏิเสธ 3 ครั้งใน 10 นาที → 12 ชม.) **แหล่งที่ปลอดภัย** — เครือข่าย `never_auto_block` หรือกฎที่ทำเครื่องหมาย `trusted: true` — ยังได้รับ 429 แต่ถูกบันทึกเป็น `"action": "throttle"` ซึ่ง jail ไม่เคยนับ
- **สคริปต์ magnet**: การจำกัดอัตราของมันเอง (ตอบกลับ 429) ไม่เคยถูกนับเป็นการตรวจจับ จึงไม่เคยนำไปสู่การแบนอัตโนมัติ สำหรับคำขอที่อยู่ในกฎโฟลเดอร์หรือกฎ IP/เครือข่าย กฎเนทีฟเป็นตัวตัดสินและ 429 ของ magnet จะถูกเพิกเฉย (ซิกเนเจอร์การโจมตีของมันยังคงใช้อยู่)
- กฎอัตรา **ไม่เคย** ปิดการตรวจสอบของ WAF ในทางกลับกัน ข้อยกเว้นการตรวจสอบ (`exclusions.path_prefixes`) ไม่เคยยกเลิก rate limit เมื่อไม่ได้เปิด `trusted_proxy` กฎที่ครอบคลุม `127.0.0.1`/`::1` จะถูกเพิกเฉย (มาตรการป้องกันเดียวกับ `never_auto_block`)

## 11d. RIPOSTE (การตอบโต้แบบเป็นขั้นตามระยะเวลา)

โมดูลเสริม (`option enable riposte` ปิดไว้เป็นค่าเริ่มต้น ต้องรีสตาร์ทเต็มรูปแบบ): ขณะที่ Active Defense ตอบสนอง**ระหว่าง**คำขอ RIPOSTE จะทำงาน**ตามระยะเวลา** มันจำที่อยู่ที่กลับมาอีกหลังช่วงเงียบ (ช่วงเหตุการณ์) และแบนที่อยู่เหล่านั้นนานขึ้นเรื่อย ๆ — ขั้นเริ่มต้น 1 ชั่วโมง, 6 ชั่วโมง, 24 ชั่วโมง, 7 วัน ช่วงพิจารณาการกระทำซ้ำ 30 วัน เก็บประวัติ 90 วัน

- **โปรเซสแยก** ที่บริการเป็นผู้เริ่มและดูแล (มีหนึ่งหรือหลายโปรเซส หนึ่งโปรเซสต่ออินสแตนซ์): อ่านบันทึกของ WAF และ Active Defense ไม่เคยอ่านคำขอที่กำลังประมวลผล หากไม่ได้เปิด WAF มันจะไม่เห็นการโจมตีใดเลย
- **นโยบาย**: เมื่อใดจะดำเนินการ (ประเภทการโจมตี จำนวนครั้งที่กลับมา ระดับ Active Defense จำนวนครั้งที่เข้าเหยื่อล่อ) และดำเนินการอย่างไร (แบนเฉพาะเครื่องใน blocklist ของ WAF, แบนเฉพาะเครื่อง + แบนระดับเครือข่ายผ่าน jail ของ omega-jail หรือขยายเวลาเหยื่อล่อของ Active Defense) มีห้าสถานการณ์พร้อมโหลด ทุกนโยบายวัดผลกับบันทึกจริงและจำลองได้ก่อนเปิดใช้ นโยบายที่เปิดใช้จะทำงานโดยอัตโนมัติ
- **ไม่มีอะไรหายไป**: ทุกการดำเนินการยังมองเห็นได้ ไม่ว่ากำลังทำอยู่หรือสิ้นสุดแล้ว พร้อมเหตุผล การหยุดมีสามระดับ: ยกเลิกการดำเนินการหนึ่งรายการ (พร้อมยกเว้นหรือ « ไม่นับเป็นการกระทำซ้ำ »), ปิดกฎหนึ่งข้อ, หยุดฉุกเฉินที่ถูกจดจำไว้
- **มาตรการป้องกัน**: ข้อยกเว้นเดียวกับ WAF (เครื่องตัวเอง, Tailscale, เครือข่ายภายใน) ไม่ทับการแบนที่ตั้งเองหรือที่นานกว่า หนึ่งการดำเนินการต่อหนึ่งช่วงเหตุการณ์ และจำกัดจำนวนการแบนพร้อมกัน
- **แบนในเครื่องและแบนเครือข่าย**: omega-serv วางการแบนในเครื่องไว้ในรายการบล็อกของ WAF — ที่อยู่นั้นจะได้รับหน้า 451 “IP ของคุณถูกแบน” ในทุกคำขอตลอดระยะเวลาที่ถูกแบน ส่วนการแบนเครือข่ายจะส่งให้ fail2ban ผ่าน jail ของ omega-jail (`<service>-riposte-1h/6h/24h/7d` หนึ่งชุดต่ออินสแตนซ์) ซึ่งไม่มีผลเมื่อการเชื่อมต่อมาผ่านพร็อกซีในเครื่อง (Tailscale Funnel) ในกรณีนั้นมีเพียงการแบนในเครื่องที่ป้องกัน
- **อินเทอร์เฟซ**: หกหน้าจอใน ความปลอดภัยเชิงรุก (สถานะ, นโยบาย, การดำเนินการ, การกระทำซ้ำ, จำลอง, การตั้งค่า) และคำสั่งเดียวกันในบรรทัดคำสั่ง (`riposte …`) การสำรองข้อมูล: `config backup --include-riposte`

## 11e. การแทรกแซงด้วยตนเอง (ความปลอดภัยเชิงรุก)

กรอบ **การแทรกแซงด้วยตนเอง** ใต้สามบล็อกของความปลอดภัยเชิงรุก สำหรับดำเนินการด้วยตนเองโดยไม่ต้องเขียนกฎการกำหนดค่า: แบนที่อยู่ IP โดยไม่มีเงื่อนไข ยกเลิกแบน และดูการแบนทั้งหมดที่มีอยู่

- **แบน**: ที่อยู่ IPv4 หรือ IPv6 เหตุผล และระยะเวลา (1 ชม. ถึง 30 วัน อิสระหรือถาวร) การแบนทำผ่านรายการบล็อกของ WAF: หน้า 451 ทั่วทั้งเว็บไซต์ ก่อนการกำหนดเส้นทาง — แบ็กเอนด์จะไม่เห็นที่อยู่นั้นเลย มีผลทันทีกับทั้งสองเอนจิน ไม่ต้องใช้สิทธิ์ root เครือข่ายแบนได้ใน WAF → โมดูล
- **เป็นอิสระ**: ไม่เกี่ยวข้องกับ Active Defense หรือ RIPOSTE — การแบนด้วยตนเองไม่นับเป็นการกระทำซ้ำ และไม่มีระบบอัตโนมัติใดแทนที่ ต้องยืนยันสำหรับที่อยู่ภายในเครื่อง ส่วนตัว หรือ Tailscale
- **ยกเลิกแบน**: เฉพาะการแบนที่ตั้งที่นี่ การแบนอื่นยกเลิกในที่ที่ตั้งไว้ (WAF → โมดูล, RIPOSTE → การดำเนินการ)
- **สถานะการแบน**: การแบนทั้งหมดพร้อมที่มา (ด้วยตนเอง, แบนอัตโนมัติ WAF, RIPOSTE, omega-jail, Magnet) ส่งออกเป็น JSON, HTML หรือ TXT ได้ — หนึ่งที่อยู่ต่อบรรทัด นำเข้า omega-fire ได้ทันที

## 12. บริการและการดำเนินงาน

ตรวจจับ systemd/OpenRC/runit อัตโนมัติ (`service install/status/start/stop/restart/enable/disable/uninstall`) unit systemd ที่สร้างขึ้นใช้การเสริมความแข็งแกร่งที่ต่อรองไม่ได้เป็นค่าเริ่มต้น: `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome`, `ReadWritePaths` จำกัดที่ `var/`, บังคับผู้ใช้/กลุ่มเฉพาะ, `UMask=0007`, `Restart=on-failure` หยุดอย่างเรียบร้อยเมื่อได้รับ SIGTERM (ระบายการเชื่อมต่อที่กำลังดำเนินอยู่ ช่วงผ่อนผันตั้งค่าได้ แล้วปิดแบบบังคับ) โหลดใหม่ขณะทำงานเมื่อได้รับ SIGHUP (เฉพาะกฎ WAF และโซน Auth — bind/พอร์ต/TLS และ Active Defense ไม่เคยเปลี่ยนได้โดยไม่รีสตาร์ทเต็มรูปแบบ)

## 13. ล็อก

`var/log/access.log` (รูปแบบ Apache combined + `request_id` การหลีกอักขระเพื่อป้องกันการฉีดล็อก), `var/log/error.log` หมุนเวียนตามขนาด/จำนวนไฟล์ที่เก็บไว้ (`logs.rotation`) WAF เนทีฟ: `var/log/waf-alerts.log` (`options.waf.logging.path`) สคริปต์ magnet: `options.waf.magnet.paths.alerts_log`/`.blocklist_log` ค่าเริ่มต้น `var/log/waf-magnet-alerts.log`/`var/log/waf-magnet-blocklist.log` — ถูกเพิ่มเข้าคลังทันที (ปุ่ม *เพิ่มล็อกที่รู้จักของ Omega-Serv*) เฉพาะเมื่อ magnet เปิดใช้งาน แต่ `lnav` เสนอให้เสมอ (ไฟล์ที่ไม่มีจะถูกข้ามตอนเรียกใช้)

### 13a. ตัวจัดการล็อก

หน้าจอ **จัดการล็อก** เป็นตัวจัดการจริง ไม่ใช่แค่ตัวอ่าน: ล็อกทุกตัว (ล็อกของอินสแตนซ์ ไฟล์ที่เพิ่มด้วยมือ หรือสำเนาจากเซิร์ฟเวอร์ระยะไกล) จะเข้าสู่ **คลัง** แล้วจึง:

- **อ่าน** — ตัวดูสามแบบ: แบบง่าย (แดชบอร์ดสด: รหัส HTTP การปฏิเสธ 403/429 IP ที่พบบ่อยที่สุด พาธ), แบบคลาสสิก (อ่านและติดตาม), `lnav` ในตัว (รวมหลายล็อก) **รายการโปรด** แต่ละรายการเก็บชุดที่เลือกพร้อมตัวดูไว้ภายใต้ชื่อหนึ่ง
- **วิเคราะห์** — **ดูและจัดการ IP** (ที่อยู่ที่มีความเคลื่อนไหวมากที่สุด ในช่วง 24 ชม. 7 วัน 30 วัน หรือทั้งไฟล์) และ **สถิติ** (รายงานฉบับเต็ม ส่งออก JSON/HTML) คำนวณเบื้องหลังบนหลายคอร์ แม้กับไฟล์ขนาดใหญ่ ใน **ดูและจัดการ IP** ยังพิมพ์ IP ที่ต้องการได้โดยตรง: ระบบจะนับบรรทัดของ IP นั้นในแต่ละล็อก แล้วนำออกได้ในคลิกเดียว
- **ตรวจสอบ** — **สุขภาพล็อก**: สิทธิ์ ล็อกที่เงียบหรือเสียหาย การหมุนเวียน พื้นที่ดิสก์ ไฟล์เก็บถาวรและงานอัตโนมัติ พร้อมสิ่งที่ต้องทำสำหรับแต่ละข้อที่พบ ส่งออก JSON/HTML/TXT
- **สำรอง** — หมุนเวียนตามเกณฑ์ขนาด สำรองทันที กู้คืนและล้างไฟล์เก็บถาวร (`var/backups/logs/`)
- **ทำงานอัตโนมัติ** — การสำรองตามกำหนดเวลาหนึ่งรายการต่อหนึ่งล็อก (ทุก N วัน) เรียกใช้ทุกคืนโดยตัวจับเวลา systemd หรือบรรทัดใน crontab ของคุณ (OpenRC, runit) ภายใต้บัญชีของคุณเสมอ ไม่เคยเป็น root

เมื่อสิทธิ์ขัดขวาง omega-serv จะขอรหัสผ่าน sudo ของคุณเพื่ออ่านล็อก หรือเพื่อแก้ไขเฉพาะสิทธิ์ที่ผิด (คำสั่งจะแสดงให้เห็นก่อนเรียกใช้)

### 13b. แหล่งระยะไกล (SSH)

รวมศูนย์ล็อกของเซิร์ฟเวอร์แบ็กเอนด์ที่อยู่ในเครือข่ายภายในเดียวกันหลัง reverse proxy ตามคำขอที่ชัดเจน (หน้าจอ **จัดการล็อก → คลัง → แหล่งระยะไกล (SSH)**) การ « fetch » เป็นการกระทำด้วยมือครั้งเดียว ไม่เคยเป็นกระแสสดหรือการตรวจถามอัตโนมัติ: **สำเนา** ถูกดึงผ่าน `scp` ในขณะที่คลิก *ดึงข้อมูลเดี๋ยวนี้* เขียนลงใน `var/log/remote/` แล้วเพิ่มเข้าคลังเหมือนล็อกปกติ (คอลัมน์ *การเข้าถึง* = `ssh`, คอลัมน์ *แก้ไขล่าสุด* = วันที่ของการดึง **ครั้งนี้** — ไม่เคยเป็นวันที่ของไฟล์ระยะไกล) การดึงใหม่เพียงแทนที่สำเนาก่อนหน้าด้วยฉบับที่ใหม่กว่า

มาตรการป้องกันโดยตั้งใจ: ไม่มีการสแกนเครือข่ายอัตโนมัติ ไม่มีการเชื่อมต่อโดยไม่มีการตั้งค่าที่ชัดเจน (ป้าย/โฮสต์/พาธระยะไกล ผู้ใช้/พอร์ต/คีย์ส่วนตัวแบบเลือกได้ — ถ้าว่าง จะปล่อยให้ `ssh`/`~/.ssh/config` ตัดสินเหมือนพิมพ์คำสั่งเอง) ไม่เคยถามหรือเก็บรหัสผ่าน (คีย์ส่วนตัวถูกอ้างอิงด้วยพาธเท่านั้น Omega-serv ไม่เคยอ่านหรือเก็บ) ไม่มีการตรวจสอบขนาดก่อนถ่ายโอน ความสามารถ `scp` ตรวจจับในเครื่องใน **ทะเบียนความสามารถ** (ตรวจเฉพาะว่ามีไฟล์โปรแกรม ไม่เคยทดสอบว่าติดต่อโฮสต์ได้) Samba ถูกพักไว้โดยตั้งใจ (YAGNI ตราบใดที่ยังไม่มีความต้องการจริงที่ได้รับการยืนยัน)
